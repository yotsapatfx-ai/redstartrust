## S11 · การใช้ข้อมูลส่วนบุคคลเพื่อการตลาด (251–275)

**P10-251 · การตั้งทะเบียนติดตามความยินยอมการตลาด `MKT-CONSENT`** `w2` `DOC+ACC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจตั้งตารางบันทึกเฉพาะไฟล์นี้ชื่อ `MKT-CONSENT` ก่อนเริ่มหมวด S11 หรือไม่ ตารางต้องมีอย่างน้อย 6 ช่อง: วันเวลาที่ให้/ถอนความยินยอม (UTC) · ช่องทาง (อีเมล/SMS/โทร/push) · สถานะปัจจุบัน · ข้อความคำต่อคำที่ใช้ขอความยินยอม · Evidence ID · หมายเหตุ ตารางนี้เป็นเครื่องมือทำงานเฉพาะไฟล์ ไม่ใช่นิยามกลางของเสา
- **ขั้นตอนการตรวจ:**
  1. เปิดไฟล์ตารางใหม่ตั้งชื่อ `MKT-CONSENT` สำหรับโบรกรายนี้
  2. วางหัวตาราง 6 ช่องตามที่กำหนด
  3. ย้อนกลับไปดูขั้นตอนสมัครบัญชี บันทึกสถานะความยินยอมเริ่มต้นที่ระบบตั้งไว้ (ติ๊กไว้แล้ว/ว่าง/ไม่มีช่องนี้)
  4. เก็บภาพหน้าจอขั้นตอนสมัครที่เห็นช่องยินยอมพร้อมนาฬิกาเครื่อง
  5. บันทึกวันเวลา UTC ที่สร้างตาราง
  6. บันทึกไฟล์เป็นฉบับตั้งต้นที่แก้ไม่ได้ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ไฟล์ตาราง `MKT-CONSENT` ฉบับตั้งต้น (`RST-BRKA-P10-251-01`) · ภาพหน้าจอขั้นตอนสมัคร (`-02`)
- **ผ่าน:** มีไฟล์ตารางครบ 6 ช่อง สร้างก่อนเริ่มบันทึกข้อมูลใดในหมวดนี้
- **ไม่ผ่าน:** ไม่มีไฟล์ตาราง หรือขาดช่องใดช่องหนึ่ง
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** ผู้ตรวจ Broker A สร้างตารางครบ 6 ช่องก่อนเริ่มขั้นตอนสมัคร → **ผ่าน**

**P10-252 · ความยินยอมด้านการตลาดแยกจากการยอมรับสัญญาหรือไม่** `w3` `ACC+DOC`

- **ตรวจอะไร:** ตรวจว่าตอนสมัครบัญชี ช่องยินยอมรับการตลาดเป็นช่องแยกต่างหากจากช่องยอมรับข้อตกลงลูกค้า/เงื่อนไขการใช้บริการหรือไม่ จุดที่ต้องดูคือหน้าสมัครทั้งหมดที่มีช่องติ๊กยอมรับ บันทึกจำนวนช่องติ๊กที่พบและข้อความกำกับแต่ละช่อง
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าสมัครทีละหน้าจนถึงขั้นยืนยันสุดท้าย
  2. จับภาพทุกช่องติ๊กที่พบพร้อมข้อความกำกับเต็ม
  3. จัดกลุ่มช่องติ๊กเป็นสองประเภท: (ก) การยอมรับสัญญาที่จำเป็นต่อการใช้บริการ (ข) การยินยอมรับการตลาด
  4. บันทึกว่าทั้งสองประเภทเป็นช่องเดียวกันที่ติ๊กครั้งเดียวได้ทั้งคู่หรือแยกกัน
  5. ถ้าแยกกัน บันทึกว่าปฏิเสธเฉพาะช่องการตลาดแล้วยังสมัครต่อได้หรือไม่ (ทดสอบจริงด้วยบัญชีของตนเอง)
  6. บันทึกผลลงตาราง `MKT-CONSENT` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพทุกช่องติ๊กพร้อมข้อความกำกับ (`RST-BRKA-P10-252-01` ถึง `-04`) · บันทึกผลการทดสอบปฏิเสธเฉพาะการตลาด
- **ผ่าน:** ช่องยินยอมการตลาดแยกจากช่องยอมรับสัญญา และปฏิเสธได้โดยยังสมัครใช้บริการต่อได้
- **ไม่ผ่าน:** ติ๊กครั้งเดียวยอมรับทั้งสัญญาและการตลาดพร้อมกัน หรือปฏิเสธการตลาดแล้วสมัครต่อไม่ได้
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker B มีช่องติ๊กเดียวเขียนว่า *"ยอมรับข้อตกลงลูกค้าและยินยอมรับข่าวสารการตลาด"* → **ไม่ผ่าน**

**P10-253 · ช่องยินยอมตั้งต้นเป็นติ๊กไว้แล้วหรือว่างเปล่า** `w3` `ACC`

- **ตรวจอะไร:** ตรวจว่าช่องยินยอมรับการตลาดตอนสมัครมีสถานะเริ่มต้นเป็น "ติ๊กไว้แล้ว" (opt-out) หรือ "ว่างเปล่าให้ผู้ใช้ติ๊กเอง" (opt-in) จุดที่ต้องดูคือสถานะของช่องนั้นก่อนผู้ตรวจแตะสิ่งใด บันทึกภาพก่อนแตะช่องนั้นให้ชัดเจน
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าสมัครในโหมดไม่บันทึกประวัติ
  2. ก่อนคลิกช่องยินยอมใด ๆ จับภาพซูมเฉพาะช่องยินยอมการตลาดให้เห็นสถานะติ๊ก
  3. บันทึกว่าสถานะเริ่มต้นคือติ๊กไว้แล้วหรือว่าง
  4. ทำซ้ำขั้น 1–3 บนหน้าจอมือถือแยกต่างหาก เพราะบางเว็บแสดงค่าเริ่มต้นต่างกันตามอุปกรณ์
  5. บันทึกผลทั้งสองอุปกรณ์ลงตาราง `MKT-CONSENT` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพซูมช่องยินยอมก่อนแตะ ทั้งเดสก์ท็อปและมือถือ (`RST-BRKA-P10-253-01`, `-02`)
- **ผ่าน:** ช่องยินยอมการตลาดเป็นค่าว่างตั้งต้นทั้งสองอุปกรณ์ ต้องให้ผู้ใช้ติ๊กเองจึงจะยินยอม
- **ไม่ผ่าน:** ช่องยินยอมติ๊กไว้ล่วงหน้าในอุปกรณ์ใดอุปกรณ์หนึ่ง
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker C มีช่องยินยอมว่างบนคอมพิวเตอร์ แต่ติ๊กไว้แล้วบนแอปมือถือ → **ไม่ผ่าน**

**P10-254 ● · แยกประเภทช่องทางการตลาดให้เลือกได้หรือไม่** `w2` `ACC+PLT`

- **ตรวจอะไร:** ตรวจว่าระบบให้ลูกค้าเลือกยินยอมแยกรายช่องทาง (อีเมล · SMS · โทรศัพท์ · การแจ้งเตือนในแอป) หรือบังคับยินยอมทุกช่องทางพร้อมกันเป็นก้อนเดียว จุดที่ต้องดูคือหน้าตั้งค่าความเป็นส่วนตัว/การแจ้งเตือนในพื้นที่ลูกค้า บันทึกรายการช่องทางที่แยกให้เลือกได้จริง
- **ขั้นตอนการตรวจ:**
  1. เข้าสู่ระบบด้วยบัญชีของตนเอง เปิดหน้าตั้งค่าความเป็นส่วนตัวหรือการแจ้งเตือน
  2. บันทึกรายการช่องทางการตลาดทั้งหมดที่ปรากฏพร้อมสถานะเปิด/ปิดของแต่ละช่องทาง
  3. ทดสอบปิดเฉพาะช่องทางอีเมล เก็บภาพก่อนและหลังกด
  4. ตรวจว่าช่องทางอื่นยังเปิดอยู่ตามเดิมหรือถูกปิดไปด้วย
  5. บันทึกผลลงตาราง `MKT-CONSENT` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าตั้งค่าก่อนและหลังทดสอบ (`RST-BRKA-P10-254-01`, `-02`)
- **ผ่าน:** ระบบให้เลือกเปิด/ปิดแยกรายช่องทางได้จริง และปิดช่องทางหนึ่งไม่กระทบช่องทางอื่น
- **ไม่ผ่าน:** มีสวิตช์เดียวควบคุมทุกช่องทางพร้อมกัน
- **ยังไม่ได้ตรวจ:** โบรกใช้ช่องทางการตลาดเดียวเท่านั้น จึงไม่มีกรณีต้องแยก
- **ตัวอย่าง:** Broker A มีสวิตช์เดียวชื่อ *"รับข่าวสารการตลาด"* ควบคุมทั้งอีเมลและ SMS พร้อมกัน → **ไม่ผ่าน**

**P10-255 · บังคับรับการตลาดเพื่อใช้บริการหรือไม่** `w3` `ACC+DOC`

- **ตรวจอะไร:** ตรวจว่าการปฏิเสธรับการตลาดทำให้ใช้บริการหลัก (เปิดบัญชี ฝาก ถอน เทรด) ไม่ได้หรือมีข้อจำกัดหรือไม่ จุดที่ต้องดูคือผลลัพธ์จริงหลังปฏิเสธการตลาดในข้อ 252–253 บันทึกว่าฟังก์ชันใดใช้ไม่ได้หลังปฏิเสธ
- **ขั้นตอนการตรวจ:**
  1. ใช้บัญชีที่ปฏิเสธการตลาดแล้วจากข้อ 252
  2. ทดสอบฝากเงินขนาดเล็กตามชุดยอดมาตรฐาน
  3. ทดสอบส่งคำสั่งเทรดขนาดเล็กที่สุด
  4. ทดสอบเปิดหน้าฟีเจอร์ทุกหมวดของพื้นที่ลูกค้า บันทึกฟีเจอร์ใดที่ล็อกไว้หรือขึ้นข้อความให้เปิดรับการตลาดก่อน
  5. บันทึกผลลงตาราง `MKT-CONSENT` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพผลการฝาก/เทรด/เปิดฟีเจอร์ทุกหมวด (`RST-BRKA-P10-255-01` ถึง `-04`)
- **ผ่าน:** ใช้บริการหลักได้ครบทุกฟังก์ชันโดยไม่ต้องยินยอมรับการตลาด
- **ไม่ผ่าน:** มีฟังก์ชันหลักอย่างน้อย 1 อย่างใช้ไม่ได้หรือถูกจำกัดเพราะปฏิเสธการตลาด
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker B ล็อกโปรแกรมส่วนลดค่าคอมมิชชันไว้เฉพาะลูกค้าที่ยินยอมรับการตลาด → **ไม่ผ่าน**

**P10-256 ● · นโยบายบอกวัตถุประสงค์การใช้ข้อมูลเพื่อการตลาดชัดหรือไม่** `w2` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายความเป็นส่วนตัว (อ้างอิงจากสำเนาที่เก็บไว้แล้วใน `p10-01`) ระบุวัตถุประสงค์การใช้ข้อมูลเพื่อการตลาดแยกเป็นข้อของตัวเองหรือไม่ ระบุว่าจะใช้ข้อมูลใดบ้าง (พฤติกรรมเทรด · ประวัติฝากถอน · ข้อมูลติดต่อ) เพื่อทำอะไร บันทึกข้อความคำต่อคำ
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนานโยบายความเป็นส่วนตัวที่เก็บไว้แล้วจาก `p10-01` **ห้ามเข้าเว็บใหม่**
  2. ค้นหัวข้อที่เกี่ยวกับการตลาดหรือการสื่อสารเชิงพาณิชย์
  3. คัดลอกข้อความที่ระบุวัตถุประสงค์และประเภทข้อมูลที่ใช้เพื่อการตลาด
  4. ตรวจว่าระบุแยกจากวัตถุประสงค์อื่น (เช่น การให้บริการ การปฏิบัติตามกฎหมาย) หรือรวมกันจนแยกไม่ออก
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความหัวข้อวัตถุประสงค์การตลาดในนโยบาย (`RST-BRKA-P10-256-01`)
- **ผ่าน:** นโยบายระบุวัตถุประสงค์การใช้ข้อมูลเพื่อการตลาดเป็นข้อแยก พร้อมประเภทข้อมูลที่ใช้
- **ไม่ผ่าน:** ไม่มีหัวข้อนี้ หรือรวมปนกับวัตถุประสงค์อื่นจนแยกไม่ออก
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตาม `p10-01`
- **ตัวอย่าง:** นโยบายของ Broker C เขียนรวมว่า *"เราใช้ข้อมูลของท่านเพื่อให้บริการและวัตถุประสงค์ทางธุรกิจอื่น ๆ"* โดยไม่แยกเรื่องการตลาด → **ไม่ผ่าน**

**P10-257 · การทำโปรไฟล์ลูกค้าเพื่อกำหนดเนื้อหาการตลาดเฉพาะราย** `w2` `DOC+PLT`

- **ตรวจอะไร:** ตรวจว่านโยบายเปิดเผยหรือไม่ว่ามีการทำโปรไฟล์ (profiling) จากข้อมูลของลูกค้าเพื่อกำหนดเนื้อหาหรือข้อเสนอการตลาดเฉพาะราย และมีสิทธิคัดค้านการทำโปรไฟล์หรือไม่ จุดที่ต้องดูคือหัวข้อ profiling หรือ automated decision ในนโยบาย และข้อเสนอที่ได้รับจริงเทียบกับที่ลูกค้ารายอื่นอาจได้รับ
- **ขั้นตอนการตรวจ:**
  1. ค้นคำว่า `profiling` `การทำโปรไฟล์` `เฉพาะบุคคล` `personalized` ในสำเนานโยบาย
  2. บันทึกข้อความที่พบพร้อมตำแหน่ง
  3. บันทึกข้อเสนอโปรโมชันที่ได้รับจริงในพื้นที่ลูกค้าตลอดรอบตรวจ พร้อมวันเวลา
  4. เทียบว่าข้อเสนอเปลี่ยนไปตามพฤติกรรมของบัญชี (เช่น ปริมาณเทรดที่ลดลง) หรือคงที่
  5. ค้นว่ามีช่องทางคัดค้านการทำโปรไฟล์หรือไม่ในหน้าตั้งค่า
  6. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความ profiling ในนโยบาย (`RST-BRKA-P10-257-01`) · บันทึกข้อเสนอที่ได้รับตามเวลา
- **ผ่าน:** นโยบายเปิดเผยการทำโปรไฟล์ชัดเจนและมีช่องทางคัดค้าน หรือไม่มีการทำโปรไฟล์เลย
- **ไม่ผ่าน:** พบสัญญาณว่ามีการทำโปรไฟล์ (ข้อเสนอเปลี่ยนตามพฤติกรรม) แต่นโยบายไม่เปิดเผยและไม่มีช่องทางคัดค้าน
- **ยังไม่ได้ตรวจ:** ไม่ได้รับข้อเสนอการตลาดใดเลยตลอดรอบตรวจ จึงเทียบไม่ได้
- **ตัวอย่าง:** Broker A เสนอโบนัสเพิ่มขึ้นเรื่อย ๆ หลังบัญชีของผู้ตรวจเริ่มเทรดน้อยลง โดยไม่มีข้อความ profiling ในนโยบายเลย → **ไม่ผ่าน**

**P10-258 · การใช้ข้อมูลพฤติกรรมการเทรดกำหนดเนื้อหาการตลาด** `w2` `PLT+DOC`

- **ตรวจอะไร:** ตรวจว่าเนื้อหาการตลาดที่ได้รับสัมพันธ์กับพฤติกรรมการเทรดจริงของบัญชีหรือไม่ (เช่น เสนอเลเวอเรจสูงขึ้นหลังใช้เลเวอเรจต่ำมาตลอด หรือเสนอสินค้าเฉพาะหลังเทรดสินค้านั้นบ่อย) ต่างจากข้อ 257 ที่ตรวจการเปิดเผยเชิงนโยบาย ข้อนี้ตรวจ **ความสัมพันธ์เชิงเนื้อหาที่สังเกตได้จริง**
- **ขั้นตอนการตรวจ:**
  1. บันทึกสินค้าและขนาดที่เทรดจริงตลอดรอบตรวจจากรายงานบัญชี (อ้างอิงข้าม `p05-06` ไม่วัดซ้ำ)
  2. บันทึกเนื้อหาโฆษณา/ข้อเสนอที่ได้รับพร้อมวันเวลา
  3. เทียบสินค้าที่ถูกโฆษณาถึงกับสินค้าที่เทรดจริงในช่วงก่อนหน้า
  4. บันทึกจำนวนครั้งที่ตรงกันเทียบกับจำนวนข้อเสนอทั้งหมด
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางเทียบสินค้าที่เทรดกับเนื้อหาโฆษณาตามเวลา (`RST-BRKA-P10-258-01`)
- **ผ่าน:** เนื้อหาการตลาดที่ได้รับไม่สัมพันธ์เจาะจงกับพฤติกรรมการเทรดส่วนตัว หรือสัมพันธ์แต่มีการเปิดเผยและช่องทางคัดค้านตามข้อ 257
- **ไม่ผ่าน:** เนื้อหาสัมพันธ์ชัดเจนกับพฤติกรรมส่วนตัวโดยไม่มีการเปิดเผยหรือช่องทางคัดค้าน
- **ยังไม่ได้ตรวจ:** ได้รับข้อเสนอน้อยกว่า 3 ครั้งตลอดรอบตรวจ ไม่พอสรุปความสัมพันธ์
- **ตัวอย่าง:** หลังเทรดทองคำสามครั้งติดต่อกัน Broker B ส่งอีเมลเสนอลดค่าคอมมิชชันเฉพาะทองคำทันที โดยไม่เคยเปิดเผยเรื่อง profiling → **ไม่ผ่าน**

**P10-259 ● · การใช้ข้อมูลติดต่อส่งโฆษณาช่องทางอื่นนอกเหนือที่ยินยอม** `w3` `ACC+DOC`

- **ตรวจอะไร:** ตรวจว่าโบรกใช้อีเมลหรือเบอร์โทรที่ให้ไว้ตอนสมัคร ส่งการตลาดผ่านช่องทางที่ผู้ตรวจไม่เคยยินยอมหรือไม่ (เช่น ให้อีเมลไว้เพื่อรับใบแจ้งยอด แต่กลับได้ SMS การตลาด) จุดที่ต้องดูคือสถานะยินยอมในตาราง `MKT-CONSENT` เทียบกับข้อความที่ได้รับจริงทุกช่องทาง
- **ขั้นตอนการตรวจ:**
  1. เปิดตาราง `MKT-CONSENT` ดูสถานะยินยอมของแต่ละช่องทาง
  2. รวบรวมข้อความการตลาดทุกชิ้นที่ได้รับตลอดรอบตรวจ แยกตามช่องทาง
  3. ทำเครื่องหมายข้อความที่มาจากช่องทางที่ไม่เคยให้ความยินยอม
  4. บันทึกจำนวนและตัวอย่างข้อความที่ผิดปกติ พร้อมวันเวลา UTC
  5. บันทึกผลลงตาราง `MKT-CONSENT` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความการตลาดทุกช่องทางพร้อมวันเวลา (`RST-BRKA-P10-259-01` ถึง `-05`) · ตารางเทียบยินยอมกับที่ได้รับจริง
- **ผ่าน:** ทุกข้อความการตลาดที่ได้รับมาจากช่องทางที่ยินยอมไว้เท่านั้น
- **ไม่ผ่าน:** พบข้อความการตลาดอย่างน้อย 1 ชิ้นจากช่องทางที่ไม่เคยยินยอม
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** ผู้ตรวจให้เฉพาะอีเมล แต่ Broker A ส่ง SMS การตลาดมาที่เบอร์โทรที่ให้ไว้เพื่อยืนยันตัวตนเท่านั้น → **ไม่ผ่าน**

**P10-260 · คุกกี้และตัวติดตามการตลาดที่ผูกกับบัญชีที่ล็อกอินแล้ว** `w1` `WEB+PLT`

- **ตรวจอะไร:** ตรวจว่าเมื่อล็อกอินเข้าพื้นที่ลูกค้าแล้ว มีตัวติดตามโฆษณาของบุคคลที่สามทำงานอยู่ในหน้าที่มีข้อมูลบัญชีหรือไม่ (ไม่ตรวจซ้ำรายชื่อผู้รับข้อมูลซึ่งเป็นของ `p10-02` แต่ตรวจว่าตัวติดตามนั้นทำงาน **ขณะล็อกอิน** หรือไม่ ซึ่งเสี่ยงส่งข้อมูลบัญชีออกไปโดยไม่ตั้งใจ) ใช้เครื่องมือมาตรฐานของเบราว์เซอร์เท่านั้น
- **ขั้นตอนการตรวจ:**
  1. ล็อกอินเข้าพื้นที่ลูกค้าด้วยบัญชีของตนเอง
  2. เปิดเครื่องมือของเบราว์เซอร์ที่แสดงคำขอเครือข่ายและคุกกี้ (เมนูมาตรฐานที่ผู้ใช้ทั่วไปเปิดได้)
  3. บันทึกรายชื่อโดเมนของตัวติดตามที่พบในหน้าที่แสดงยอดเงินหรือข้อมูลบัญชี
  4. เทียบรายชื่อกับที่นโยบายความเป็นส่วนตัวประกาศไว้ (อ้างอิงข้าม `p10-02` เป็นแหล่งของรายชื่อที่ประกาศ)
  5. บันทึกโดเมนที่พบแต่ไม่ได้ประกาศไว้
  6. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอเครื่องมือเบราว์เซอร์ที่เห็นรายชื่อตัวติดตามขณะล็อกอิน (`RST-BRKA-P10-260-01`)
- **ผ่าน:** ตัวติดตามที่พบขณะล็อกอินทั้งหมดตรงกับรายชื่อที่ประกาศไว้ในนโยบาย
- **ไม่ผ่าน:** พบตัวติดตามโฆษณาที่ไม่ได้ประกาศไว้ทำงานอยู่ในหน้าที่แสดงข้อมูลบัญชี
- **ยังไม่ได้ตรวจ:** เครื่องมือของเบราว์เซอร์ที่ใช้ไม่รองรับการแสดงรายการนี้
- **ตัวอย่าง:** Broker B มีตัวติดตามโฆษณา 3 รายที่ไม่ปรากฏในนโยบายทำงานอยู่ในหน้าแสดงยอดเงินคงเหลือ → **ไม่ผ่าน**

**P10-261 · การแชร์ข้อมูลกับเครือข่ายโฆษณาบุคคลที่สาม** `w2` `WEB+DOC`

- **ตรวจอะไร:** ตรวจว่าโบรกส่งข้อมูลของผู้ตรวจให้เครือข่ายโฆษณาบุคคลที่สามเพื่อทำการตลาดข้ามแพลตฟอร์มหรือไม่ ใช้รายชื่อผู้รับข้อมูลที่บันทึกไว้แล้วจาก `p10-02` เป็นฐาน **ไม่สร้างการค้นหาใหม่** ตรวจเฉพาะว่าในรายชื่อนั้นมีเครือข่ายโฆษณาหรือไม่ และนโยบายอธิบายวัตถุประสงค์การส่งต่อเพื่อการตลาดชัดเจนหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดผลจากไฟล์บันทึกของ `p10-02` ที่มีรายชื่อผู้รับข้อมูล
  2. คัดกรองรายชื่อที่เป็นเครือข่ายโฆษณาหรือแพลตฟอร์มการตลาด
  3. เปิดสำเนานโยบายความเป็นส่วนตัว ค้นข้อความที่อธิบายวัตถุประสงค์การส่งต่อให้เครือข่ายเหล่านี้
  4. บันทึกว่าข้อความอธิบายวัตถุประสงค์ชัดเจนหรือเขียนกว้างว่า "พันธมิตรทางธุรกิจ"
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางคัดกรองเครือข่ายโฆษณาจากรายชื่อ `p10-02` (`RST-BRKA-P10-261-01`) · ภาพข้อความวัตถุประสงค์ในนโยบาย (`-02`)
- **ผ่าน:** นโยบายระบุชื่อหรือประเภทของเครือข่ายโฆษณาที่รับข้อมูลและวัตถุประสงค์ชัดเจน หรือไม่มีการส่งต่อให้เครือข่ายโฆษณาเลย
- **ไม่ผ่าน:** พบเครือข่ายโฆษณาในรายชื่อผู้รับข้อมูลจริง แต่นโยบายไม่ระบุวัตถุประสงค์การส่งต่อเพื่อการตลาด
- **ยังไม่ได้ตรวจ:** ผลจาก `p10-02` ยังไม่พร้อม
- **ตัวอย่าง:** รายชื่อผู้รับข้อมูลของ Broker A มีเครือข่ายโฆษณา 2 ราย แต่นโยบายไม่กล่าวถึงการส่งต่อข้อมูลเพื่อการตลาดเลย → **ไม่ผ่าน**

**P10-262 ● · ผลจริงหลังขอถอนความยินยอมรับการตลาด** `w3` `SUP+DOC`

- **ตรวจอะไร:** ตรวจว่าหลังยื่นคำขอถอนความยินยอมรับการตลาดตามที่ทดสอบไว้แล้วใน `p10-02` (S03) โบรกหยุดส่งการตลาดจริงหรือไม่ ข้อนี้ **ไม่สร้างการทดสอบขอถอนใหม่** แต่ใช้เวลา `V0` ของคำขอนั้นเป็นจุดเริ่ม แล้วเฝ้าดูข้อความที่ได้รับหลังจากนั้นทุกชิ้น
- **ขั้นตอนการตรวจ:**
  1. เปิดบันทึกผลคำขอถอนความยินยอมจาก `p10-02` ดูค่า `V0` และ `V2`
  2. เฝ้าสังเกตข้อความทุกช่องทางที่ได้รับตั้งแต่ `V0` เป็นต้นไป เป็นเวลาอย่างน้อย 14 วันปฏิทิน `[เกณฑ์เสนอ: 14 วัน]`
  3. จัดกลุ่มข้อความที่ได้รับเป็นการตลาดหรือข้อความจำเป็น (อ้างเกณฑ์จากข้อ 266)
  4. บันทึกจำนวนข้อความการตลาดที่ยังได้รับหลัง `V0` พร้อมวันเวลา
  5. บันทึกผลลงตาราง `MKT-CONSENT` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความการตลาดทุกชิ้นที่ได้รับหลัง `V0` (`RST-BRKA-P10-262-01` ถึง `-05`) · ตารางไทม์ไลน์
- **ผ่าน:** ไม่มีข้อความการตลาดใดมาถึงหลัง `V0` ของคำขอถอน (ยกเว้นข้อความจำเป็นตามข้อ 266)
- **ไม่ผ่าน:** มีข้อความการตลาดอย่างน้อย 1 ชิ้นมาถึงหลัง `V0`
- **ยังไม่ได้ตรวจ:** ยังไม่เคยยื่นคำขอถอนความยินยอมตาม `p10-02`
- **ตัวอย่าง:** ผู้ตรวจถอนความยินยอมกับ Broker C เมื่อ `V0` แต่ยังได้รับอีเมลโปรโมชันอีก 3 ฉบับใน 10 วันถัดมา → **ไม่ผ่าน**

**P10-263 · ระยะเวลาที่ใช้จนหยุดส่งจริงหลังขอถอน** `w2` `SUP`

- **ตรวจอะไร:** ตรวจว่าใช้เวลานานเท่าใดนับจาก `V0` ของคำขอถอน จนถึงข้อความการตลาดชิ้นสุดท้ายที่ได้รับ (ถ้ามี) จุดที่ต้องดูคือไทม์ไลน์จากข้อ 262 ตัวแปรที่ต้องบันทึกคือระยะเวลาเป็นวันจาก `V0` ถึงข้อความสุดท้าย
- **ขั้นตอนการตรวจ:**
  1. เปิดไทม์ไลน์จากข้อ 262
  2. หาข้อความการตลาดชิ้นสุดท้ายที่ได้รับหลัง `V0` (ถ้ามี)
  3. คำนวณส่วนต่างวันระหว่าง `V0` กับวันที่ของข้อความชิ้นนั้น
  4. ถ้าไม่มีข้อความการตลาดใดหลัง `V0` เลย ให้บันทึกว่า "หยุดทันที"
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางคำนวณระยะเวลา (`RST-BRKA-P10-263-01`)
- **ผ่าน:** หยุดทันทีหรือภายใน `[เกณฑ์เสนอ: 3 วันทำการ]` นับจาก `V0`
- **ไม่ผ่าน:** เกินระยะเวลาที่กำหนด
- **ยังไม่ได้ตรวจ:** ตามข้อ 262
- **ตัวอย่าง:** Broker A หยุดส่งการตลาดภายใน 1 วันหลัง `V0` → **ผ่าน**

**P10-264 ● · ถอนความยินยอมช่องทางหนึ่งแต่ยังได้รับผ่านช่องทางอื่น** `w3` `SUP+ACC`

- **ตรวจอะไร:** ตรวจว่าเมื่อถอนความยินยอมเฉพาะช่องทางหนึ่ง (เช่น อีเมล) ตามข้อ 254 แล้ว การตลาดผ่านช่องทางอื่นที่ไม่ได้ขอถอน (SMS · push) ยังทำงานตามปกติหรือกลับหยุดไปด้วยทั้งที่ไม่ได้ขอ จุดที่ต้องดูคือสถานะรายช่องทางในตาราง `MKT-CONSENT` เทียบกับที่ได้รับจริง
- **ขั้นตอนการตรวจ:**
  1. ใช้บัญชีที่ปิดเฉพาะช่องทางอีเมลตามข้อ 254
  2. เฝ้าสังเกตข้อความช่องทางอื่นที่ยังเปิดอยู่เป็นเวลา 14 วัน
  3. บันทึกว่าช่องทางอื่นยังได้รับการตลาดตามปกติหรือหยุดไปด้วย
  4. ถ้าช่องทางอื่นหยุดไปด้วยทั้งที่ไม่ได้ขอ ให้บันทึกเป็นความผิดปกติ (การตั้งค่าไม่ทำงานจริง)
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** บันทึกข้อความช่องทางอื่นตลอด 14 วัน (`RST-BRKA-P10-264-01`)
- **ผ่าน:** ช่องทางที่ปิดหยุดจริง และช่องทางอื่นที่ไม่ได้ปิดยังทำงานตามที่ตั้งไว้
- **ไม่ผ่าน:** ช่องทางที่ปิดยังส่งอยู่ หรือช่องทางอื่นที่ไม่ได้ขอปิดกลับถูกปิดไปด้วย (แปลว่าการตั้งค่าไม่ตรงกับที่แสดง)
- **ยังไม่ได้ตรวจ:** ตามข้อ 254
- **ตัวอย่าง:** ผู้ตรวจปิดเฉพาะอีเมลกับ Broker B แต่ยังได้รับ SMS การตลาดตามปกติ และอีเมลก็หยุดจริง → **ผ่าน**

**P10-265 · การติดต่อจากบุคคลที่สามหลังถอนความยินยอมกับโบรกโดยตรง** `w2` `SUP+PUB`

- **ตรวจอะไร:** ตรวจว่าหลังถอนความยินยอมกับโบรกโดยตรง ผู้ตรวจยังได้รับการติดต่อทางการตลาดจากผู้แนะนำหรือบุคคลที่สามที่อ้างว่าเป็นพันธมิตรของโบรกรายนี้หรือไม่ (อ้างอิงข้าม `p08-05` และ `p09-04` สำหรับการวิเคราะห์พฤติกรรมการติดต่อโดยรวม ไม่ตรวจซ้ำ ตรวจเฉพาะมุมว่าการถอนความยินยอมมีผลครอบคลุมถึงบุคคลที่สามด้วยหรือไม่)
- **ขั้นตอนการตรวจ:**
  1. บันทึกวันที่ถอนความยินยอมตามข้อ 262
  2. เฝ้าสังเกตการติดต่อจากบุคคลที่อ้างว่าเป็นตัวแทนหรือผู้แนะนำของโบรกรายนี้เป็นเวลา 14 วันถัดมา
  3. บันทึกช่องทางที่ติดต่อมาและข้อความคำต่อคำ
  4. ตรวจสอบว่านโยบายความเป็นส่วนตัวระบุหรือไม่ว่าการถอนความยินยอมครอบคลุมถึงบุคคลที่สามที่ได้รับข้อมูลไปแล้ว
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** บันทึกการติดต่อจากบุคคลที่สามหลังถอนความยินยอม (`RST-BRKA-P10-265-01`)
- **ผ่าน:** ไม่มีการติดต่อจากบุคคลที่สามหลังถอนความยินยอม หรือนโยบายระบุชัดว่าครอบคลุมถึงบุคคลที่สาม และเป็นจริง
- **ไม่ผ่าน:** ยังมีการติดต่อจากบุคคลที่สามหลังถอนความยินยอมโดยนโยบายไม่ได้ระบุข้อยกเว้นนี้
- **ยังไม่ได้ตรวจ:** โบรกไม่มีโครงการผู้แนะนำหรือพันธมิตรตาม `p09-04`
- **ตัวอย่าง:** ผู้แนะนำของ Broker C ยังส่งข้อความชวนเทรดมาหลังผู้ตรวจถอนความยินยอมกับโบรกโดยตรงแล้ว 5 วัน → **ไม่ผ่าน**

**P10-266 ● · แยกข้อความจำเป็นออกจากข้อความการตลาดชัดเจนหรือไม่** `w2` `SUP`

- **ตรวจอะไร:** ตรวจว่าหลังถอนความยินยอมการตลาดแล้ว ลูกค้ายังคงได้รับข้อความที่จำเป็นต่อการใช้บริการ (ยืนยันธุรกรรม · แจ้งเตือนความปลอดภัย · ใบแจ้งยอด) ตามปกติหรือไม่ และข้อความทั้งสองประเภทแยกแยะได้ชัดจากหัวเรื่องหรือไม่ ข้อนี้ตรวจ **ความถูกต้อง** ของการแยกประเภท ไม่ใช่การหยุดการตลาด (ซึ่งเป็นข้อ 262)
- **ขั้นตอนการตรวจ:**
  1. เปิดกล่องข้อความทั้งหมดที่ได้รับตลอดรอบตรวจ
  2. จัดกลุ่มเป็นข้อความจำเป็นกับข้อความการตลาดตามเนื้อหา
  3. ตรวจว่าหลังถอนความยินยอมตามข้อ 262 ข้อความจำเป็นยังมาถึงตามปกติหรือไม่
  4. ตรวจว่าหัวเรื่องหรือรูปแบบบอกความแตกต่างระหว่างสองประเภทให้ลูกค้าแยกได้เองหรือไม่
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางจัดกลุ่มข้อความทั้งหมด (`RST-BRKA-P10-266-01`)
- **ผ่าน:** ข้อความจำเป็นยังมาถึงตามปกติหลังถอนการตลาด และแยกแยะจากข้อความการตลาดได้ชัดจากหัวเรื่อง
- **ไม่ผ่าน:** ข้อความจำเป็นหยุดไปด้วยหลังถอนการตลาด หรือแยกแยะไม่ออกจากข้อความการตลาดเลย
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker A ส่งใบแจ้งยอดรายเดือนใช้หัวเรื่องเดียวกับอีเมลโปรโมชันจนแยกไม่ออกก่อนเปิดอ่าน → **ไม่ผ่าน**

**P10-267 · ระยะเวลาเก็บข้อมูลเพื่อการตลาดหลังไม่เคลื่อนไหวหรือหลังถอนความยินยอม** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายระบุหรือไม่ว่าข้อมูลที่เคยใช้เพื่อการตลาด (เช่น ประวัติพฤติกรรมที่ใช้ทำโปรไฟล์) จะถูกลบหรือหยุดใช้ภายในกี่วันหลังลูกค้าถอนความยินยอมหรือไม่เคลื่อนไหวนาน จุดที่ต้องดูคือหัวข้อการเก็บรักษาข้อมูลในนโยบาย
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนานโยบายความเป็นส่วนตัว
  2. ค้นหัวข้อระยะเวลาเก็บรักษาข้อมูลเพื่อการตลาดโดยเฉพาะ (แยกจากข้อมูลบัญชีทั่วไป)
  3. บันทึกตัวเลขวันหรือปีที่ระบุ ถ้าไม่มีให้บันทึกว่า "ไม่ระบุ"
  4. เทียบกับระยะเวลาเก็บข้อมูลบัญชีทั่วไปที่ `p10-01` บันทึกไว้ ว่าต่างกันหรือไม่
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความระยะเวลาเก็บรักษาในนโยบาย (`RST-BRKA-P10-267-01`)
- **ผ่าน:** นโยบายระบุระยะเวลาเก็บข้อมูลเพื่อการตลาดเป็นตัวเลขชัดเจน
- **ไม่ผ่าน:** ไม่ระบุระยะเวลาเลย หรือเขียนว่า "เก็บไว้ตราบเท่าที่จำเป็น" โดยไม่ขยายความ
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** นโยบายของ Broker B ไม่มีหัวข้อระยะเวลาเก็บข้อมูลเพื่อการตลาดแยกจากข้อมูลบัญชีเลย → **ไม่ผ่าน**

**P10-268 ● · ใช้ข้อมูลจากบัญชีที่ปิดแล้วเพื่อการตลาดหรือไม่** `w3` `SUP`

- **ตรวจอะไร:** ตรวจว่าหลังบัญชีถูกปิดแล้ว (ต้องรอผลจากหมวด S12 ของไฟล์นี้เอง โดยเฉพาะข้อ 279 เป็นต้นไป) ยังมีการส่งการตลาดถึงผู้ตรวจในฐานะอดีตลูกค้าหรือไม่ ข้อนี้เป็นจุดเชื่อมระหว่าง S11 กับ S12 **ต้องทำหลัง** ทดสอบปิดบัญชีในหมวด S12 แล้วเท่านั้น ไม่สร้างการทดสอบปิดบัญชีซ้ำ
- **ขั้นตอนการตรวจ:**
  1. บันทึกวันเวลาที่บัญชีถูกปิดสำเร็จจากข้อ 279–286
  2. เฝ้าสังเกตข้อความทุกช่องทางที่ได้รับหลังวันปิดบัญชี เป็นเวลาอย่างน้อย 30 วัน
  3. จัดกลุ่มข้อความที่เป็นการตลาดชวนกลับมาเปิดบัญชีใหม่
  4. เทียบกับที่นโยบายระบุไว้ว่าจะหยุดใช้ข้อมูลเพื่อการตลาดเมื่อใดหลังปิดบัญชี
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** บันทึกข้อความหลังปิดบัญชีตลอด 30 วัน (`RST-BRKA-P10-268-01`)
- **ผ่าน:** ไม่มีการตลาดถึงผู้ตรวจหลังปิดบัญชี เว้นแต่นโยบายระบุไว้ล่วงหน้าและได้รับความยินยอมแยกต่างหากสำหรับกรณีนี้
- **ไม่ผ่าน:** ยังได้รับการตลาดหลังปิดบัญชีโดยไม่มีความยินยอมใหม่
- **ยังไม่ได้ตรวจ:** ยังไม่ได้ทดสอบปิดบัญชีตามหมวด S12
- **ตัวอย่าง:** Broker C ยังส่งอีเมลชวนกลับมาเปิดบัญชีทุกสัปดาห์ นาน 3 เดือนหลังปิดบัญชี → **ไม่ผ่าน**

**P10-269 · ระบบอัตโนมัติตัดสินใจเสนอโปรโมชันเฉพาะราย** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายเปิดเผยหรือไม่ว่ามีการใช้ระบบอัตโนมัติ (รวมปัญญาประดิษฐ์) ตัดสินใจเลือกข้อเสนอหรือเนื้อหาการตลาดให้แต่ละบุคคลโดยไม่มีมนุษย์ทบทวน และมีสิทธิขอให้มนุษย์ทบทวนหรือคัดค้านหรือไม่
- **ขั้นตอนการตรวจ:**
  1. ค้นคำว่า `automated decision` `การตัดสินใจอัตโนมัติ` `AI` `ปัญญาประดิษฐ์` ในสำเนานโยบาย
  2. บันทึกข้อความที่พบพร้อมตำแหน่ง
  3. ค้นว่ามีช่องทางขอให้มนุษย์ทบทวนคำตัดสินอัตโนมัตินั้นหรือไม่
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้องในนโยบาย (`RST-BRKA-P10-269-01`)
- **ผ่าน:** นโยบายเปิดเผยการใช้ระบบอัตโนมัติพร้อมช่องทางขอให้มนุษย์ทบทวน หรือไม่มีการใช้ระบบอัตโนมัติลักษณะนี้เลย
- **ไม่ผ่าน:** พบสัญญาณว่ามีระบบอัตโนมัติเลือกข้อเสนอเฉพาะราย (อ้างอิงจากข้อ 257–258) แต่นโยบายไม่เปิดเผยและไม่มีช่องทางขอทบทวน
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker A ไม่กล่าวถึงระบบอัตโนมัติใดในนโยบาย และไม่พบสัญญาณการทำโปรไฟล์ตามข้อ 257–258 → **ผ่าน**

**P10-270 ● · ข้อความการตลาดที่ปลอมเป็นข้อความแจ้งเตือนบัญชี** `w3` `SUP`

- **ตรวจอะไร:** ตรวจว่าโบรกใช้หัวเรื่องหรือรูปแบบที่เลียนแบบข้อความแจ้งเตือนด้านความปลอดภัยหรือการเงิน (เช่น *"แจ้งเตือน: บัญชีของท่าน..."*) เพื่อหลอกให้เปิดอ่านข้อความที่แท้จริงเป็นโฆษณาหรือไม่ จุดที่ต้องดูคือหัวเรื่องเทียบกับเนื้อหาจริงของทุกข้อความที่ได้รับ
- **ขั้นตอนการตรวจ:**
  1. รวบรวมหัวเรื่องข้อความทั้งหมดที่ได้รับตลอดรอบตรวจ
  2. เปิดอ่านเนื้อหาจริงของแต่ละข้อความ
  3. ทำเครื่องหมายข้อความที่หัวเรื่องสื่อถึงความปลอดภัยหรือธุรกรรมสำคัญ แต่เนื้อหาจริงเป็นโฆษณา
  4. บันทึกจำนวนและตัวอย่างที่พบ
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหัวเรื่องคู่กับเนื้อหาจริงของข้อความที่ทำเครื่องหมาย (`RST-BRKA-P10-270-01` ถึง `-03`)
- **ผ่าน:** หัวเรื่องทุกข้อความสื่อถึงเนื้อหาจริงตรงกัน ไม่มีข้อความที่ใช้หัวเรื่องด้านความปลอดภัยบังหน้าโฆษณา
- **ไม่ผ่าน:** พบข้อความอย่างน้อย 1 ชิ้นที่หัวเรื่องหลอกว่าเป็นเรื่องความปลอดภัยแต่เนื้อหาเป็นโฆษณา
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker B ส่งอีเมลหัวเรื่อง *"แจ้งเตือนความปลอดภัยบัญชีของท่าน"* แต่เนื้อหาเป็นโปรโมชันฝากเงินเพิ่ม → **ไม่ผ่าน**

**P10-271 · ความถี่การตลาดสูงสุดที่ประกาศเทียบกับที่ได้รับจริง** `w1` `DOC+SUP`

- **ตรวจอะไร:** ตรวจว่านโยบายหรือหน้าตั้งค่าระบุความถี่สูงสุดของข้อความการตลาด (เช่น ไม่เกินกี่ฉบับต่อสัปดาห์) หรือไม่ และเทียบกับจำนวนที่ได้รับจริงตลอดรอบตรวจ (ต่างจากข้อ 271 ในเสา P08 ซึ่งวัดการติดต่อรายบุคคลทั้งหมดรวมทุกประเภท — ข้อนี้นับเฉพาะข้อความการตลาดที่เข้าเกณฑ์ตามข้อ 266)
- **ขั้นตอนการตรวจ:**
  1. ค้นหาตัวเลขความถี่สูงสุดที่ประกาศไว้ในนโยบายหรือหน้าตั้งค่า
  2. นับจำนวนข้อความการตลาดจริงที่ได้รับต่อสัปดาห์ตลอดรอบตรวจ จากตารางที่จัดกลุ่มไว้ในข้อ 266
  3. เทียบจำนวนจริงกับเพดานที่ประกาศไว้รายสัปดาห์
  4. บันทึกสัปดาห์ที่เกินเพดาน (ถ้ามี)
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางนับความถี่รายสัปดาห์เทียบเพดาน (`RST-BRKA-P10-271-01`)
- **ผ่าน:** จำนวนข้อความการตลาดจริงไม่เกินเพดานที่ประกาศไว้ทุกสัปดาห์ หรือไม่มีการประกาศเพดานแต่ความถี่จริงอยู่ในระดับที่สมเหตุสมผล
- **ไม่ผ่าน:** มีสัปดาห์ใดที่จำนวนจริงเกินเพดานที่ประกาศไว้
- **ยังไม่ได้ตรวจ:** ไม่มีการประกาศเพดานและได้รับข้อความน้อยกว่า 2 สัปดาห์ตลอดรอบตรวจ
- **ตัวอย่าง:** Broker A ประกาศว่าส่งไม่เกิน 2 ฉบับต่อสัปดาห์ แต่ผู้ตรวจได้รับ 5 ฉบับในสัปดาห์หนึ่ง → **ไม่ผ่าน**

**P10-272 ● · การส่งต่อฐานข้อมูลลูกค้าเพื่อการตลาดเมื่อมีการควบรวมกิจการ** `w2` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายระบุหรือไม่ว่าหากเกิดการควบรวมกิจการ ขายกิจการ หรือโอนธุรกิจ ข้อมูลของลูกค้ารวมถึงข้อมูลที่ใช้เพื่อการตลาดจะถูกโอนไปพร้อมกิจการหรือไม่ และลูกค้ามีสิทธิคัดค้านหรือไม่
- **ขั้นตอนการตรวจ:**
  1. ค้นคำว่า `merger` `acquisition` `transfer of business` `ควบรวม` `โอนกิจการ` ในสำเนานโยบาย
  2. บันทึกข้อความที่พบพร้อมตำแหน่ง
  3. ตรวจว่าระบุสิทธิคัดค้านหรือขอลบข้อมูลก่อนการโอนหรือไม่
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้องในนโยบาย (`RST-BRKA-P10-272-01`)
- **ผ่าน:** นโยบายระบุเงื่อนไขการโอนข้อมูลกรณีควบรวมกิจการ พร้อมช่องทางแจ้งลูกค้าและสิทธิคัดค้าน
- **ไม่ผ่าน:** ไม่มีข้อความใดกล่าวถึงกรณีนี้เลย
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** นโยบายของ Broker C ไม่มีหัวข้อใดกล่าวถึงกรณีควบรวมหรือโอนกิจการเลย → **ไม่ผ่าน**

**P10-273 · ช่องทางแจ้งความไม่พอใจเรื่องการตลาดที่รบกวน** `w1` `WEB+ACC`

- **ตรวจอะไร:** ตรวจว่ามีช่องทางเฉพาะให้ลูกค้าแจ้งความไม่พอใจเรื่องการตลาดที่มากเกินไปหรือรบกวน แยกจากช่องทางร้องเรียนทั่วไปหรือไม่ และหาเจอง่ายเพียงใดจากหน้าตั้งค่าความเป็นส่วนตัว
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าตั้งค่าความเป็นส่วนตัวและการแจ้งเตือน
  2. ค้นหาช่องทางหรือปุ่มที่เกี่ยวข้องกับการแจ้งปัญหาเรื่องการตลาด
  3. บันทึกจำนวนคลิกที่ต้องใช้เพื่อเข้าถึงช่องทางนี้จากหน้าตั้งค่า
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพเส้นทางคลิกไปยังช่องทางแจ้งปัญหา (`RST-BRKA-P10-273-01`)
- **ผ่าน:** มีช่องทางเฉพาะที่หาเจอได้ภายใน `[เกณฑ์เสนอ: 2 คลิก]` จากหน้าตั้งค่า
- **ไม่ผ่าน:** ไม่มีช่องทางเฉพาะ ต้องใช้ช่องทางร้องเรียนทั่วไปปนกับเรื่องอื่น
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker B ไม่มีปุ่มแจ้งปัญหาเรื่องการตลาดแยก ต้องส่งอีเมลไปช่องทางร้องเรียนทั่วไปเท่านั้น → **ไม่ผ่าน**

**P10-274 · ผลกระทบของการถอนความยินยอมต่อสิทธิประโยชน์อื่น** `w2` `SUP+DOC`

- **ตรวจอะไร:** ตรวจว่าการถอนความยินยอมรับการตลาดส่งผลให้ลูกค้าเสียสิทธิประโยชน์อื่นที่ไม่เกี่ยวข้องกันหรือไม่ (เช่น เสียสิทธิรับโบนัส ส่วนลดค่าคอมมิชชัน หรือถูกลดระดับบัญชี VIP) จุดที่ต้องดูคือสถานะบัญชีก่อนและหลังถอนความยินยอมตามข้อ 262
- **ขั้นตอนการตรวจ:**
  1. บันทึกสถานะสิทธิประโยชน์ของบัญชีก่อนถอนความยินยอม (ระดับบัญชี · ส่วนลดที่มีอยู่ · โบนัสที่รอปลดล็อก)
  2. ถอนความยินยอมตามข้อ 262
  3. ตรวจสอบสถานะสิทธิประโยชน์เดิมอีกครั้งหลังผ่านไป 7 วัน
  4. บันทึกสิทธิประโยชน์ใดที่หายไปหรือเปลี่ยนแปลง
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพสถานะสิทธิประโยชน์ก่อนและหลัง (`RST-BRKA-P10-274-01`, `-02`)
- **ผ่าน:** สิทธิประโยชน์ที่มีอยู่แล้วก่อนถอนความยินยอมไม่เปลี่ยนแปลง
- **ไม่ผ่าน:** สิทธิประโยชน์ที่มีอยู่แล้วหายไปหรือลดลงหลังถอนความยินยอมโดยไม่มีเหตุอื่นอธิบาย
- **ยังไม่ได้ตรวจ:** บัญชีไม่มีสิทธิประโยชน์ใดอยู่ก่อนถอนความยินยอม
- **ตัวอย่าง:** ผู้ตรวจถูกลดระดับบัญชีจาก VIP กลับเป็นมาตรฐานทันทีหลังถอนความยินยอมรับการตลาดกับ Broker A → **ไม่ผ่าน**

**P10-275 · ข้อสรุปปิดหมวด S11 — ดัชนีความยินยอมเพื่อการตลาด** `w2` `DOC+SUP`

- **ตรวจอะไร:** หมวดนี้ **ห้ามสร้างการทดสอบใหม่** ให้รวมผลจากข้อ 251–274 มาตัดสินผ่าน/ไม่ผ่านรวมหมวดเดียว ว่าโบรกรายนี้จัดการความยินยอมด้านการตลาดเป็นไปตามหลักที่ควรหรือไม่ ตัวแปรที่ต้องบันทึกคือจำนวนข้อที่ผ่าน · ไม่ผ่าน · ยังไม่ได้ตรวจ ในหมวด S11 ทั้งหมด
- **ขั้นตอนการตรวจ:**
  1. เปิดผลของทุกข้อในหมวด S11 (251–274)
  2. นับจำนวนข้อที่ผ่าน ไม่ผ่าน และยังไม่ได้ตรวจ แยกตามน้ำหนัก `w1`/`w2`/`w3` (เพื่อรายงานเท่านั้น ไม่ใช่เพื่อคำนวณคะแนน)
  3. ยืนยันว่าจำนวนข้อที่ผ่าน เท่ากับจำนวนข้อทั้งหมดในช่วง 251–274 (24 ข้อ) และไม่มีข้อใดยังไม่ได้ตรวจ
  4. ทำเครื่องหมายข้อที่เป็น `w3` เป็นรายการอ้างอิงสำหรับรายงานเท่านั้น ไม่มีผลต่างจากข้ออื่นในการตัดสินผ่าน/ไม่ผ่าน
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางสรุปผลทั้งหมวด (`RST-BRKA-P10-275-01`)
- **ผ่าน:** ทุกข้อในช่วง 251 ถึง 274 ตรวจแล้วครบและผ่านทุกข้อ ไม่มีข้อยกเว้นแม้แต่ข้อเดียว
- **ไม่ผ่าน:** มีข้ออย่างน้อย 1 ข้อในช่วง 251 ถึง 274 ที่ตัดสินเป็น "ไม่ผ่าน"
- **ยังไม่ได้ตรวจ:** ยังมีข้ออย่างน้อย 1 ข้อในช่วง 251 ถึง 274 ที่ยังไม่ได้ตรวจ (ไม่มีสิทธิ์สรุปผลจนกว่าจะครบ)
- **ตัวอย่าง:** Broker A ตรวจครบทั้ง 24 ข้อในหมวด S11 และผ่านทุกข้อ รวมถึงข้อ `w3` ทุกข้อ → **ผ่าน**

## S12 · การลบบัญชีและข้อมูลหลังปิดบัญชี (276–300)

**P10-276 · การตั้งทะเบียนติดตามข้อมูลหลังปิดบัญชี `POST-CLOSE`** `w2` `DOC+ACC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจตั้งตารางบันทึกเฉพาะไฟล์นี้ชื่อ `POST-CLOSE` ก่อนเริ่มทดสอบขอลบข้อมูลในหมวดนี้หรือไม่ ตารางต้องมีอย่างน้อย 6 ช่อง: รายการข้อมูลอ้างอิงตามรหัส `PII-SET` · สถานะก่อนขอลบ (มี/ไม่มี) · สถานะหลังขอลบ · วันเวลาที่ตรวจซ้ำ (UTC) · Evidence ID · หมายเหตุ ตารางนี้เป็นเครื่องมือทำงานเฉพาะไฟล์ ไม่ใช่นิยามกลาง
- **ขั้นตอนการตรวจ:**
  1. เปิดไฟล์ตารางใหม่ตั้งชื่อ `POST-CLOSE` สำหรับโบรกรายนี้
  2. วางหัวตาราง 6 ช่อง แล้วเติมแถวตั้งต้นตามรหัส `PII-01` ถึง `PII-15` จากนิยามกลาง
  3. บันทึกสถานะข้อมูลแต่ละรายการที่มองเห็นได้ในพื้นที่ลูกค้าก่อนปิดบัญชี
  4. บันทึกวันเวลา UTC ที่สร้างตาราง
  5. บันทึกไฟล์เป็นฉบับตั้งต้นที่แก้ไม่ได้ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ไฟล์ตาราง `POST-CLOSE` ฉบับตั้งต้น (`RST-BRKA-P10-276-01`)
- **ผ่าน:** มีไฟล์ตารางครบ 6 ช่อง เติมสถานะก่อนปิดบัญชีครบ 15 รายการ
- **ไม่ผ่าน:** ไม่มีไฟล์ตาราง หรือขาดช่องใดช่องหนึ่ง
- **ยังไม่ได้ตรวจ:** ยังไม่ได้เริ่มขั้นตอนปิดบัญชีกับโบรกรายนี้
- **ตัวอย่าง:** ผู้ตรวจ Broker A สร้างตารางครบ 6 ช่องและเติมสถานะก่อนปิดบัญชีครบ 15 รายการก่อนยื่นคำขอปิดบัญชี → **ผ่าน**

**P10-277 ● · นโยบายระบุระยะเวลาเก็บข้อมูลหลังปิดบัญชีเป็นตัวเลขหรือไม่** `w3` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายความเป็นส่วนตัวระบุระยะเวลาที่จะเก็บข้อมูลของลูกค้าไว้หลังปิดบัญชีเป็นตัวเลขที่ชัดเจน (เช่น 5 ปี) หรือเขียนกว้างว่า "ตามที่กฎหมายกำหนด" โดยไม่บอกจำนวนปี จุดที่ต้องดูคือหัวข้อระยะเวลาเก็บรักษาข้อมูลในสำเนานโยบายที่เก็บไว้แล้ว
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนานโยบายความเป็นส่วนตัวจาก `p10-01`
  2. ค้นหัวข้อระยะเวลาเก็บรักษาข้อมูลหลังสิ้นสุดความสัมพันธ์กับลูกค้า
  3. บันทึกตัวเลขปีหรือวันที่ระบุ ถ้าไม่มีตัวเลขให้บันทึกข้อความที่ใช้แทน
  4. ค้นว่ามีการแยกระยะเวลาตามประเภทข้อมูลหรือไม่ (เช่น ข้อมูลธุรกรรมเก็บนานกว่าข้อมูลการตลาด)
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความระยะเวลาเก็บรักษาในนโยบาย (`RST-BRKA-P10-277-01`)
- **ผ่าน:** นโยบายระบุระยะเวลาเก็บข้อมูลหลังปิดบัญชีเป็นตัวเลขชัดเจน
- **ไม่ผ่าน:** ไม่ระบุตัวเลขใด เขียนเพียงว่า "ตามที่กฎหมายกำหนด" หรือ "เท่าที่จำเป็น" โดยไม่ขยายความ
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตาม `p10-01`
- **ตัวอย่าง:** นโยบายของ Broker B เขียนว่า *"เราเก็บข้อมูลของท่านตราบเท่าที่จำเป็นตามกฎหมาย"* โดยไม่ระบุจำนวนปีใด → **ไม่ผ่าน**

**P10-278 · เหตุผลทางกฎหมายที่อ้างสำหรับการเก็บข้อมูลต่อระบุชัดหรือไม่** `w2` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายระบุเหตุผลทางกฎหมายที่ใช้อ้างเก็บข้อมูลต่อหลังปิดบัญชี (เช่น กฎหมายป้องกันการฟอกเงิน กฎหมายภาษี) เป็นกฎหมายเฉพาะเจาะจงหรือเขียนกว้างว่า "ตามกฎหมายที่เกี่ยวข้อง"
- **ขั้นตอนการตรวจ:**
  1. เปิดหัวข้อระยะเวลาเก็บรักษาข้อมูลจากข้อ 277
  2. บันทึกชื่อกฎหมายหรือประเภทข้อบังคับที่ถูกอ้างถึง
  3. ค้นชื่อกฎหมายนั้นในแหล่งสาธารณะเพื่อยืนยันว่ามีอยู่จริงและเกี่ยวข้องกับธุรกิจโบรกจริง
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความอ้างกฎหมายในนโยบาย (`RST-BRKA-P10-278-01`) · ภาพยืนยันการมีอยู่ของกฎหมายนั้นจากแหล่งสาธารณะ
- **ผ่าน:** ระบุชื่อกฎหมายหรือประเภทข้อบังคับเฉพาะเจาะจงที่ตรวจสอบได้ว่าเกี่ยวข้องจริง
- **ไม่ผ่าน:** เขียนกว้างว่า "ตามกฎหมายที่เกี่ยวข้อง" โดยไม่ระบุชื่อใด
- **ยังไม่ได้ตรวจ:** ตามข้อ 277
- **ตัวอย่าง:** นโยบายของ Broker C ระบุว่าเก็บข้อมูลธุรกรรมตามกฎหมายป้องกันและปราบปรามการฟอกเงินเป็นเวลา 5 ปี → **ผ่าน**

**P10-279 ● · ขอให้ลบข้อมูลทันทีหลังปิดบัญชีได้หรือไม่** `w3` `SUP+ACC`

- **ตรวจอะไร:** ตรวจว่าหลังปิดบัญชีสำเร็จ (อ้างอิงกระบวนการปิดบัญชีจาก `p03-06` ไม่ทดสอบซ้ำ) ผู้ตรวจยื่นคำขอให้ลบข้อมูลส่วนบุคคลทันที ระบบรับคำขอและตอบสนองอย่างไร จุดที่ต้องดูคือช่องทางยื่นคำขอและการตอบกลับ ใช้นิยามเวลา `V0`–`V2` จากนิยามกลาง
- **ขั้นตอนการตรวจ:**
  1. หลังปิดบัญชีสำเร็จ ยื่นคำขอลบข้อมูลผ่านช่องทางที่นโยบายระบุ บันทึก `V0`
  2. เก็บภาพหน้าจอหรือสำเนาอีเมลคำขอ
  3. บันทึก `V1` เมื่อได้รับการตอบรับครั้งแรก
  4. บันทึก `V2` เมื่อได้รับผลลัพธ์ (ลบแล้ว/ปฏิเสธพร้อมเหตุผล/ลบบางส่วน)
  5. บันทึกผลลงตาราง `POST-CLOSE` แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** สำเนาคำขอลบข้อมูล (`RST-BRKA-P10-279-01-RED`) · การตอบกลับทุกขั้น (`-02` ถึง `-04`)
- **ผ่าน:** ระบบรับคำขอได้จริงและตอบกลับภายในเวลาที่นโยบายกำหนด พร้อมผลลัพธ์ชัดเจน
- **ไม่ผ่าน:** ไม่มีช่องทางรับคำขอลบข้อมูล หรือไม่ตอบกลับภายในเวลาที่นโยบายกำหนด
- **ยังไม่ได้ตรวจ:** ยังไม่ได้ปิดบัญชีตาม `p03-06`
- **ตัวอย่าง:** ผู้ตรวจยื่นคำขอลบข้อมูลกับ Broker A หลังปิดบัญชี ได้รับการตอบรับใน 2 วันและผลลัพธ์ใน 20 วัน ตรงตามที่นโยบายระบุ → **ผ่าน**

**P10-280 · โบรกปฏิเสธคำขอลบและเหตุผลตรงกับที่ประกาศไว้หรือไม่** `w2` `SUP+DOC`

- **ตรวจอะไร:** ถ้าคำขอลบข้อมูลตามข้อ 279 ถูกปฏิเสธหรือลบเพียงบางส่วน ตรวจว่าเหตุผลที่โบรกให้ตรงกับข้อยกเว้นที่ประกาศไว้ในนโยบายตามข้อ 278 หรือไม่ หรือเป็นเหตุผลใหม่ที่ไม่เคยประกาศไว้
- **ขั้นตอนการตรวจ:**
  1. เปิดผลลัพธ์ `V2` จากข้อ 279
  2. ถ้าเป็นการปฏิเสธหรือลบบางส่วน บันทึกเหตุผลที่โบรกให้คำต่อคำ
  3. เทียบเหตุผลนั้นกับข้อยกเว้นที่นโยบายระบุไว้จากข้อ 278
  4. บันทึกว่าตรงกันหรือเป็นเหตุผลใหม่
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ข้อความปฏิเสธคำต่อคำ (`RST-BRKA-P10-280-01-RED`) · ตารางเทียบกับข้อยกเว้นที่ประกาศ
- **ผ่าน:** ลบข้อมูลได้ครบตามคำขอ หรือปฏิเสธด้วยเหตุผลที่ตรงกับข้อยกเว้นซึ่งประกาศไว้ล่วงหน้าแล้ว
- **ไม่ผ่าน:** ปฏิเสธด้วยเหตุผลที่ไม่เคยประกาศไว้ในนโยบายเลย
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** Broker B ปฏิเสธการลบเลขบัญชีธนาคารโดยอ้างเหตุผลใหม่ที่ไม่เคยปรากฏในนโยบายเลย → **ไม่ผ่าน**

**P10-281 ● · ข้อมูลใดถูกลบจริงและข้อมูลใดยังคงอยู่หลังคำขอ** `w3` `SUP+ACC`

- **ตรวจอะไร:** ตรวจว่าหลังคำขอลบข้อมูลตามข้อ 279 ข้อมูลแต่ละรายการใน `PII-SET` ยังปรากฏให้เห็นในช่องทางใดของโบรกหรือไม่ (พื้นที่ลูกค้าเดิม หากยังเข้าได้ · อีเมลยืนยันเก่า · ใบแจ้งยอดเก่า) จุดที่ต้องดูคือทุกรายการในตาราง `POST-CLOSE` เทียบสถานะก่อนกับหลัง
- **ขั้นตอนการตรวจ:**
  1. หลังได้รับผลลัพธ์ `V2` จากข้อ 279 รอ 7 วันแล้วพยายามล็อกอินเข้าพื้นที่ลูกค้าเดิม (ถ้าระบบยังอนุญาต)
  2. บันทึกว่าข้อมูลรายการใดยังปรากฏให้เห็น
  3. เทียบรายการที่ยังเห็นกับสิ่งที่โบรกยืนยันว่าลบแล้วในข้อ 279
  4. บันทึกความไม่สอดคล้องทุกจุดลงตาราง `POST-CLOSE`
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตาราง `POST-CLOSE` ที่กรอกครบ 15 รายการหลังคำขอ (`RST-BRKA-P10-281-01`) · ภาพหน้าจอที่พบข้อมูลยังคงอยู่ (ถ้ามี)
- **ผ่าน:** ทุกรายการที่โบรกยืนยันว่าลบแล้วไม่ปรากฏให้เห็นอีกในทุกช่องทางที่ตรวจได้
- **ไม่ผ่าน:** มีข้อมูลอย่างน้อย 1 รายการที่โบรกยืนยันว่าลบแล้ว แต่ยังพบเห็นได้จริง
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** Broker C ยืนยันว่าลบเอกสารแสดงตนแล้ว แต่ผู้ตรวจยังพบไฟล์แนบเดิมในอีเมลยืนยันการสมัครเก่าที่ยังเปิดได้ผ่านลิงก์เดิม → **ไม่ผ่าน**

**P10-282 · การเข้าถึงประวัติบัญชีที่ปิดแล้ว** `w1` `PLT+ACC`

- **ตรวจอะไร:** ตรวจว่าบัญชีที่ปิดแล้วยังเข้าดูประวัติการเทรดหรือรายงานเก่าได้หรือไม่ ในมุมความเป็นส่วนตัวว่าการเข้าถึงยังปลอดภัยอยู่หรือไม่ (ไม่ตรวจฟังก์ชันส่งออกข้อมูลซึ่งเป็นของ `p06-03`) จุดที่ต้องดูคือผลของการพยายามล็อกอินหลังปิดบัญชี
- **ขั้นตอนการตรวจ:**
  1. พยายามล็อกอินด้วยข้อมูลเดิมหลังบัญชีปิดสำเร็จ
  2. บันทึกว่าล็อกอินได้หรือไม่ และถ้าได้ เห็นข้อมูลใดบ้าง
  3. ถ้าล็อกอินได้ ตรวจว่าการยืนยันตัวตนยังทำงานตามปกติหรือหย่อนลง (เช่น ไม่ต้องใช้สองชั้นอีกต่อไป)
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพผลการพยายามล็อกอินหลังปิดบัญชี (`RST-BRKA-P10-282-01`)
- **ผ่าน:** ล็อกอินไม่ได้อีกหลังปิดบัญชี หรือถ้าล็อกอินได้ยังคงบังคับยืนยันตัวตนระดับเดิม
- **ไม่ผ่าน:** ล็อกอินได้ตามปกติราวกับบัญชียังเปิดอยู่ โดยการยืนยันตัวตนหย่อนลง
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** บัญชีที่ปิดแล้วของ Broker A ยังล็อกอินได้ปกติและเห็นข้อมูลครบทุกอย่างเหมือนก่อนปิด → **ไม่ผ่าน**

**P10-283 ● · ข้อมูลจากบัญชีปิดแล้วถูกใช้เพื่อการตลาดหรือไม่** `w3` `SUP`

- **ตรวจอะไร:** ข้อนี้ **อ้างผลจากข้อ 268 ในไฟล์นี้เอง ไม่ตรวจซ้ำ** ให้ดึงผลการเฝ้าสังเกต 30 วันหลังปิดบัญชีมาบันทึกในหมวด S12 เพื่อให้ดัชนีปิดหมวดของหมวดนี้ครบถ้วน
- **ขั้นตอนการตรวจ:**
  1. เปิดผลจากข้อ 268
  2. คัดลอกผลสรุปมาบันทึกในตาราง `POST-CLOSE`
  3. ตรวจว่าผลนั้นสอดคล้องกับสิ่งที่นโยบายประกาศไว้ในข้อ 277–278 หรือไม่
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** สำเนาผลจากข้อ 268 ที่คัดลอกมา (`RST-BRKA-P10-283-01`)
- **ผ่าน:** ผลจากข้อ 268 คือ "ผ่าน"
- **ไม่ผ่าน:** ผลจากข้อ 268 คือ "ไม่ผ่าน"
- **ยังไม่ได้ตรวจ:** ผลจากข้อ 268 คือ "ยังไม่ได้ตรวจ"
- **ตัวอย่าง:** ผลจากข้อ 268 คือไม่ผ่าน จึงบันทึกข้อนี้เป็นไม่ผ่านตามกัน → **ไม่ผ่าน**

**P10-284 · การเปิดบัญชีใหม่หลังปิด — ใช้ข้อมูลเดิมหรือต้องส่งใหม่ทั้งหมด** `w1` `ACC`

- **ตรวจอะไร:** ตรวจว่าถ้าเปิดบัญชีใหม่กับโบรกรายเดิมหลังปิดบัญชีไปแล้ว ระบบใช้ข้อมูลและเอกสารเดิมที่เคยลบไปหรือต้องส่งเอกสารยืนยันตัวตนใหม่ทั้งหมด (การใช้ข้อมูลเดิมทั้งที่ยืนยันว่าลบแล้วเป็นสัญญาณว่าการลบไม่จริง)
- **ขั้นตอนการตรวจ:**
  1. หลังผ่านกระบวนการลบข้อมูลตามข้อ 279–281 อย่างน้อย 30 วัน สมัครเปิดบัญชีใหม่ด้วยข้อมูลเดิม
  2. บันทึกว่าระบบขอเอกสารยืนยันตัวตนใหม่ทั้งหมดหรือดึงข้อมูลเก่ามาเติมอัตโนมัติ
  3. ถ้าดึงข้อมูลเก่ามาเติมอัตโนมัติ ให้ถือเป็นหลักฐานว่าข้อมูลเดิมยังไม่ถูกลบจริง
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพขั้นตอนสมัครใหม่ (`RST-BRKA-P10-284-01`)
- **ผ่าน:** ระบบขอเอกสารและข้อมูลยืนยันตัวตนใหม่ทั้งหมดเหมือนลูกค้าใหม่
- **ไม่ผ่าน:** ระบบดึงข้อมูลหรือเอกสารเดิมที่เคยยืนยันว่าลบแล้วมาเติมให้อัตโนมัติ
- **ยังไม่ได้ตรวจ:** สถาบันยังไม่อนุญาตให้เปิดบัญชีซ้ำกับโบรกรายเดิมตามระเบียบผู้ตรวจภาคสนาม
- **ตัวอย่าง:** Broker B แสดงชื่อและเลขบัตรประชาชนเดิมของผู้ตรวจโดยอัตโนมัติตอนสมัครใหม่ ทั้งที่เคยยืนยันว่าลบข้อมูลนี้แล้ว → **ไม่ผ่าน**

**P10-285 ● · แจ้งยืนยันเมื่อข้อมูลถูกลบจริงหรือไม่** `w2` `SUP`

- **ตรวจอะไร:** ตรวจว่าเมื่อการลบข้อมูลเสร็จสิ้น (`V2` จากข้อ 279) โบรกส่งข้อความยืนยันให้ผู้ตรวจทราบอย่างชัดเจนหรือไม่ ระบุรายการที่ลบและรายการที่ยังต้องเก็บไว้ตามกฎหมายหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดข้อความยืนยันผลลัพธ์จาก `V2` ในข้อ 279
  2. ตรวจว่าข้อความระบุรายการที่ลบสำเร็จเป็นรายการหรือเขียนกว้างว่า "ดำเนินการเรียบร้อยแล้ว"
  3. ตรวจว่าระบุรายการที่ยังต้องเก็บไว้พร้อมเหตุผลหรือไม่
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ข้อความยืนยันคำต่อคำ (`RST-BRKA-P10-285-01-RED`)
- **ผ่าน:** ข้อความยืนยันระบุรายการที่ลบและรายการที่ยังเก็บไว้พร้อมเหตุผลอย่างชัดเจน
- **ไม่ผ่าน:** ได้รับเพียงข้อความกว้าง ๆ ว่า "ดำเนินการเรียบร้อยแล้ว" โดยไม่ระบุรายการ
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** Broker A ส่งรายการแจกแจงชัดเจนว่าลบชิ้นใดบ้างและเก็บชิ้นใดไว้กี่ปีเพราะเหตุผลใด → **ผ่าน**

**P10-286 · ระยะเวลาจริงที่ใช้จนข้อมูลถูกลบ** `w2` `SUP`

- **ตรวจอะไร:** ตรวจว่าระยะเวลาจาก `V0` ถึง `V2` ของคำขอลบข้อมูลตามข้อ 279 ตรงกับที่นโยบายประกาศไว้หรือไม่ และเทียบกับเกณฑ์กลางของเสา
- **ขั้นตอนการตรวจ:**
  1. เปิด `V0` และ `V2` จากข้อ 279
  2. คำนวณ `V2 − V0` เป็นวัน
  3. เทียบกับระยะเวลาที่นโยบายประกาศไว้
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางคำนวณระยะเวลา (`RST-BRKA-P10-286-01`)
- **ผ่าน:** ระยะเวลาจริงไม่เกินที่ประกาศไว้ หรือไม่เกิน `[เกณฑ์เสนอ: 30 วัน]` หากไม่มีการประกาศ
- **ไม่ผ่าน:** เกินระยะเวลาที่ประกาศไว้หรือเกินเกณฑ์เสนอ
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** Broker C ใช้เวลา 45 วันจนข้อมูลถูกลบ ทั้งที่ประกาศไว้ว่าไม่เกิน 30 วัน → **ไม่ผ่าน**

**P10-287 · นโยบายลบข้อมูลกรณีโบรกปิดบัญชีเองต่างจากกรณีลูกค้าขอปิดหรือไม่** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายแยกกรณีบัญชีถูกโบรกปิดเอง (ไม่ใช่ลูกค้าร้องขอ) ออกจากกรณีลูกค้าขอปิดบัญชีเอง ในแง่ระยะเวลาเก็บข้อมูลและสิทธิขอลบหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนานโยบาย ค้นหัวข้อที่แยกสองกรณีนี้
  2. บันทึกความแตกต่างที่พบ (ถ้ามี)
  3. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้อง (`RST-BRKA-P10-287-01`)
- **ผ่าน:** นโยบายระบุชัดว่าสิทธิขอลบข้อมูลของลูกค้าเหมือนกันไม่ว่าใครเป็นผู้ปิดบัญชี
- **ไม่ผ่าน:** นโยบายจำกัดสิทธิขอลบข้อมูลเฉพาะกรณีลูกค้าขอปิดเองเท่านั้น โดยไม่ให้สิทธิเมื่อโบรกเป็นผู้ปิด
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** นโยบายของ Broker A ไม่แยกสองกรณีนี้ ลูกค้ามีสิทธิขอลบข้อมูลเหมือนกันทุกกรณี → **ผ่าน**

**P10-288 · การลบข้อมูลในระบบสำรองพร้อมระบบหลักหรือไม่** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายกล่าวถึงข้อมูลสำรอง (backup) หรือไม่ว่าจะถูกลบตามรอบเดียวกับระบบหลักหรือคงอยู่นานกว่า **ข้อนี้ตรวจได้จำกัดจากภายนอก** ผู้ตรวจไม่มีทางพิสูจน์การลบจริงในระบบสำรองได้ ให้ตัดสินจากคำประกาศเท่านั้น
- **ขั้นตอนการตรวจ:**
  1. ค้นคำว่า `backup` `ข้อมูลสำรอง` ในสำเนานโยบาย
  2. บันทึกข้อความที่พบ
  3. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้อง (`RST-BRKA-P10-288-01`)
- **ผ่าน:** นโยบายระบุว่าข้อมูลในระบบสำรองจะถูกลบภายในระยะเวลาที่กำหนดหลังการลบในระบบหลัก
- **ไม่ผ่าน:** ไม่กล่าวถึงระบบสำรองเลย
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** นโยบายของ Broker B ระบุว่าระบบสำรองจะลบข้อมูลตามภายใน 90 วันหลังลบในระบบหลัก → **ผ่าน**

**P10-289 ● · นโยบายลบข้อมูลตรงกับที่หน่วยงานคุ้มครองข้อมูลประกาศกำหนดหรือไม่** `w2` `DOC+PUB`

- **ตรวจอะไร:** ตรวจว่าระยะเวลาเก็บและลบข้อมูลที่นโยบายระบุตรงกับหรือสั้นกว่าเพดานที่หน่วยงานคุ้มครองข้อมูลส่วนบุคคลที่เกี่ยวข้องกำหนดไว้หรือไม่ ต้องอ้างจากประกาศสาธารณะของหน่วยงานนั้นโดยตรง ห้ามใช้ความรู้ทั่วไป
- **ขั้นตอนการตรวจ:**
  1. ระบุหน่วยงานคุ้มครองข้อมูลที่เกี่ยวข้องกับลูกค้าในไทย (อ้างอิงจากกฎหมายที่นโยบายอ้างถึงในข้อ 278)
  2. เข้าเว็บทางการของหน่วยงานนั้นโดยตรง ค้นประกาศที่เกี่ยวกับระยะเวลาเก็บข้อมูล
  3. เก็บสำเนาถาวรของประกาศนั้น
  4. เทียบตัวเลขที่นโยบายของโบรกระบุกับเพดานของหน่วยงาน
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** สำเนาประกาศของหน่วยงาน (`RST-BRKA-P10-289-01`) · ตารางเทียบตัวเลข
- **ผ่าน:** ระยะเวลาที่โบรกระบุไม่เกินเพดานที่หน่วยงานกำหนด
- **ไม่ผ่าน:** ระยะเวลาที่โบรกระบุเกินเพดานที่หน่วยงานกำหนด
- **ยังไม่ได้ตรวจ:** หน่วยงานที่เกี่ยวข้องไม่มีประกาศเพดานระยะเวลาที่ชัดเจน
- **ตัวอย่าง:** Broker C ระบุเก็บข้อมูลทั่วไป 15 ปี ขณะที่ประกาศของหน่วยงานกำหนดเพดานทั่วไปไว้ที่ 10 ปี → **ไม่ผ่าน**

**P10-290 · สิทธิขอสำเนาข้อมูลทั้งหมดก่อนลบ** `w2` `SUP+ACC`

- **ตรวจอะไร:** ตรวจว่าก่อนลบข้อมูลตามคำขอในข้อ 279 ผู้ตรวจขอรับสำเนาข้อมูลทั้งหมดของตนก่อนได้หรือไม่ (การใช้สิทธิพกพาข้อมูลควบคู่กับการลบ) และได้รับสำเนาครบตามที่ขอหรือไม่
- **ขั้นตอนการตรวจ:**
  1. ก่อนยื่นคำขอลบข้อมูลในข้อ 279 ยื่นคำขอรับสำเนาข้อมูลทั้งหมดก่อน
  2. บันทึก `V0` ของคำขอรับสำเนา
  3. เปิดสำเนาที่ได้รับ เทียบกับรายการใน `PII-SET`
  4. บันทึกรายการที่ขาดหายจากสำเนาที่ได้รับ
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** สำเนาข้อมูลที่ได้รับ (`RST-BRKA-P10-290-01-FULL/-RED`) · ตารางเทียบกับ `PII-SET`
- **ผ่าน:** ได้รับสำเนาข้อมูลครบตามที่ขอก่อนดำเนินการลบ
- **ไม่ผ่าน:** ปฏิเสธไม่ให้สำเนา หรือสำเนาที่ได้ไม่ครบตามที่มีจริง
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker A ให้สำเนาข้อมูลครบทุกรายการก่อนดำเนินการลบตามคำขอ → **ผ่าน**

**P10-291 · เอกสารยืนยันตัวตนถูกเก็บนานกว่าข้อมูลอื่นหรือไม่ และเหตุผล** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายแยกระยะเวลาเก็บเอกสารยืนยันตัวตน (`PII-07`) ออกจากข้อมูลประเภทอื่นหรือไม่ และให้เหตุผลที่สมเหตุสมผล (เช่น กฎหมายป้องกันการฟอกเงิน) หรือเก็บนานผิดปกติโดยไม่มีเหตุผล
- **ขั้นตอนการตรวจ:**
  1. เปิดหัวข้อระยะเวลาเก็บรักษาข้อมูลจากข้อ 277
  2. บันทึกว่ามีการแยกระยะเวลาของเอกสารยืนยันตัวตนหรือไม่
  3. เทียบระยะเวลานั้นกับกฎหมายที่อ้างถึงในข้อ 278
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้อง (`RST-BRKA-P10-291-01`)
- **ผ่าน:** ระยะเวลาเก็บเอกสารยืนยันตัวตนตรงกับหรือสั้นกว่าที่กฎหมายที่อ้างถึงกำหนด
- **ไม่ผ่าน:** เก็บนานกว่าที่กฎหมายที่อ้างถึงกำหนดโดยไม่มีเหตุผลอื่นอธิบาย
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker B เก็บเอกสารยืนยันตัวตนไว้ 20 ปี ขณะที่กฎหมายฟอกเงินที่อ้างถึงกำหนดไว้เพียง 5 ปี โดยไม่มีคำอธิบายเพิ่มเติม → **ไม่ผ่าน**

**P10-292 · การจัดการข้อมูลของบัญชีที่ไม่เคลื่อนไหวนานแต่ยังไม่ปิดทางการ** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายแยกกรณีบัญชีไม่เคลื่อนไหวนาน (dormant แต่ยังไม่ปิด) ออกจากบัญชีที่ปิดทางการแล้วในแง่การจัดการข้อมูลหรือไม่ และระบุว่าจะปฏิบัติต่อข้อมูลของบัญชีเหล่านี้อย่างไร
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนานโยบาย ค้นหัวข้อเกี่ยวกับบัญชีไม่เคลื่อนไหว (อ้างอิงข้าม `p07-04` สำหรับตัวบทค่าธรรมเนียม ไม่ตรวจซ้ำ)
  2. บันทึกว่ามีข้อความเกี่ยวกับการจัดการข้อมูล (ไม่ใช่ค่าธรรมเนียม) ของบัญชีเหล่านี้หรือไม่
  3. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้อง (`RST-BRKA-P10-292-01`)
- **ผ่าน:** นโยบายระบุชัดว่าข้อมูลของบัญชีไม่เคลื่อนไหวจะถูกจัดการอย่างไรและเมื่อใด
- **ไม่ผ่าน:** ไม่มีข้อความใดกล่าวถึงกรณีนี้เลย
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** นโยบายของ Broker C ไม่มีข้อความใดเกี่ยวกับการจัดการข้อมูลของบัญชีไม่เคลื่อนไหวเลย → **ไม่ผ่าน**

**P10-293 · ความสอดคล้องระหว่างนโยบายที่ประกาศกับผลจริงเมื่อทดสอบขอลบ** `w2` `DOC+SUP`

- **ตรวจอะไร:** หมวดนี้ **ห้ามสร้างการทดสอบใหม่** ให้เทียบทุกคำมั่นในนโยบาย (ข้อ 277–278 · 287–289) กับผลที่วัดได้จริงจากการทดสอบ (ข้อ 279–286 · 290) ทีละข้อ แล้วสรุปว่าตรงกันกี่จุดจากทั้งหมด
- **ขั้นตอนการตรวจ:**
  1. สร้างตารางสองคอลัมน์: คำมั่นที่ประกาศ / ผลที่วัดได้จริง
  2. เติมคู่คำมั่น-ผลจริงทุกคู่ที่เกี่ยวข้องในหมวด S12
  3. ทำเครื่องหมายคู่ที่ไม่ตรงกัน
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางเทียบคำมั่นกับผลจริง (`RST-BRKA-P10-293-01`)
- **ผ่าน:** คู่คำมั่น-ผลจริงตรงกันทั้งหมด
- **ไม่ผ่าน:** มีคู่ใดคู่หนึ่งไม่ตรงกัน
- **ยังไม่ได้ตรวจ:** ยังไม่มีคู่ใดที่ทดสอบครบทั้งสองด้าน
- **ตัวอย่าง:** Broker A ประกาศลบภายใน 30 วันและทำได้จริงใน 25 วัน ทุกคู่ตรงกันหมด → **ผ่าน**

**P10-294 · การลบข้อมูลในระบบของผู้ประมวลผลภายนอกพร้อมระบบหลักหรือไม่** `w1` `SUP`

- **ตรวจอะไร:** ตรวจว่าเมื่อขอลบข้อมูลกับโบรกโดยตรง โบรกยืนยันหรือไม่ว่าได้แจ้งผู้ประมวลผลข้อมูลภายนอก (ตามรายชื่อจาก `p10-02`) ให้ลบข้อมูลตามไปด้วย **ข้อนี้ตรวจได้จำกัดจากภายนอก** ให้ถามในฐานะลูกค้าที่สงสัยและบันทึกคำตอบเท่านั้น ไม่สามารถพิสูจน์การลบจริงในระบบของบุคคลที่สามได้
- **ขั้นตอนการตรวจ:**
  1. เปิดรายชื่อผู้ประมวลผลภายนอกจาก `p10-02`
  2. สอบถามฝ่ายบริการในฐานะลูกค้าที่สงสัยว่าข้อมูลที่เคยส่งให้บุคคลที่สามจะถูกลบด้วยหรือไม่
  3. บันทึกคำตอบที่ได้รับคำต่อคำ
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** transcript คำถาม-คำตอบ (`RST-BRKA-P10-294-01-RED`)
- **ผ่าน:** ได้รับคำตอบยืนยันชัดเจนว่าจะแจ้งผู้ประมวลผลภายนอกให้ลบข้อมูลด้วย
- **ไม่ผ่าน:** ฝ่ายบริการตอบว่าไม่ทราบหรือปฏิเสธที่จะตอบคำถามนี้
- **ยังไม่ได้ตรวจ:** ไม่มีผู้ประมวลผลภายนอกตามรายชื่อจาก `p10-02`
- **ตัวอย่าง:** ฝ่ายบริการของ Broker B ตอบว่า "ไม่ทราบว่าผู้ให้บริการภายนอกจัดการข้อมูลอย่างไร" → **ไม่ผ่าน**

**P10-295 ● · ช่องทางขอลบข้อมูลหาง่ายหรือถูกซ่อน** `w2` `WEB+ACC`

- **ตรวจอะไร:** ตรวจว่าช่องทางยื่นคำขอลบข้อมูลหาเจอง่ายจากหน้าตั้งค่าความเป็นส่วนตัวหรือถูกซ่อนจนต้องค้นหาเอง จุดที่ต้องดูคือจำนวนคลิกจากหน้าตั้งค่าหลักถึงแบบฟอร์มหรือช่องทางยื่นคำขอ
- **ขั้นตอนการตรวจ:**
  1. เข้าสู่ระบบด้วยบัญชีของตนเอง เปิดหน้าตั้งค่าความเป็นส่วนตัว
  2. หาช่องทางยื่นคำขอลบข้อมูล นับจำนวนคลิกที่ใช้
  3. เทียบกับจำนวนคลิกที่ใช้หาช่องทางสมัครหรือฝากเงิน (เพื่อเทียบว่าการลบถูกทำให้ยากกว่าการสมัครหรือไม่)
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพเส้นทางคลิกไปยังช่องทางขอลบ (`RST-BRKA-P10-295-01`)
- **ผ่าน:** หาช่องทางขอลบข้อมูลเจอได้ภายใน `[เกณฑ์เสนอ: 3 คลิก]` จากหน้าตั้งค่าหลัก
- **ไม่ผ่าน:** ต้องค้นหาเอง ไม่มีในหน้าตั้งค่า หรือใช้มากกว่าเกณฑ์ที่กำหนด
- **ยังไม่ได้ตรวจ:** ตามนิยามกลาง
- **ตัวอย่าง:** Broker A ไม่มีช่องทางขอลบข้อมูลในหน้าตั้งค่าเลย ต้องค้นหาในนโยบายจึงพบอีเมลที่ต้องส่งคำขอเอง → **ไม่ผ่าน**

**P10-296 · ข้อมูลที่ปรากฏต่อสาธารณะลบได้ตามคำขอหรือไม่** `w1` `WEB+SUP`

- **ตรวจอะไร:** ตรวจว่าถ้าผู้ตรวจเคยโพสต์ความคิดเห็นหรือรีวิวบนช่องทางที่โบรกดูแล (เช่น หน้าฟอรัมหรือโซเชียลมีเดียทางการของโบรก) คำขอลบข้อมูลครอบคลุมถึงเนื้อหาที่ปรากฏต่อสาธารณะนี้ด้วยหรือไม่
- **ขั้นตอนการตรวจ:**
  1. ถ้าเคยโพสต์เนื้อหาใดบนช่องทางที่โบรกดูแล ให้รวมไว้ในคำขอลบข้อมูลตามข้อ 279
  2. บันทึกว่าเนื้อหานั้นถูกลบพร้อมข้อมูลอื่นหรือไม่
  3. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพเนื้อหาก่อนและหลังคำขอ (`RST-BRKA-P10-296-01`, `-02`)
- **ผ่าน:** เนื้อหาที่ปรากฏต่อสาธารณะถูกลบพร้อมข้อมูลอื่นตามคำขอ
- **ไม่ผ่าน:** เนื้อหาที่ปรากฏต่อสาธารณะยังคงอยู่ทั้งที่รวมอยู่ในคำขอลบแล้ว
- **ยังไม่ได้ตรวจ:** ผู้ตรวจไม่เคยโพสต์เนื้อหาใดบนช่องทางที่โบรกดูแล
- **ตัวอย่าง:** ผู้ตรวจไม่เคยโพสต์เนื้อหาใดบนช่องทางของ Broker C จึงไม่มีกรณีให้ตรวจ → **ยังไม่ได้ตรวจ**

**P10-297 · ระยะเวลา cool-off ก่อนลบจริงมีหรือไม่และแจ้งลูกค้าหรือไม่** `w1` `DOC+SUP`

- **ตรวจอะไร:** ตรวจว่าระหว่างยื่นคำขอลบกับการลบจริง มีช่วงเวลาผ่อนผัน (cool-off) ให้ยกเลิกคำขอได้หรือไม่ และถ้ามี ได้รับแจ้งล่วงหน้าก่อนลบจริงหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดข้อความตอบรับ `V1` จากข้อ 279
  2. ตรวจว่าระบุระยะเวลา cool-off และวิธียกเลิกคำขอหรือไม่
  3. ถ้ามี ตรวจว่าได้รับข้อความแจ้งเตือนก่อนวันที่จะลบจริงหรือไม่
  4. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความตอบรับและข้อความแจ้งเตือน (`RST-BRKA-P10-297-01`)
- **ผ่าน:** มีระยะเวลา cool-off พร้อมช่องทางยกเลิกและได้รับแจ้งก่อนลบจริง หรือไม่มี cool-off แต่ระบุชัดตั้งแต่ต้นว่าลบทันที
- **ไม่ผ่าน:** ไม่ระบุว่ามี cool-off หรือไม่ และไม่มีการแจ้งเตือนใดก่อนลบจริง
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** Broker B ระบุ cool-off 7 วันและส่งอีเมลแจ้งเตือนก่อนลบจริง 3 วัน → **ผ่าน**

**P10-298 · ผลของการลบข้อมูลต่อสิทธิเรียกร้องในอนาคต** `w2` `DOC`

- **ตรวจอะไร:** ตรวจว่านโยบายหรือข้อความยืนยันการลบเตือนหรือไม่ว่าการลบข้อมูลอาจทำให้ลูกค้าไม่สามารถร้องเรียนหรือเรียกร้องสิทธิย้อนหลังในอนาคตได้ (เพราะไม่มีหลักฐานประวัติเหลืออยู่) เพื่อให้ลูกค้าตัดสินใจโดยรู้ผลกระทบ
- **ขั้นตอนการตรวจ:**
  1. เปิดข้อความตอบรับและยืนยันจากข้อ 279 และ 285
  2. ค้นข้อความเตือนเรื่องผลกระทบต่อสิทธิเรียกร้องในอนาคต
  3. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความที่เกี่ยวข้อง (`RST-BRKA-P10-298-01`)
- **ผ่าน:** มีข้อความเตือนผลกระทบต่อสิทธิเรียกร้องในอนาคตก่อนดำเนินการลบจริง
- **ไม่ผ่าน:** ไม่มีคำเตือนใดเลยก่อนลบข้อมูลถาวร
- **ยังไม่ได้ตรวจ:** ตามข้อ 279
- **ตัวอย่าง:** Broker C ลบข้อมูลทันทีตามคำขอโดยไม่แจ้งเตือนผลกระทบใดเลย → **ไม่ผ่าน**

**P10-299 · การควบคุมคุณภาพภายใน — การเก็บค่าแฮชของหลักฐานการลบและยืนยัน** `w1` `DOC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจคำนวณและบันทึกค่าแฮชของไฟล์หลักฐานทุกชิ้นในหมวด S12 ตามระเบียบการบันทึกหลักฐานของโครงการหรือไม่ ข้อนี้เป็นการควบคุมคุณภาพภายในของผู้ตรวจเอง ไม่เกี่ยวกับพฤติกรรมของโบรก
- **ขั้นตอนการตรวจ:**
  1. เปิดทะเบียนหลักฐานของหมวด S12 ทั้งหมด
  2. คำนวณค่าแฮชของไฟล์หลักฐานทุกไฟล์
  3. บันทึกค่าแฮชลงทะเบียนหลักฐานคู่กับ Evidence ID
  4. ตรวจว่าครบทุกไฟล์ในหมวดนี้หรือไม่
- **หลักฐานที่ต้องเก็บ:** ทะเบียนค่าแฮชของหมวด S12 ทั้งหมด
- **ผ่าน:** ทุกไฟล์หลักฐานในหมวด S12 มีค่าแฮชบันทึกไว้ครบ
- **ไม่ผ่าน:** มีไฟล์หลักฐานที่ไม่มีค่าแฮชบันทึกไว้
- **ยังไม่ได้ตรวจ:** ไม่เกี่ยวข้อง — ข้อนี้เป็นการควบคุมคุณภาพภายในที่ต้องทำเสมอ
- **ตัวอย่าง:** ผู้ตรวจคำนวณค่าแฮชครบทุกไฟล์ในหมวด S12 ก่อนปิดรอบ → **ผ่าน**

**P10-300 · ข้อสรุปดัชนีความปลอดภัยข้อมูลส่วนบุคคลของทั้งเสา P10** `w3` `DOC+SUP`

- **ตรวจอะไร:** ข้อสุดท้ายของเสา P10 **ห้ามสร้างการทดสอบใหม่** ให้รวมผลจากทั้ง 6 ไฟล์ของเสา (P10-001 ถึง P10-300) มาตัดสินผ่าน/ไม่ผ่านรวมทั้งเสาเดียว ว่าความปลอดภัยของข้อมูลส่วนบุคคลและบัญชีของโบรกรายนี้ผ่านครบทุกข้อหรือไม่ ตัวแปรที่ต้องบันทึกคือจำนวนข้อที่ผ่าน · ไม่ผ่าน · ยังไม่ได้ตรวจ ของทั้งเสา แยกตามน้ำหนัก (เพื่อรายงานเท่านั้น)
- **ขั้นตอนการตรวจ:**
  1. เปิดผลของทุกข้อในเสา P10 ทั้ง 6 ไฟล์ (P10-001 ถึง P10-300 รวม 300 ข้อ)
  2. นับจำนวนข้อที่ผ่าน ไม่ผ่าน และยังไม่ได้ตรวจ แยกตามน้ำหนัก `w1`/`w2`/`w3` (เพื่อรายงานเท่านั้น ไม่ใช่เพื่อคำนวณคะแนน)
  3. ยืนยันว่าจำนวนข้อที่ผ่าน เท่ากับ 300 ข้อ (ครบทั้งเสา) และไม่มีข้อใดยังไม่ได้ตรวจ
  4. แยกรายการข้อ `w3` ที่ไม่ผ่านทั้งหมดเป็นบัญชีอ้างอิงสำหรับรายงาน ไม่มีผลต่างจากข้ออื่นในการตัดสินผ่าน/ไม่ผ่าน
  5. บันทึกผลและตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางสรุปผลทั้งเสา P10 (`RST-BRKA-P10-300-01`)
- **ผ่าน:** ทุกข้อทั้ง 300 ข้อในเสา P10 (ไฟล์ p10-01 ถึง p10-06) ตรวจแล้วครบและผ่านทุกข้อ ไม่มีข้อยกเว้นแม้แต่ข้อเดียว
- **ไม่ผ่าน:** มีข้ออย่างน้อย 1 ข้อในทั้งเสา P10 ที่ตัดสินเป็น "ไม่ผ่าน"
- **ยังไม่ได้ตรวจ:** ยังมีข้ออย่างน้อย 1 ข้อในทั้งเสา P10 ที่ยังไม่ได้ตรวจ (ไม่มีสิทธิ์สรุปผลจนกว่าจะครบทั้ง 300 ข้อ)
- **ตัวอย่าง:** Broker A ตรวจครบทั้ง 300 ข้อในเสา P10 และผ่านทุกข้อ ไม่มีข้อใดไม่ผ่านหรือยังไม่ได้ตรวจแม้แต่ข้อเดียว → **ผ่าน**

## นิยามกลางของเสา P10 — ใช้ร่วมกันทั้ง 6 ไฟล์

> บล็อกนี้เป็นแหล่งนิยามเดียวของเสา P10 ไฟล์ `p10-02` ถึง `p10-06` ให้อ้างกลับมาที่บล็อกนี้ **ห้ามตั้งนิยามซ้ำ**

### 1. ทะเบียนข้อมูลที่ผู้ตรวจมอบให้โบรก — `PII-SET`

`PII-SET` คือ **ตารางกลางของโบรกหนึ่งราย** ที่ไล่รายการทุกชิ้นข้อมูลส่วนบุคคลที่โบรกขอจากผู้ตรวจ ตั้งแต่วินาทีแรกที่เปิดหน้าสมัคร จนถึงการใช้งานบัญชีตามปกติ ตารางนี้ต้องเปิดขึ้นก่อนกรอกช่องแรกของแบบฟอร์มสมัคร และเติมต่อเนื่องตลอดรอบตรวจ

ทุกแถวของ `PII-SET` ต้องมี 7 ช่องนี้เสมอ:

| ช่อง | ความหมาย |
|---|---|
| `รหัสรายการ` | รหัสประจำชิ้นข้อมูล เช่น `PII-01` (ใช้อ้างข้ามไฟล์ได้) |
| `ชื่อชิ้นข้อมูล` | ชื่อช่องหรือเอกสารตามที่หน้าจอเรียก คำต่อคำ |
| `ขั้นตอนที่ถูกขอ` | ขั้นตอนใดของเส้นทางลูกค้า — สมัคร · ยืนยันตัวตน · ฝากเงินครั้งแรก · ถอนเงินครั้งแรก · หลังเปิดบัญชี · ตอนติดต่อฝ่ายบริการ |
| `บังคับหรือไม่` | บังคับ / ไม่บังคับ / ไม่ระบุ — ตัดสินจากเครื่องหมายบนหน้าจอและจากการทดสอบเว้นว่างจริง |
| `เหตุผลที่โบรกอ้าง` | ข้อความอธิบายที่โบรกแสดงคู่กับช่องนั้น คำต่อคำ ถ้าไม่มีให้เขียนว่า "ไม่มีคำอธิบาย" |
| `ประกาศในนโยบายหรือไม่` | พบ / ไม่พบ ในนโยบายความเป็นส่วนตัวฉบับที่บันทึกไว้ พร้อมข้อความที่ตรงกัน |
| `Evidence ID` | รหัสหลักฐานของภาพหน้าจอที่เห็นการขอชิ้นข้อมูลนั้น |

รายการอย่างน้อยที่ต้องไล่ให้ครบทุกโบรก (ถ้าโบรกไม่ขอชิ้นใด ให้บันทึกว่า "ไม่ถูกขอ" ห้ามลบแถวทิ้ง):

| รหัส | ชิ้นข้อมูล |
|---|---|
| `PII-01` | ชื่อ–นามสกุลตามเอกสารราชการ |
| `PII-02` | วันเดือนปีเกิด |
| `PII-03` | สัญชาติและประเทศที่พำนัก |
| `PII-04` | ที่อยู่ที่พำนักปัจจุบัน |
| `PII-05` | หมายเลขโทรศัพท์ |
| `PII-06` | ที่อยู่อีเมล |
| `PII-07` | เอกสารแสดงตน (บัตรประชาชน · หนังสือเดินทาง · ใบขับขี่) รวมเลขประจำตัวบนเอกสาร |
| `PII-08` | เอกสารยืนยันที่อยู่ (บิลค่าสาธารณูปโภค · รายการเดินบัญชี) |
| `PII-09` | อาชีพ นายจ้าง และรายได้ต่อปี |
| `PII-10` | แหล่งที่มาของเงินที่นำมาลงทุน และเอกสารประกอบ |
| `PII-11` | ข้อมูลการเงินสำหรับฝาก–ถอน (เลขบัญชีธนาคาร · เลขบัตร · ที่อยู่กระเป๋าสินทรัพย์ดิจิทัล) |
| `PII-12` | ภาพถ่ายใบหน้า ภาพถือเอกสารคู่ใบหน้า และวิดีโอยืนยันตัวตน |
| `PII-13` | แบบประเมินความรู้และประสบการณ์การลงทุน |
| `PII-14` | ข้อมูลอุปกรณ์ (รุ่นเครื่อง · ระบบปฏิบัติการ · เบราว์เซอร์ · ลายนิ้วมืออุปกรณ์) |
| `PII-15` | ข้อมูลตำแหน่งที่ตั้ง (จากหมายเลขไอพี และจากสิทธิ์ตำแหน่งบนแอปมือถือ) |

### 2. กฎความปลอดภัยของหลักฐานเสานี้ — สำคัญที่สุด ห้ามละเว้น

หลักฐานของเสา P10 มี **ข้อมูลส่วนตัวจริงของผู้ตรวจ** ไม่ใช่ข้อมูลสมมติ จึงต้องปฏิบัติดังนี้ทุกข้อโดยไม่มีข้อยกเว้น

1. **เก็บสองชุดเสมอ** — ทุกชิ้นหลักฐานของเสานี้ต้องมี
   - **ฉบับเต็ม (`-FULL`)** — เก็บในที่เก็บที่เข้ารหัส เปิดได้เฉพาะผู้รับผิดชอบรอบตรวจที่มีชื่อระบุไว้ ห้ามวางบนที่เก็บร่วมที่ทีมอื่นเข้าถึงได้
   - **ฉบับปิดบัง (`-RED`)** — ปิดทับข้อมูลส่วนตัวทุกจุดด้วยแถบทึบที่ลบข้อมูลออกจริง **ห้ามใช้การเบลอหรือปรับสีที่ย้อนกลับได้** ฉบับนี้เท่านั้นที่นำไปอ้างอิงในรายงานได้
2. **ห้ามนำภาพเอกสารแสดงตนฉบับเต็มเข้าไปในรายงานทุกกรณี** — แม้ปิดบังบางส่วนแล้วก็ห้าม ให้บรรยายเป็นข้อความแทน เช่น "อัปโหลดหนังสือเดินทาง 1 ฉบับ"
3. **ห้ามเผยแพร่ชื่อผู้ตรวจ** ในรายงาน ในชื่อไฟล์ และในข้อมูลกำกับไฟล์ ให้ใช้รหัสผู้ตรวจแทนเสมอ
4. ก่อนส่งหลักฐานใดเข้ารายงาน ต้อง **เปิดดูฉบับปิดบังทีละภาพ** แล้วบันทึกผู้ตรวจทานและวันเวลา UTC ที่ตรวจทาน
5. เมื่อจบรอบตรวจ ให้บันทึกรายการฉบับเต็มทั้งหมดพร้อมวันครบกำหนดทำลาย และทำลายตามกำหนดโดยบันทึกหลักฐานการทำลายไว้

### 3. นิยามการจับเวลาของเสานี้ — `V0` · `V1` · `V2` (UTC ทุกค่า)

| จุด | ความหมาย |
|---|---|
| `V0` | เวลาที่ผู้ตรวจ **ยื่นคำขอใช้สิทธิ** ออกจากฝั่งผู้ตรวจ (เวลาที่กดส่งแบบฟอร์ม หรือเวลาส่งอีเมลตามที่ปรากฏในกล่องขาออก) |
| `V1` | เวลาที่ **โบรกตอบรับ** ครั้งแรกที่เป็นการยืนยันว่าได้รับคำขอ (ไม่นับข้อความตอบกลับอัตโนมัติที่ไม่อ้างถึงคำขอ) |
| `V2` | เวลาที่โบรก **ดำเนินการเสร็จ** คือส่งผลลัพธ์ของคำขอให้ครบ หรือแจ้งปฏิเสธพร้อมเหตุผล |

ค่าที่ใช้รายงานคือ `V1 − V0` (ความเร็วตอบรับ) และ `V2 − V0` (ความเร็วดำเนินการจนจบ) บันทึกเป็นชั่วโมงทศนิยม 1 ตำแหน่ง และบันทึกเวลาที่หน้าจอหรืออีเมลแสดงพร้อมเขตเวลาต้นทางไว้ควบคู่เสมอ

### 4. กฎจริยธรรมและกฎหมายของเสานี้ — เส้นที่ข้ามไม่ได้

1. ผู้ตรวจตรวจได้เฉพาะ **ข้อมูลของตนเอง** และสิ่งที่โบรก **เผยแพร่ต่อสาธารณะ** เท่านั้น
2. **ห้ามพยายามเข้าถึงข้อมูลของลูกค้ารายอื่นเด็ดขาด** ไม่ว่าด้วยวิธีใด รวมถึงการเดารหัสอ้างอิง การแก้เลขในที่อยู่เว็บ และการใช้บัญชีของผู้อื่น
3. **ห้ามทดสอบเจาะระบบ ห้ามทดสอบช่องโหว่ ห้ามยิงคำขอผิดปกติ** — ห้ามส่งคำขอถี่ผิดปกติ ห้ามใส่ข้อความสั่งการลงในช่องกรอก ห้ามใช้เครื่องมือสแกน ห้ามแก้ค่าที่ส่งออกจากเบราว์เซอร์
4. เครื่องมือที่ใช้ได้มีเพียง **เครื่องมือมาตรฐานของเบราว์เซอร์ที่ผู้ใช้ทั่วไปเปิดได้เอง** เพื่ออ่านสิ่งที่หน้าเว็บส่งมาให้เครื่องตนเองเท่านั้น
5. ถ้าพบสิ่งผิดปกติ **โดยบังเอิญ** — เช่น เห็นข้อมูลของคนอื่นโผล่บนหน้าจอตนเอง — ให้ **บันทึกภาพหนึ่งครั้งแล้วหยุดทันที ห้ามทำซ้ำเพื่อยืนยัน** ห้ามกดต่อ ห้ามเก็บข้อมูลของบุคคลนั้นเกินกว่าที่จำเป็นต่อการรายงาน แล้วส่งเรื่องให้ผู้รับผิดชอบรอบตรวจตัดสินใจ
6. เอกสารทุกฉบับที่โบรกให้ผู้ตรวจในฐานะลูกค้า ใช้เพื่อการตรวจได้ แต่ **ห้ามเผยแพร่ฉบับเต็มต่อสาธารณะ** ถ้าเอกสารนั้นไม่ได้เผยแพร่อยู่แล้ว

## S01 · นโยบายความเป็นส่วนตัวและความครบถ้วน (001–025)

**P10-001 · การตั้งทะเบียน `PII-SET` ก่อนกรอกช่องแรก** `w3` `DOC+ACC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจตั้งตาราง `PII-SET` ตามนิยามกลางไว้ **ก่อน** กรอกช่องแรกของแบบฟอร์มสมัครโบรกรายนี้หรือไม่ จุดที่ต้องเปิดดูคือไฟล์ตาราง `PII-SET` ของโบรกรายนี้ และภาพหน้าจอแบบฟอร์มสมัครหน้าแรก ตัวแปรที่ต้องบันทึกคือ วันเวลา UTC ที่สร้างไฟล์ตาราง · วันเวลา UTC ที่กรอกช่องแรก · จำนวนแถวตั้งต้น · ครบทั้ง 7 ช่องหรือไม่ ข้อนี้เป็นฐานของทั้งเสา ถ้าไม่มีตารางนี้ ข้อในหมวด S02 จะเทียบอะไรไม่ได้เลย
- **ขั้นตอนการตรวจ:**
  1. เปิดไฟล์ตาราง `PII-SET` ใหม่สำหรับโบรกรายนี้โดยเฉพาะ แล้ววางหัวตาราง 7 ช่องตามนิยามกลาง
  2. เติมแถวตั้งต้น 15 แถวตาม `PII-01` ถึง `PII-15` โดยยังไม่กรอกผลลัพธ์ ให้ทุกแถวมีค่าเริ่มต้นว่า "ยังไม่พบ"
  3. บันทึกวันเวลา UTC ที่สร้างไฟล์ลงในหัวไฟล์ และเก็บภาพหน้าจอไฟล์ที่เห็นวันเวลาสร้าง
  4. เปิดหน้าสมัครของโบรกในเบราว์เซอร์โหมดไม่บันทึกประวัติ จับภาพเต็มหน้าก่อนกรอกอะไรทั้งสิ้น พร้อมให้เห็นนาฬิกาเครื่อง
  5. บันทึกวันเวลา UTC ของภาพในขั้น 4 แล้วเทียบว่าเกิดหลังเวลาสร้างไฟล์ในขั้น 3 หรือไม่
  6. ตรวจว่าหัวตารางมีครบ 7 ช่อง และไม่มีช่องใดถูกตัดออก บันทึกผลเป็นรายการติ๊ก
  7. บันทึกไฟล์ตารางเป็นฉบับตั้งต้นที่แก้ไม่ได้ (สำเนาแช่แข็ง) แล้วตั้งชื่อไฟล์ตามรูปแบบ Evidence ID
- **หลักฐานที่ต้องเก็บ:** ไฟล์ตาราง `PII-SET` ฉบับตั้งต้น (`RST-BRKA-P10-001-01-FULL` และ `-01-RED`) · ภาพหน้าจอที่เห็นวันเวลาสร้างไฟล์ (`-02`) · ภาพเต็มหน้าสมัครก่อนกรอก (`-03`) · รายการติ๊กหัวตาราง 7 ช่อง
- **ผ่าน:** มีไฟล์ตาราง `PII-SET` ที่มีครบ 15 แถวตั้งต้นและครบ 7 ช่อง โดยเวลาสร้างไฟล์อยู่ก่อนเวลาที่กรอกช่องแรกของแบบฟอร์มสมัคร
- **ไม่ผ่าน:** ไม่มีไฟล์ตาราง หรือมีแต่สร้างหลังกรอกช่องแรกไปแล้ว หรือขาดช่องใดช่องหนึ่งใน 7 ช่อง
- **ยังไม่ได้ตรวจ:** ยังไม่ได้เริ่มขั้นตอนสมัครกับโบรกรายนี้
- **ตัวอย่าง:** ผู้ตรวจ Broker A สร้างตารางครบ 15 แถวเวลา 08:12 UTC แล้วเปิดหน้าสมัครกรอกช่องแรกเวลา 08:41 UTC โดยตารางมีครบ 7 ช่อง → **ผ่าน**

**P10-002 ● · มีนโยบายความเป็นส่วนตัวเผยแพร่ต่อสาธารณะหรือไม่** `w3` `WEB`

- **ตรวจอะไร:** ตรวจว่าโบรกมีเอกสารที่เป็นนโยบายความเป็นส่วนตัวเผยแพร่บนเว็บสาธารณะจริงหรือไม่ จุดที่ต้องเปิดดูคือส่วนท้ายของหน้าแรก หน้ารวมเอกสารกฎหมาย และผลค้นในเว็บของโบรกเอง ตัวแปรที่ต้องบันทึกคือ ชื่อเอกสารตามที่โบรกเรียก · ที่อยู่เว็บเต็ม · จำนวนคำของเอกสาร · เอกสารนั้นมีเนื้อหาว่าด้วยการเก็บและใช้ข้อมูลส่วนบุคคลจริงหรือเป็นเพียงย่อหน้าเดียวในหน้าเงื่อนไขการใช้งาน ไม่นับข้อความสั้น ๆ ว่า "เราให้ความสำคัญกับความเป็นส่วนตัวของคุณ" ที่ไม่มีเนื้อหาต่อ
- **ขั้นตอนการตรวจ:**
  1. เปิดเบราว์เซอร์โหมดไม่บันทึกประวัติ แล้วพิมพ์โดเมนของโบรกเอง **ห้ามเข้าผ่านลิงก์โฆษณาหรือลิงก์แนะนำ**
  2. เลื่อนลงถึงส่วนท้ายหน้าแรก จับภาพเต็มหน้าให้เห็นรายการลิงก์เอกสารทั้งหมด
  3. ค้นคำว่า `privacy` · `ความเป็นส่วนตัว` · `ข้อมูลส่วนบุคคล` · `data protection` ทีละคำในหน้าแรก บันทึกจำนวนที่พบและตำแหน่ง
  4. เปิดทุกลิงก์ที่ชื่อเข้าข่ายนโยบายความเป็นส่วนตัว บันทึกที่อยู่เว็บเต็มของแต่ละหน้า
  5. อ่านเอกสารที่เปิดได้ทั้งฉบับ แล้วนับจำนวนคำและบันทึกหัวข้อระดับบนทั้งหมด
  6. ตัดสินว่าเอกสารนั้นเป็นนโยบายเต็มฉบับ หรือเป็นเพียงย่อหน้าแทรกในเอกสารอื่น โดยดูว่ามีหัวข้อว่าด้วยการเก็บ การใช้ และสิทธิ ครบหรือไม่
  7. เก็บสำเนาถาวรของเอกสารเป็นไฟล์ที่แก้ไม่ได้ พร้อมบันทึกวันเวลา UTC ที่บันทึก แล้วตั้งชื่อไฟล์ตาม Evidence ID

- **ผ่าน:** พบเอกสารนโยบายความเป็นส่วนตัวเป็นเอกสารของตนเองบนเว็บสาธารณะ ที่มีหัวข้อครอบคลุมทั้งการเก็บ การใช้ และสิทธิของเจ้าของข้อมูล

- **ตัวอย่าง:** Broker A มีลิงก์ *Privacy* ที่ส่วนท้าย กดแล้วได้หน้าที่มีเพียง 2 ประโยคว่าให้ความสำคัญกับความเป็นส่วนตัวและใช้การเข้ารหัส ไม่มีหัวข้อใดบอกว่าเก็บข้อมูลอะไร → **ไม่ผ่าน**

**P10-003 ● · หานโยบายเจอโดยไม่ต้องล็อกอิน และกี่คลิกจากหน้าแรก** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่าลูกค้าทั่วไปที่ยังไม่มีบัญชี เข้าถึงนโยบายความเป็นส่วนตัวได้หรือไม่ และต้องกดกี่ครั้งจากหน้าแรก จุดที่ต้องเปิดดูคือเส้นทางการกดจากหน้าแรกถึงหน้านโยบาย ตัวแปรที่ต้องบันทึกคือ จำนวนคลิกที่สั้นที่สุด · ต้องล็อกอินหรือไม่ · ต้องเลือกประเทศหรือยอมรับแบนเนอร์ก่อนจึงจะเห็นลิงก์หรือไม่ · ลิงก์อยู่ในตำแหน่งที่มองเห็นได้โดยไม่ต้องเลื่อนหรือไม่ นโยบายที่ต้องล็อกอินก่อนจึงอ่านได้ ถือว่าลูกค้าที่กำลังตัดสินใจอ่านไม่ได้
- **ขั้นตอนการตรวจ:**
  1. เปิดเบราว์เซอร์โหมดไม่บันทึกประวัติหน้าต่างใหม่ ล้างคุกกี้ก่อนเริ่ม แล้วพิมพ์โดเมนของโบรกเอง
  2. **ไม่กดยอมรับแบนเนอร์ใด ๆ** แล้วลองหาลิงก์นโยบายให้เจอ บันทึกว่าหาเจอหรือไม่ในสภาพนี้
  3. นับจำนวนคลิกที่สั้นที่สุดจากหน้าแรกถึงหน้านโยบายที่เปิดอ่านได้ครบ จับภาพหน้าจอทุกคลิกตามลำดับ
  4. บันทึกว่าระหว่างทางมีจุดใดบังคับให้ล็อกอิน สมัคร เลือกประเทศ หรือกรอกอีเมลก่อนหรือไม่
  5. ทำซ้ำขั้น 1–4 บนหน้าจอโทรศัพท์ เพราะเมนูส่วนท้ายบนมือถือมักถูกพับ บันทึกจำนวนคลิกของมือถือแยกไว้
  6. ทำซ้ำขั้น 1–4 อีกครั้งโดยเข้าจากผลค้นในเครื่องมือค้นหาแทนการเข้าหน้าแรก บันทึกว่าถึงหน้านโยบายได้โดยตรงหรือไม่
  7. บันทึกตารางสรุป ช่องทาง/จำนวนคลิก/ต้องล็อกอินหรือไม่ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอทุกคลิกของเส้นทางสั้นที่สุดทั้งบนคอมพิวเตอร์และมือถือ (`RST-BRKA-P10-003-01` ถึง `-08`) · ตารางสรุปช่องทาง/จำนวนคลิก
- **ผ่าน:** เปิดอ่านนโยบายฉบับเต็มได้โดยไม่ต้องล็อกอิน ไม่ต้องสมัคร ไม่ต้องกรอกข้อมูลใด และถึงหน้านโยบายได้ภายใน 3 คลิกจากหน้าแรก ทั้งบนคอมพิวเตอร์และมือถือ `[เกณฑ์เสนอ: 3 คลิก]`
- **ไม่ผ่าน:** ต้องล็อกอินหรือกรอกข้อมูลก่อนจึงอ่านได้ หรือใช้เกิน 3 คลิกบนช่องทางใดช่องทางหนึ่ง
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker B เปิดนโยบายได้ใน 2 คลิกบนคอมพิวเตอร์ แต่บนมือถือลิงก์อยู่ในเมนูที่ต้องกด 4 ครั้งจึงถึง → **ไม่ผ่าน**

**P10-004 · นโยบายบันทึกเป็นสำเนาถาวรได้หรือไม่** `w1` `WEB+DOC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจเก็บนโยบายเป็นสำเนาที่ยืนยันเนื้อหา ณ วันที่อ่านได้หรือไม่ เพราะเนื้อหาบนเว็บเปลี่ยนได้ทุกเมื่อโดยไม่แจ้ง จุดที่ต้องเปิดดูคือหน้านโยบายบนเว็บ และไฟล์สำเนาที่บันทึกได้ ตัวแปรที่ต้องบันทึกคือ รูปแบบไฟล์ที่บันทึกได้ · เนื้อหาในสำเนาครบเท่าหน้าเว็บหรือไม่ · ค่าแฮชของไฟล์สำเนา · วันเวลา UTC ที่บันทึก · หน้าเว็บมีมาตรการขัดขวางการคัดลอกหรือพิมพ์หรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้านโยบายฉบับเต็ม แล้วกดขยายทุกส่วนที่พับอยู่จนไม่เหลือส่วนที่ยังพับ
  2. บันทึกหน้าเป็นไฟล์เอกสารพิมพ์ (พิมพ์เป็นไฟล์) แล้วเปิดไฟล์ที่ได้ตรวจว่าเนื้อหาครบทุกหัวข้อเท่าที่เห็นบนหน้าจอ
  3. บันทึกหน้าเป็นภาพเต็มหน้าอีกชุดหนึ่ง ให้เห็นที่อยู่เว็บและนาฬิกาเครื่องในภาพ
  4. คัดลอกข้อความทั้งหน้าเป็นไฟล์ข้อความล้วน แล้วนับจำนวนคำ เทียบกับจำนวนคำที่นับได้จากไฟล์เอกสารพิมพ์
  5. คำนวณค่าแฮชของไฟล์สำเนาทุกไฟล์ แล้วบันทึกค่าแฮชคู่กับวันเวลา UTC ที่บันทึก
  6. บันทึกว่าหน้าเว็บมีการปิดการคัดลอก ปิดการพิมพ์ หรือแสดงเนื้อหาเป็นภาพที่ค้นข้อความไม่ได้หรือไม่
  7. เก็บไฟล์ทั้งชุดในที่เก็บของรอบตรวจ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ไฟล์เอกสารพิมพ์ของนโยบาย (`RST-BRKA-P10-004-01`) · ภาพเต็มหน้า (`-02`) · ไฟล์ข้อความล้วน (`-03`) · ตารางค่าแฮชและวันเวลา UTC
- **ผ่าน:** บันทึกสำเนาที่มีเนื้อหาครบเท่าหน้าเว็บได้อย่างน้อย 1 รูปแบบ และมีค่าแฮชกับวันเวลา UTC กำกับครบทุกไฟล์
- **ไม่ผ่าน:** บันทึกสำเนาไม่ได้เลย หรือสำเนาที่ได้มีเนื้อหาไม่ครบเท่าที่เห็นบนหน้าจอ
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker C แสดงนโยบายในกรอบเลื่อนที่พิมพ์ออกมาได้เพียงหน้าจอแรก ผู้ตรวจจึงเก็บเป็นภาพเต็มหน้าและไฟล์ข้อความล้วนที่ครบทั้งฉบับ พร้อมค่าแฮช → **ผ่าน**

**P10-005 ● · ระบุวันที่มีผลและเลขเวอร์ชันหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายระบุ "วันที่มีผลบังคับใช้" และ "เลขเวอร์ชัน" ที่เจาะจงหรือไม่ จุดที่ต้องเปิดดูคือส่วนหัวและส่วนท้ายของเอกสารนโยบาย ตัวแปรที่ต้องบันทึกคือ ข้อความวันที่คำต่อคำ · รูปแบบวันที่ที่ใช้ · เลขเวอร์ชันถ้ามี · วันที่นั้นเป็นวันที่มีผล วันที่แก้ไขล่าสุด หรือวันที่ทบทวน (สามอย่างนี้ไม่เหมือนกัน ต้องบันทึกตามที่เอกสารเขียน ห้ามตีความเอง) เอกสารที่ไม่มีวันที่ ทำให้พิสูจน์ไม่ได้ว่าฉบับที่ลูกค้าตกลงคือฉบับใด
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบายจากข้อ 004
  2. อ่านย่อหน้าแรกสุดและย่อหน้าท้ายสุดทั้งหมด บันทึกข้อความที่มีวันที่คำต่อคำ
  3. ค้นคำว่า `effective` · `last updated` · `version` · `มีผล` · `ปรับปรุงล่าสุด` · `ฉบับ` ทีละคำ บันทึกทุกจุดที่พบ
  4. จำแนกว่าวันที่ที่พบเป็นวันที่มีผล วันที่แก้ไขล่าสุด หรือวันที่ทบทวน ตามคำที่เอกสารใช้
  5. บันทึกรูปแบบวันที่ และตรวจว่ารูปแบบนั้นอ่านได้ชัดเจนหรือกำกวม เช่น เลขเดือนกับเลขวันสลับกันได้
  6. จับภาพส่วนที่เห็นวันที่และเลขเวอร์ชันในเฟรมเดียวกับหัวเอกสาร
  7. บันทึกผลลงแบบฟอร์มพร้อมตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพส่วนหัวและส่วนท้ายเอกสารที่เห็นวันที่ (`RST-BRKA-P10-005-01`, `-02`) · ข้อความวันที่คำต่อคำ · สำเนาถาวรจากข้อ 004
- **ผ่าน:** เอกสารระบุวันที่ที่เจาะจงถึงระดับวัน และระบุคำกำกับว่าเป็นวันที่ประเภทใด อยู่บนหน้าเดียวกับตัวนโยบาย
- **ไม่ผ่าน:** ไม่มีวันที่ใดเลย หรือมีเพียงปีโดยไม่ระบุวันและเดือน หรือมีวันที่แต่ไม่ระบุว่าเป็นวันที่ประเภทใด
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker A เขียนที่ท้ายเอกสารว่า *"© 2024"* เท่านั้น ไม่มีคำว่ามีผลหรือปรับปรุงล่าสุดที่ใด → **ไม่ผ่าน**

**P10-006 · มีประวัติเวอร์ชันย้อนหลังให้ดูหรือไม่** `w1` `WEB`

- **ตรวจอะไร:** ตรวจว่าโบรกเปิดให้ดูนโยบายฉบับก่อนหน้าหรือสรุปการเปลี่ยนแปลงหรือไม่ จุดที่ต้องเปิดดูคือหน้านโยบายและหน้ารวมเอกสารกฎหมาย ตัวแปรที่ต้องบันทึกคือ มีลิงก์ฉบับเก่าหรือไม่ · มีตารางสรุปการเปลี่ยนแปลงหรือไม่ · จำนวนฉบับย้อนหลังที่เปิดดูได้ · ฉบับเก่าที่สุดที่เข้าถึงได้ลงวันที่ใด ข้อนี้ต่างจากข้อ 023 ที่ตรวจว่าโบรก "แจ้ง" การแก้ไขอย่างไร ข้อนี้ตรวจเพียงว่าฉบับเก่ายัง "เปิดดูได้" หรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้านโยบายฉบับปัจจุบัน แล้วค้นคำว่า `previous` · `archive` · `history` · `ฉบับก่อนหน้า` · `ประวัติ`
  2. เปิดหน้ารวมเอกสารกฎหมายของโบรก แล้วไล่ดูทุกรายการว่ามีฉบับลงวันที่ต่างกันหรือไม่
  3. เปิดทุกลิงก์ฉบับเก่าที่พบ บันทึกวันที่ของแต่ละฉบับและที่อยู่เว็บ
  4. นับจำนวนฉบับย้อนหลังที่เปิดอ่านได้ครบ และบันทึกวันที่ของฉบับเก่าที่สุด
  5. ถ้ามีตารางสรุปการเปลี่ยนแปลง ให้อ่านทั้งตารางและบันทึกจำนวนรายการเปลี่ยนแปลงที่ระบุ
  6. เก็บสำเนาถาวรของทุกฉบับที่เปิดได้ พร้อมวันเวลา UTC ที่บันทึก
  7. บันทึกตารางสรุปฉบับ/วันที่/ที่อยู่เว็บ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้ารวมเอกสารกฎหมาย (`RST-BRKA-P10-006-01`) · สำเนาถาวรของฉบับย้อนหลังทุกฉบับที่เปิดได้ (`-02` เป็นต้นไป) · ตารางสรุปฉบับ/วันที่
- **ผ่าน:** เปิดดูนโยบายฉบับก่อนหน้าได้อย่างน้อย 1 ฉบับ หรือมีตารางสรุปการเปลี่ยนแปลงที่ระบุว่าแก้อะไรและเมื่อใด
- **ไม่ผ่าน:** เข้าถึงได้เฉพาะฉบับปัจจุบัน และไม่มีสรุปการเปลี่ยนแปลงใด ๆ
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker B มีหน้ารวมเอกสารที่แสดงนโยบายฉบับปี 2023 และ 2024 คู่กัน พร้อมตารางสรุปว่าฉบับใหม่เพิ่มเรื่องการโอนข้อมูลออกนอกประเทศ → **ผ่าน**

**P10-007 ● · มีนโยบายฉบับภาษาไทยหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่าโบรกที่ให้บริการลูกค้าไทยมีนโยบายความเป็นส่วนตัวฉบับภาษาไทยหรือไม่ จุดที่ต้องเปิดดูคือตัวเลือกภาษาบนเว็บ และหน้านโยบายเมื่อสลับเป็นภาษาไทย ตัวแปรที่ต้องบันทึกคือ เว็บมีตัวเลือกภาษาไทยหรือไม่ · เมื่อสลับเป็นไทยแล้วหน้านโยบายเป็นภาษาไทยจริงหรือยังเป็นภาษาเดิม · เป็นคำแปลทั้งฉบับหรือแปลบางส่วน · การแปลอ่านเข้าใจได้หรือเป็นคำแปลเครื่องที่อ่านไม่รู้เรื่อง
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าแรกในเบราว์เซอร์โหมดไม่บันทึกประวัติ แล้วหาตัวเลือกภาษา บันทึกรายการภาษาทั้งหมดที่มี
  2. สลับเป็นภาษาไทย จับภาพหน้าแรกหลังสลับ ให้เห็นที่อยู่เว็บ
  3. เปิดหน้านโยบายจากสถานะภาษาไทย จับภาพเต็มหน้า
  4. ตรวจทีละหัวข้อว่าเนื้อหาเป็นภาษาไทยครบทั้งฉบับหรือไม่ บันทึกหัวข้อที่ยังเป็นภาษาอื่นทุกหัวข้อ
  5. นับจำนวนหัวข้อระดับบนของฉบับไทย เทียบกับฉบับภาษาต้นทาง บันทึกส่วนต่าง
  6. อ่านย่อหน้าสำคัญ 3 ย่อหน้า (การเก็บ · การส่งต่อ · สิทธิ) แล้วบันทึกว่าอ่านแล้วเข้าใจความหมายได้หรือไม่ ถ้าไม่ได้ให้ยกข้อความที่กำกวมมาไว้เป็นหลักฐาน
  7. เก็บสำเนาถาวรของฉบับไทย แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพตัวเลือกภาษา (`RST-BRKA-P10-007-01`) · ภาพเต็มหน้านโยบายฉบับไทย (`-02`) · สำเนาถาวรฉบับไทย (`-03`) · ตารางเทียบจำนวนหัวข้อไทยกับต้นทาง
- **ผ่าน:** มีนโยบายฉบับภาษาไทยที่มีหัวข้อครบเท่าฉบับภาษาต้นทาง และย่อหน้าสำคัญทั้ง 3 อ่านเข้าใจความหมายได้
- **ไม่ผ่าน:** ไม่มีฉบับไทยเลย หรือสลับเป็นไทยแล้วหน้านโยบายยังเป็นภาษาอื่น หรือฉบับไทยมีหัวข้อน้อยกว่าฉบับต้นทาง
- **ยังไม่ได้ตรวจ:** โบรกไม่ได้ให้บริการลูกค้าไทยและไม่มีตัวเลือกภาษาไทยบนเว็บ (ต้องบันทึกข้อเท็จจริงนี้ไว้ ห้ามตีความเป็นไม่ผ่าน)
- **ตัวอย่าง:** Broker C มีตัวเลือกภาษาไทย หน้าแรกเป็นไทยครบ แต่กดเข้าหน้านโยบายแล้วเนื้อหากลับเป็นภาษาอังกฤษทั้งฉบับ → **ไม่ผ่าน**

**P10-008 · ฉบับแปลกับฉบับต้นทางตรงกันและระบุฉบับที่มีผลเหนือกว่าหรือไม่** `w2` `WEB+DOC`

- **ตรวจอะไร:** ตรวจว่าเนื้อหาสาระของนโยบายฉบับแปลตรงกับฉบับภาษาต้นทางหรือไม่ และเอกสารระบุหรือไม่ว่าถ้าสองฉบับขัดกัน ให้ยึดฉบับใด จุดที่ต้องเปิดดูคือนโยบายทั้งสองภาษาวางคู่กัน ตัวแปรที่ต้องบันทึกคือ จำนวนหัวข้อของแต่ละฉบับ · จุดที่เนื้อหาสาระต่างกัน · มีข้อความระบุฉบับที่มีผลเหนือกว่าหรือไม่ · วันที่มีผลของสองฉบับตรงกันหรือไม่ ข้อนี้จับกรณีที่ฉบับแปลอ่อนกว่าหรือตัดข้อความที่เสียเปรียบลูกค้าออก
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบายทั้งสองภาษาวางคู่กันบนหน้าจอเดียว
  2. จัดทำตารางเทียบรายหัวข้อ โดยไล่หัวข้อของฉบับต้นทางเป็นแกน แล้วเติมว่าฉบับแปลมีหัวข้อตรงกันหรือไม่
  3. เทียบเนื้อหาของ 6 หัวข้อบังคับทีละหัวข้อ ได้แก่ ประเภทข้อมูล · วัตถุประสงค์ · ฐานทางกฎหมาย · ระยะเวลาเก็บ · การส่งต่อและโอนออกนอกประเทศ · สิทธิของเจ้าของข้อมูล
  4. บันทึกทุกจุดที่ฉบับแปลมีข้อความเพิ่ม ขาด หรือเปลี่ยนความหมาย โดยยกข้อความทั้งสองฝั่งมาไว้คู่กัน
  5. ค้นคำว่า `prevail` · `governing language` · `ฉบับภาษา` · `มีผลเหนือกว่า` ในทั้งสองฉบับ บันทึกข้อความที่พบคำต่อคำ
  6. เทียบวันที่มีผลของสองฉบับ บันทึกส่วนต่างเป็นจำนวนวัน
  7. บันทึกตารางเทียบและภาพหน้าจอที่วางคู่กัน แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางเทียบรายหัวข้อสองภาษา (`RST-BRKA-P10-008-01`) · ภาพหน้าจอวางคู่ของทุกจุดที่ต่างกัน (`-02` เป็นต้นไป) · ข้อความว่าด้วยภาษาที่มีผลเหนือกว่าคำต่อคำ
- **ผ่าน:** ทั้ง 6 หัวข้อบังคับมีเนื้อหาสาระตรงกันทั้งสองฉบับ และมีข้อความระบุชัดว่าถ้าขัดกันให้ยึดฉบับใด
- **ไม่ผ่าน:** มีหัวข้อบังคับอย่างน้อย 1 หัวข้อที่เนื้อหาสาระต่างกัน หรือไม่มีข้อความระบุฉบับที่มีผลเหนือกว่าเลย
- **ยังไม่ได้ตรวจ:** มีนโยบายเพียงภาษาเดียว จึงไม่มีสิ่งให้เทียบ
- **ตัวอย่าง:** ฉบับต้นทางของ Broker A ระบุว่าโอนข้อมูลไปยังบริษัทในเครือนอกประเทศ แต่ฉบับไทยตัดประโยคนี้ออกทั้งประโยค → **ไม่ผ่าน**

**P10-009 · ระบุผู้ควบคุมข้อมูลเป็นนิติบุคคลใด** `w3` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายระบุชื่อนิติบุคคลที่เป็นผู้ควบคุมข้อมูลหรือไม่ ต้องเป็นชื่อบริษัทเต็มพร้อมประเภทนิติบุคคล ไม่ใช่ชื่อแบรนด์หรือคำว่า "เรา" ลอย ๆ จุดที่ต้องเปิดดูคือย่อหน้าเปิดของนโยบายและหัวข้อว่าด้วยผู้ควบคุมข้อมูล ตัวแปรที่ต้องบันทึกคือ ชื่อนิติบุคคลคำต่อคำ · เลขทะเบียนบริษัทถ้ามี · ประเทศที่จดทะเบียน · จำนวนนิติบุคคลที่ถูกระบุ (บางโบรกระบุหลายรายโดยไม่บอกว่ารายใดคุมข้อมูลของลูกค้าประเทศใด) **ข้อนี้ไม่ตรวจซ้ำเรื่องตัวตนนิติบุคคล — ใช้ผลจาก `p01` เป็นแหล่งของชื่อนิติบุคคลคู่สัญญา**
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วอ่านย่อหน้าเปิดทั้งย่อหน้า
  2. ค้นคำว่า `data controller` · `controller` · `ผู้ควบคุมข้อมูล` ทีละคำ บันทึกทุกจุดที่พบ
  3. ค้นคำต่อท้ายนิติบุคคลทีละคำ เช่น `Ltd` · `Limited` · `PLC` · `LLC` · `Pty` · `บจก` แล้วบันทึกชื่อทุกชื่อที่พบพร้อมตำแหน่งในเอกสาร
  4. บันทึกเลขทะเบียนบริษัทและประเทศที่จดทะเบียนที่ปรากฏคู่กับแต่ละชื่อ ถ้าไม่มีให้เขียนว่า "ไม่ระบุ"
  5. ถ้าพบมากกว่า 1 นิติบุคคล ให้บันทึกว่าเอกสารอธิบายหรือไม่ว่ารายใดควบคุมข้อมูลของลูกค้าประเทศใด
  6. จับภาพย่อหน้าที่ระบุผู้ควบคุมข้อมูลให้เห็นชื่อเต็มในเฟรมเดียว
  7. บันทึกผลลงตารางแล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพย่อหน้าที่ระบุผู้ควบคุมข้อมูล (`RST-BRKA-P10-009-01`) · ตารางชื่อนิติบุคคล/เลขทะเบียน/ประเทศ · สำเนาถาวรจากข้อ 004
- **ผ่าน:** นโยบายระบุชื่อนิติบุคคลเต็มพร้อมประเภทนิติบุคคลอย่างน้อย 1 ราย และถ้ามีหลายรายก็อธิบายว่ารายใดควบคุมข้อมูลของลูกค้าประเทศใด
- **ไม่ผ่าน:** ระบุเพียงชื่อแบรนด์หรือคำว่า "เรา" โดยไม่มีชื่อนิติบุคคลใดในเอกสาร หรือระบุหลายรายโดยไม่อธิบายว่ารายใดคุมข้อมูลของลูกค้ารายใด
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** นโยบายของ Broker B เขียนว่า *"BrokerB ให้ความสำคัญกับข้อมูลของคุณ"* ตลอดทั้งฉบับ ค้นคำต่อท้ายนิติบุคคลทั้งเอกสารแล้วไม่พบเลย → **ไม่ผ่าน**

**P10-010 ● · ผู้ควบคุมข้อมูลตรงกับนิติบุคคลคู่สัญญาหรือไม่** `w3` `DOC`

- **ตรวจอะไร:** เทียบชื่อผู้ควบคุมข้อมูลที่ได้จากข้อ 009 กับชื่อนิติบุคคลคู่สัญญาที่ผู้ตรวจทำสัญญาด้วยจริง **โดยใช้ชื่อนิติบุคคลคู่สัญญาจากผลตรวจเสา `p01` เป็นแหล่งเดียว ห้ามค้นทะเบียนซ้ำในข้อนี้** จุดที่ต้องเปิดดูคือแบบฟอร์มบันทึกผลของ `p01` และย่อหน้าผู้ควบคุมข้อมูลในนโยบาย ตัวแปรที่ต้องบันทึกคือ ชื่อจากสองแหล่งคำต่อคำ · จุดที่ต่างกันทุกจุด · ถ้าต่างกัน เอกสารอธิบายความสัมพันธ์ระหว่างสองนิติบุคคลหรือไม่ ข้อนี้สำคัญเพราะถ้าผู้ควบคุมข้อมูลเป็นคนละนิติบุคคลกับคู่สัญญา ลูกค้าอาจใช้สิทธิกับใครไม่ได้เลย

  1. เปิดแบบฟอร์มบันทึกผลของเสา `p01` แล้วคัดลอกชื่อนิติบุคคลคู่สัญญาที่บันทึกไว้เป็นข้อความ **ห้ามพิมพ์เอง**
  2. คัดลอกชื่อผู้ควบคุมข้อมูลจากสำเนานโยบายเป็นข้อความ
  3. วางทั้งสองในเครื่องมือเทียบข้อความ บันทึกจุดที่ต่างกันทุกจุดรวมคำต่อท้ายและเครื่องหมายวรรคตอน
  4. ประเมินว่าจุดที่ต่างเป็นเพียงรูปแบบการเขียนที่ไม่เปลี่ยนตัวตน หรือเป็นคนละนิติบุคคล
  5. ถ้าเป็นคนละราย ให้ค้นในนโยบายและในสัญญาว่ามีข้อความอธิบายความสัมพันธ์หรือไม่ เช่น บริษัทแม่ บริษัทในเครือ ผู้ประมวลผลข้อมูล บันทึกข้อความคำต่อคำ
  6. จับภาพสองแหล่งวางคู่กันในภาพเดียว โดยปิดบังข้อมูลส่วนตัวของผู้ตรวจก่อนบันทึกฉบับปิดบัง
  7. บันทึกคำตัดสินพร้อมเหตุผลลงแบบฟอร์ม แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพเทียบคู่สองแหล่ง (`RST-BRKA-P10-010-01-FULL` และ `-01-RED`) · ผลการเทียบข้อความที่ระบุจุดต่าง · ข้อความอธิบายความสัมพันธ์คำต่อคำถ้ามี
- **ผ่าน:** ชื่อผู้ควบคุมข้อมูลตรงกับนิติบุคคลคู่สัญญา หรือต่างกันแต่เอกสารอธิบายความสัมพันธ์และระบุว่าลูกค้าใช้สิทธิกับรายใดได้

**P10-012 ● · ระบุประเภทข้อมูลที่เก็บครบหรือไม่** `w3` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายไล่รายการ "ประเภทข้อมูลที่เก็บ" ไว้เป็นรายการที่ระบุได้หรือไม่ จุดที่ต้องเปิดดูคือหัวข้อว่าด้วยข้อมูลที่เก็บในนโยบาย ตัวแปรที่ต้องบันทึกคือ จำนวนประเภทข้อมูลที่ถูกระบุ · เขียนเป็นรายการเจาะจงหรือเขียนกว้างว่า "ข้อมูลที่คุณให้เรา" · มีคำว่า "รวมถึงแต่ไม่จำกัดเพียง" หรือไม่ (คำนี้ทำให้รายการเปิดกว้างจนตรวจสอบไม่ได้) · ครอบคลุมข้อมูลอ่อนไหวเช่นข้อมูลชีวมิติหรือไม่ ข้อนี้ตรวจเฉพาะตัวเอกสาร **ส่วนการเทียบกับสิ่งที่ถูกขอจริงอยู่ในหมวด S02**
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วหาหัวข้อว่าด้วยข้อมูลที่เก็บ
  2. คัดลอกรายการประเภทข้อมูลทั้งหมดออกมาเป็นรายการหนึ่งบรรทัดต่อหนึ่งประเภท แล้วนับจำนวน
  3. ทำเครื่องหมายแยกว่าประเภทใดเขียนเจาะจงพอที่จะชี้ไปยังช่องกรอกได้จริง และประเภทใดเขียนกว้างจนชี้ไม่ได้
  4. ค้นคำว่า `including but not limited to` · `เช่น` · `รวมถึงแต่ไม่จำกัด` · `อื่น ๆ` บันทึกทุกจุดที่พบ พร้อมข้อความรอบข้าง
  5. ค้นคำว่า `biometric` · `ชีวมิติ` · `ใบหน้า` · `sensitive` · `อ่อนไหว` บันทึกว่าประกาศไว้หรือไม่
  6. เทียบรายการที่ได้กับ 15 รายการใน `PII-SET` แล้วทำเครื่องหมายว่ารายการใดของ `PII-SET` มีที่รองรับในนโยบาย
  7. บันทึกตารางผลลงแบบฟอร์ม แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหัวข้อข้อมูลที่เก็บทั้งหัวข้อ (`RST-BRKA-P10-012-01`) · รายการประเภทข้อมูลที่คัดลอกออกมา · ตารางเทียบกับ 15 รายการของ `PII-SET`
- **ผ่าน:** นโยบายไล่ประเภทข้อมูลเป็นรายการเจาะจงที่ชี้ไปยังช่องกรอกจริงได้ และมีที่รองรับครบทุกรายการของ `PII-SET` ที่โบรกขอจริง
- **ไม่ผ่าน:** เขียนกว้างว่า "ข้อมูลที่คุณให้เรา" โดยไม่ไล่รายการ หรือมีรายการของ `PII-SET` ที่โบรกขอจริงแต่ไม่มีที่รองรับในนโยบาย

**P10-013 · ระบุวัตถุประสงค์การใช้แยกรายประเภทข้อมูลหรือไม่** `w3` `WEB`

**P10-014 · ระบุฐานทางกฎหมายที่ใช้เก็บแต่ละวัตถุประสงค์หรือไม่** `w2` `WEB`

- **ตัวอย่าง:** Broker C ระบุฐานครบทุกวัตถุประสงค์ แต่วัตถุประสงค์ "วิเคราะห์พฤติกรรมผู้ใช้" อ้างประโยชน์โดยชอบด้วยกฎหมายโดยไม่มีคำใดอธิบายว่าประโยชน์นั้นคืออะไร → **ไม่ผ่าน**

**P10-015 ● · ระบุระยะเวลาเก็บรักษาเป็นตัวเลขหรือเขียนกว้าง ๆ** `w3` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายบอกระยะเวลาเก็บรักษาข้อมูลเป็นจำนวนปีหรือจำนวนเดือนที่นับได้ หรือเขียนกว้างว่า "เท่าที่จำเป็น" จุดที่ต้องเปิดดูคือหัวข้อว่าด้วยระยะเวลาเก็บรักษา ตัวแปรที่ต้องบันทึกคือ ข้อความคำต่อคำ · มีตัวเลขหรือไม่ · หน่วยเวลาที่ใช้ · จุดตั้งต้นของการนับ (นับจากวันเปิดบัญชี วันทำรายการสุดท้าย หรือวันปิดบัญชี) · มีการอ้างกฎหมายที่กำหนดระยะเวลาหรือไม่ ข้อความว่า "เท่าที่จำเป็นตามวัตถุประสงค์" โดยไม่มีตัวเลข ทำให้ลูกค้าคาดหมายไม่ได้ว่าข้อมูลจะอยู่ในระบบนานเท่าใด
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วค้นคำว่า `retention` · `retain` · `ระยะเวลา` · `เก็บรักษา` · `จัดเก็บ` ทีละคำ
  2. คัดลอกทุกประโยคที่กล่าวถึงระยะเวลาเก็บรักษามาไว้คู่กันเป็นรายการ
  3. ทำเครื่องหมายว่าประโยคใดมีตัวเลขและหน่วยเวลา และประโยคใดไม่มี
  4. สำหรับประโยคที่มีตัวเลข ให้บันทึกจุดตั้งต้นของการนับตามที่เอกสารเขียน ถ้าไม่ระบุจุดตั้งต้นให้เขียนว่า "ไม่ระบุจุดตั้งต้น"
  5. ตรวจว่าเอกสารแยกระยะเวลาตามประเภทข้อมูลหรือใช้ค่าเดียวรวมทุกประเภท บันทึกผล
  6. บันทึกกฎหมายหรือข้อบังคับที่เอกสารอ้างเป็นเหตุผลของระยะเวลานั้น ถ้ามี
  7. จับภาพหัวข้อระยะเวลาเก็บรักษาทั้งหัวข้อ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหัวข้อระยะเวลาเก็บรักษา (`RST-BRKA-P10-015-01`) · รายการประโยคที่กล่าวถึงระยะเวลาคำต่อคำ · ตารางประเภทข้อมูล–ระยะเวลา–จุดตั้งต้น
- **ผ่าน:** นโยบายระบุระยะเวลาเก็บรักษาเป็นตัวเลขพร้อมหน่วยเวลา และระบุจุดตั้งต้นของการนับอย่างน้อยสำหรับข้อมูลระบุตัวตนและข้อมูลการทำรายการ
- **ไม่ผ่าน:** ไม่มีตัวเลขใดเลย หรือมีตัวเลขแต่ไม่ระบุจุดตั้งต้นของการนับจนคำนวณวันสิ้นสุดไม่ได้
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker A เขียนว่า *"เราเก็บข้อมูลของคุณไว้เท่าที่จำเป็นตามวัตถุประสงค์ที่ระบุไว้"* เพียงประโยคเดียว ไม่มีตัวเลขใดในทั้งฉบับ → **ไม่ผ่าน**

**P10-016 · แยกระยะเวลาเก็บรักษาตามประเภทข้อมูลหรือใช้ค่าเดียวรวม** `w1` `WEB`

- **ตรวจอะไร:** ตรวจความละเอียดของการประกาศระยะเวลาเก็บรักษา ว่าโบรกแยกตามประเภทข้อมูลหรือประกาศค่าเดียวรวมทุกอย่าง จุดที่ต้องเปิดดูคือหัวข้อระยะเวลาเก็บรักษาที่บันทึกไว้ในข้อ 015 ตัวแปรที่ต้องบันทึกคือ จำนวนประเภทข้อมูลที่มีระยะเวลาเฉพาะของตน · จำนวนประเภทที่ตกอยู่ใต้ค่ารวม · ระยะเวลาที่ยาวที่สุดที่ประกาศ · ระยะเวลาที่สั้นที่สุดที่ประกาศ · ข้อมูลอ่อนไหวเช่นภาพใบหน้ามีระยะเวลาเฉพาะหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดตารางประเภทข้อมูล–ระยะเวลาที่สร้างไว้ในข้อ 015
  2. ไล่ 15 รายการของ `PII-SET` ทีละรายการ แล้วบันทึกว่ารายการนั้นมีระยะเวลาเฉพาะของตนหรือตกอยู่ใต้ค่ารวม
  3. บันทึกระยะเวลาที่ยาวที่สุดและสั้นที่สุดที่ประกาศ พร้อมประเภทข้อมูลที่ผูกอยู่
  4. ตรวจเฉพาะเจาะจงว่ารายการ `PII-12` ภาพใบหน้าและวิดีโอยืนยันตัวตน มีระยะเวลาเฉพาะหรือไม่ เพราะเป็นข้อมูลที่ลบยากที่สุดเมื่อรั่วไหล
  5. ตรวจว่าเอกสารระบุหรือไม่ว่าเมื่อครบกำหนดแล้วดำเนินการอย่างไร (ลบ · ทำให้ระบุตัวตนไม่ได้ · เก็บต่อในรูปแบบอื่น)
  6. จับภาพส่วนที่แสดงการแยกระยะเวลา ถ้ามีเป็นตารางให้จับทั้งตาราง
  7. บันทึกตารางสรุปความละเอียด แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพส่วนที่แยกระยะเวลารายประเภท (`RST-BRKA-P10-016-01`) · ตารางไล่ 15 รายการของ `PII-SET` กับระยะเวลาที่ผูกอยู่
- **ผ่าน:** มีระยะเวลาเฉพาะสำหรับข้อมูลอย่างน้อย 3 ประเภท และรายการ `PII-12` มีระยะเวลาเฉพาะของตน พร้อมระบุว่าเมื่อครบกำหนดจะดำเนินการอย่างไร `[เกณฑ์เสนอ: 3 ประเภท]`
- **ไม่ผ่าน:** ใช้ค่าเดียวรวมทุกประเภท หรือรายการ `PII-12` ไม่มีระยะเวลาเฉพาะทั้งที่โบรกขอข้อมูลนี้จริง
- **ยังไม่ได้ตรวจ:** นโยบายไม่ระบุระยะเวลาเป็นตัวเลขเลยตามข้อ 015 จึงไม่มีสิ่งให้แยก
- **ตัวอย่าง:** Broker B แยกระยะเวลาไว้ 4 ประเภท ระบุว่าเมื่อครบกำหนดจะทำให้ระบุตัวตนไม่ได้ และระบุว่าวิดีโอยืนยันตัวตนเก็บ 5 ปีนับจากวันปิดบัญชี → **ผ่าน**

**P10-017 ● · ระบุการส่งข้อมูลออกนอกประเทศและประเทศปลายทางหรือไม่** `w3` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายบอกหรือไม่ว่าข้อมูลของลูกค้าถูกส่งหรือเก็บไว้นอกประเทศที่ลูกค้าอยู่ และปลายทางคือประเทศใด จุดที่ต้องเปิดดูคือหัวข้อว่าด้วยการโอนข้อมูลระหว่างประเทศ ตัวแปรที่ต้องบันทึกคือ มีหัวข้อนี้หรือไม่ · ระบุชื่อประเทศปลายทางเป็นชื่อประเทศหรือเขียนกว้างว่า "นอกเขตเศรษฐกิจ" · จำนวนประเทศที่ระบุ · ระบุหรือไม่ว่าข้อมูลชนิดใดถูกโอน **ข้อนี้ไม่ตรวจซ้ำเรื่องการส่งต่อให้บุคคลที่สามซึ่งอยู่ที่ `p10-02`** ข้อนี้จำกัดที่ประเด็นเขตแดนของที่เก็บข้อมูลเท่านั้น
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วค้นคำว่า `transfer` · `outside` · `international` · `cross-border` · `นอกประเทศ` · `ต่างประเทศ` · `โอนข้อมูล` ทีละคำ
  2. คัดลอกทุกย่อหน้าที่กล่าวถึงการโอนหรือการเก็บข้อมูลนอกประเทศมาไว้เป็นรายการ
  3. บันทึกชื่อประเทศหรือภูมิภาคทุกชื่อที่ปรากฏ ถ้าเขียนกว้างให้ยกข้อความมาคำต่อคำ
  4. บันทึกว่าเอกสารระบุหรือไม่ว่าข้อมูลชนิดใดถูกโอน หรือระบุเพียงว่า "ข้อมูลของคุณ" รวม ๆ
  5. ค้นในหน้าอื่นของเว็บว่ามีการระบุที่ตั้งศูนย์ข้อมูลหรือไม่ แล้วบันทึกว่าสอดคล้องกับนโยบายหรือไม่
  6. จับภาพหัวข้อการโอนข้อมูลระหว่างประเทศทั้งหัวข้อ
  7. บันทึกตารางประเทศปลายทางและชนิดข้อมูลที่โอน แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหัวข้อการโอนข้อมูลระหว่างประเทศ (`RST-BRKA-P10-017-01`) · ตารางประเทศปลายทาง–ชนิดข้อมูล · ภาพหน้าอื่นที่ระบุที่ตั้งศูนย์ข้อมูลถ้ามี (`-02`)
- **ผ่าน:** นโยบายระบุว่ามีหรือไม่มีการโอนข้อมูลออกนอกประเทศ และถ้ามี ระบุชื่อประเทศหรือภูมิภาคปลายทางที่ระบุตัวได้
- **ไม่ผ่าน:** ไม่มีหัวข้อนี้เลยทั้งที่โบรกเป็นนิติบุคคลต่างประเทศ หรือมีแต่ระบุกว้างจนชี้ประเทศปลายทางไม่ได้
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker C เขียนเพียงว่า *"ข้อมูลของคุณอาจถูกโอนไปยังประเทศอื่น"* โดยไม่ระบุประเทศใดเลยทั้งฉบับ → **ไม่ผ่าน**

**P10-018 · ระบุกลไกคุ้มครองการโอนข้ามประเทศหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่าเมื่อมีการโอนข้อมูลออกนอกประเทศ นโยบายระบุกลไกคุ้มครองที่ใช้หรือไม่ เช่น ข้อสัญญามาตรฐาน การรับรองความเพียงพอของประเทศปลายทาง หรือกฎเกณฑ์ภายในกลุ่มบริษัท จุดที่ต้องเปิดดูคือหัวข้อการโอนข้อมูลระหว่างประเทศ ตัวแปรที่ต้องบันทึกคือ ระบุกลไกหรือไม่ · ชื่อกลไกที่อ้าง · มีช่องทางขอสำเนาเอกสารกลไกนั้นหรือไม่ · ระบุหรือไม่ว่าประเทศปลายทางมีระดับการคุ้มครองอย่างไร
- **ขั้นตอนการตรวจ:**
  1. เปิดย่อหน้าการโอนข้อมูลที่คัดลอกไว้ในข้อ 017
  2. ค้นคำว่า `standard contractual clauses` · `adequacy` · `binding corporate rules` · `safeguard` · `ข้อสัญญามาตรฐาน` · `มาตรการคุ้มครอง` ทีละคำ
  3. บันทึกชื่อกลไกทุกกลไกที่พบ พร้อมข้อความรอบข้างคำต่อคำ
  4. ตรวจว่าเอกสารให้ช่องทางขอสำเนาหรือรายละเอียดของกลไกนั้นหรือไม่ บันทึกช่องทางที่ให้
  5. บันทึกว่าเอกสารระบุระดับการคุ้มครองของประเทศปลายทางหรือไม่ ถ้าระบุให้ยกข้อความมา
  6. เทียบว่ากลไกที่อ้างครอบคลุมทุกประเทศปลายทางที่ระบุในข้อ 017 หรือครอบคลุมเพียงบางประเทศ
  7. บันทึกตารางประเทศ–กลไกคุ้มครอง แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพส่วนที่ระบุกลไกคุ้มครอง (`RST-BRKA-P10-018-01`) · ตารางประเทศ–กลไก · ข้อความช่องทางขอสำเนาคำต่อคำ
- **ผ่าน:** ระบุกลไกคุ้มครองที่ระบุชื่อได้ ครอบคลุมทุกประเทศปลายทางที่ประกาศไว้ในข้อ 017
- **ไม่ผ่าน:** ระบุว่ามีการโอนออกนอกประเทศแต่ไม่ระบุกลไกใดเลย หรือกลไกที่ระบุครอบคลุมเพียงบางประเทศปลายทาง
- **ยังไม่ได้ตรวจ:** นโยบายระบุชัดว่าไม่มีการโอนข้อมูลออกนอกประเทศ จึงไม่มีสิ่งให้ตรวจ
- **ตัวอย่าง:** Broker A ระบุปลายทาง 3 ประเทศ แต่ระบุกลไกข้อสัญญามาตรฐานเฉพาะประเทศเดียว อีก 2 ประเทศไม่มีคำใดกล่าวถึงกลไก → **ไม่ผ่าน**

**P10-019 ● · ระบุสิทธิของเจ้าของข้อมูลครบหรือไม่** `w3` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายไล่รายการสิทธิของเจ้าของข้อมูลไว้ครบหรือไม่ ได้แก่ สิทธิเข้าถึงและขอสำเนา · สิทธิขอแก้ไขให้ถูกต้อง · สิทธิขอลบ · สิทธิคัดค้านการประมวลผล · สิทธิขอให้ระงับการใช้ · สิทธิขอให้โอนข้อมูลไปยังผู้ให้บริการอื่น · สิทธิถอนความยินยอม · สิทธิร้องเรียน จุดที่ต้องเปิดดูคือหัวข้อว่าด้วยสิทธิ ตัวแปรที่ต้องบันทึกคือ จำนวนสิทธิที่ระบุ · สิทธิใดที่ขาด · มีเงื่อนไขจำกัดการใช้สิทธิใดหรือไม่ **ข้อนี้ตรวจเฉพาะตัวเอกสาร การยื่นคำขอใช้สิทธิจริงอยู่ที่ `p10-02`**
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วหาหัวข้อว่าด้วยสิทธิของเจ้าของข้อมูล
  2. คัดลอกรายการสิทธิทั้งหมดออกมาเป็นรายการหนึ่งบรรทัดต่อหนึ่งสิทธิ
  3. ไล่เทียบกับรายการสิทธิ 8 ข้อข้างต้นทีละข้อ แล้วทำเครื่องหมายว่าพบหรือไม่พบ
  4. สำหรับสิทธิที่พบ ให้บันทึกเงื่อนไขหรือข้อจำกัดที่เอกสารกำหนดไว้คู่กัน คำต่อคำ
  5. ค้นคำว่า `refuse` · `decline` · `ปฏิเสธ` · `ข้อยกเว้น` ในหัวข้อสิทธิ บันทึกกรณีที่โบรกสงวนสิทธิปฏิเสธ
  6. บันทึกว่าเอกสารระบุกรอบเวลาที่โบรกจะดำเนินการตามคำขอหรือไม่ ถ้าระบุให้บันทึกเป็นจำนวนวัน
  7. จับภาพหัวข้อสิทธิทั้งหัวข้อ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหัวข้อสิทธิทั้งหัวข้อ (`RST-BRKA-P10-019-01`) · ตารางไล่เทียบสิทธิ 8 ข้อ · ข้อความเงื่อนไขและข้อยกเว้นคำต่อคำ
- **ผ่าน:** นโยบายระบุสิทธิครบทั้ง 8 ข้อ และระบุกรอบเวลาดำเนินการเป็นจำนวนวัน
- **ไม่ผ่าน:** ขาดสิทธิอย่างน้อย 1 ข้อจาก 8 ข้อ หรือไม่ระบุกรอบเวลาดำเนินการเลย
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker B ระบุสิทธิไว้ 7 ข้อครบถ้วน แต่ไม่มีคำใดกล่าวถึงสิทธิขอให้โอนข้อมูลไปยังผู้ให้บริการอื่น → **ไม่ผ่าน**

**P10-020 · ระบุช่องทางใช้สิทธิที่ระบุตัวได้จริงหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายบอกช่องทางที่ลูกค้าจะใช้สิทธิได้จริงหรือไม่ และช่องทางนั้นระบุตัวได้ถึงระดับที่เปิดใช้ได้ทันที จุดที่ต้องเปิดดูคือหัวข้อสิทธิและหัวข้อการติดต่อ ตัวแปรที่ต้องบันทึกคือ ประเภทช่องทาง (แบบฟอร์มออนไลน์ · อีเมลเฉพาะ · ไปรษณีย์ · แชทสด) · ที่อยู่หรือลิงก์ของแต่ละช่องทาง · ช่องทางนั้นเปิดได้จริงหรือลิงก์เสีย · ต้องล็อกอินก่อนใช้ช่องทางหรือไม่ **ข้อนี้ตรวจเพียงว่าช่องทางเปิดได้ ส่วนการยื่นคำขอและจับเวลา `V0`–`V2` อยู่ที่ `p10-02`**
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วรวบรวมช่องทางใช้สิทธิทุกช่องทางที่ระบุไว้
  2. บันทึกที่อยู่หรือลิงก์ของแต่ละช่องทางคำต่อคำ
  3. เปิดลิงก์แต่ละช่องทางในเบราว์เซอร์โหมดไม่บันทึกประวัติ **โดยยังไม่กรอกและยังไม่ส่งข้อมูลใด** แล้วจับภาพหน้าที่เปิดได้
  4. บันทึกว่าช่องทางใดเปิดได้ ช่องทางใดขึ้นหน้าผิดพลาด และช่องทางใดบังคับให้ล็อกอินก่อน
  5. สำหรับช่องทางอีเมล ให้ตรวจว่าที่อยู่อีเมลเขียนครบถ้วนใช้ส่งได้จริงหรือถูกตัดทอน บันทึกที่อยู่คำต่อคำ
  6. ทำซ้ำขั้น 3–4 บนหน้าจอโทรศัพท์ เพราะแบบฟอร์มบางแบบใช้ไม่ได้บนมือถือ
  7. บันทึกตารางช่องทาง–สถานะการเปิดใช้ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอทุกช่องทางที่เปิด ทั้งบนคอมพิวเตอร์และมือถือ (`RST-BRKA-P10-020-01` ถึง `-06`) · ตารางช่องทาง–สถานะการเปิดใช้ · ที่อยู่อีเมลคำต่อคำ
- **ผ่าน:** มีช่องทางใช้สิทธิอย่างน้อย 1 ช่องทางที่ระบุตัวได้และเปิดใช้ได้จริงทั้งบนคอมพิวเตอร์และมือถือ โดยไม่ต้องล็อกอิน
- **ไม่ผ่าน:** ไม่ระบุช่องทางใดเลย หรือทุกช่องทางที่ระบุเปิดไม่ได้ หรือทุกช่องทางบังคับให้ล็อกอินก่อนทั้งที่ผู้ที่ยังไม่มีบัญชีก็เป็นเจ้าของข้อมูลได้
- **ยังไม่ได้ตรวจ:** นโยบายไม่ระบุสิทธิเลยตามข้อ 019 จึงไม่มีช่องทางให้ตรวจ
- **ตัวอย่าง:** Broker C ระบุแบบฟอร์มออนไลน์เป็นช่องทางเดียว กดแล้วขึ้นหน้าไม่พบเอกสารทั้งบนคอมพิวเตอร์และมือถือ → **ไม่ผ่าน**

**P10-021 · ระบุเจ้าหน้าที่คุ้มครองข้อมูลและช่องทางติดต่อหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายระบุการมีเจ้าหน้าที่คุ้มครองข้อมูลหรือผู้รับผิดชอบด้านข้อมูลส่วนบุคคลหรือไม่ และให้ช่องทางติดต่อโดยตรงหรือไม่ จุดที่ต้องเปิดดูคือหัวข้อการติดต่อและหัวข้อว่าด้วยผู้รับผิดชอบ ตัวแปรที่ต้องบันทึกคือ ระบุตำแหน่งนี้หรือไม่ · ช่องทางติดต่อโดยตรงคืออะไร · ช่องทางนั้นแยกจากช่องทางบริการลูกค้าทั่วไปหรือใช้ร่วมกัน · ระบุชื่อบุคคลหรือระบุเพียงตำแหน่ง (การระบุเพียงตำแหน่งเป็นเรื่องปกติและไม่ถือเป็นข้อบกพร่อง)
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วค้นคำว่า `data protection officer` · `DPO` · `เจ้าหน้าที่คุ้มครองข้อมูล` · `ผู้รับผิดชอบข้อมูล` ทีละคำ
  2. คัดลอกทุกย่อหน้าที่พบมาไว้เป็นรายการ พร้อมบันทึกตำแหน่งในเอกสาร
  3. บันทึกช่องทางติดต่อที่ให้ไว้คู่กับตำแหน่งนี้ คำต่อคำ
  4. เทียบช่องทางที่ได้กับช่องทางบริการลูกค้าทั่วไปที่ปรากฏในหน้าติดต่อของเว็บ บันทึกว่าเป็นช่องทางเดียวกันหรือแยกกัน
  5. ค้นในหน้าอื่นของเว็บด้วยคำเดียวกัน เพื่อดูว่ามีการระบุตำแหน่งนี้ที่อื่นซึ่งขัดกับนโยบายหรือไม่
  6. จับภาพย่อหน้าที่ระบุตำแหน่งและช่องทางติดต่อในเฟรมเดียว
  7. บันทึกผลลงแบบฟอร์ม แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพย่อหน้าที่ระบุเจ้าหน้าที่คุ้มครองข้อมูล (`RST-BRKA-P10-021-01`) · ช่องทางติดต่อคำต่อคำ · ภาพหน้าติดต่อทั่วไปเพื่อเทียบ (`-02`)
- **ผ่าน:** นโยบายระบุว่ามีผู้รับผิดชอบด้านข้อมูลส่วนบุคคล พร้อมช่องทางติดต่อที่ระบุตัวได้อย่างน้อย 1 ช่องทาง
- **ไม่ผ่าน:** ไม่มีคำใดกล่าวถึงผู้รับผิดชอบด้านข้อมูลส่วนบุคคล หรือกล่าวถึงแต่ไม่ให้ช่องทางติดต่อใดเลย
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker A ระบุว่ามีเจ้าหน้าที่คุ้มครองข้อมูล และให้อีเมลเฉพาะที่แยกจากอีเมลบริการลูกค้าทั่วไป → **ผ่าน**

**P10-022 · ระบุวิธีร้องเรียนต่อหน่วยงานกำกับด้านข้อมูลหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายบอกลูกค้าหรือไม่ว่าถ้าไม่พอใจการจัดการข้อมูลของโบรก สามารถร้องเรียนต่อหน่วยงานใดได้ จุดที่ต้องเปิดดูคือหัวข้อสิทธิและหัวข้อการร้องเรียน ตัวแปรที่ต้องบันทึกคือ ระบุชื่อหน่วยงานหรือไม่ · ระบุชื่อเต็มที่ค้นต่อได้หรือเขียนกว้าง · ให้ที่อยู่เว็บของหน่วยงานหรือไม่ · ระบุหรือไม่ว่าต้องร้องเรียนกับโบรกก่อน · หน่วยงานที่ระบุเป็นหน่วยงานด้านข้อมูลส่วนบุคคลจริงหรือเป็นหน่วยงานกำกับการเงิน (สองอย่างนี้คนละหน่วยงาน)
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วค้นคำว่า `complaint` · `supervisory authority` · `ร้องเรียน` · `หน่วยงานกำกับ` · `คณะกรรมการคุ้มครองข้อมูล` ทีละคำ
  2. คัดลอกทุกย่อหน้าที่พบมาไว้เป็นรายการ
  3. บันทึกชื่อหน่วยงานทุกชื่อที่ปรากฏ พร้อมที่อยู่เว็บที่เอกสารให้ไว้
  4. นำชื่อหน่วยงานที่ได้ไปค้นในเครื่องมือค้นหา แล้วเข้าเว็บทางการของหน่วยงานด้วยตนเอง **ห้ามเข้าผ่านลิงก์ที่โบรกให้** เพื่อยืนยันว่าเป็นหน่วยงานด้านข้อมูลส่วนบุคคลจริง จับภาพหน้าทางการ
  5. เทียบว่าลิงก์ที่โบรกให้ชี้ไปยังโดเมนเดียวกับเว็บทางการที่ค้นเจอหรือไม่ บันทึกผล
  6. บันทึกว่าเอกสารกำหนดหรือไม่ว่าต้องร้องเรียนกับโบรกก่อนจึงจะร้องเรียนต่อหน่วยงานได้
  7. บันทึกตารางหน่วยงาน–ที่อยู่เว็บ–ผลการยืนยัน แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพย่อหน้าการร้องเรียนในนโยบาย (`RST-BRKA-P10-022-01`) · ภาพหน้าทางการของหน่วยงานที่ค้นเอง (`-02`) · ตารางเทียบโดเมน
- **ผ่าน:** นโยบายระบุชื่อหน่วยงานที่รับเรื่องร้องเรียนด้านข้อมูลส่วนบุคคลได้ชัดเจนพอที่จะค้นต่อได้ และถ้าให้ลิงก์ ลิงก์นั้นชี้ไปยังโดเมนทางการของหน่วยงาน
- **ไม่ผ่าน:** ไม่กล่าวถึงการร้องเรียนต่อหน่วยงานภายนอกเลย หรือระบุกว้างจนค้นหน่วยงานไม่ได้ หรือลิงก์ที่ให้ชี้ไปยังโดเมนที่ไม่ใช่ของหน่วยงาน
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker B เขียนว่า *"คุณมีสิทธิร้องเรียนต่อหน่วยงานที่เกี่ยวข้อง"* โดยไม่ระบุชื่อหน่วยงานใดในทั้งฉบับ → **ไม่ผ่าน**

**P10-023 · ระบุวิธีแจ้งลูกค้าเมื่อมีการแก้ไขนโยบายหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่านโยบายกำหนดวิธีแจ้งลูกค้าเมื่อเนื้อหาถูกแก้ไขหรือไม่ จุดที่ต้องเปิดดูคือหัวข้อว่าด้วยการเปลี่ยนแปลงนโยบาย ตัวแปรที่ต้องบันทึกคือ มีหัวข้อนี้หรือไม่ · วิธีแจ้งที่ระบุ (อีเมล · ประกาศบนเว็บ · แจ้งเตือนในบัญชี · ไม่แจ้ง) · ระยะเวลาแจ้งล่วงหน้าเป็นจำนวนวัน · ระบุหรือไม่ว่าการใช้บริการต่อถือเป็นการยอมรับฉบับใหม่โดยอัตโนมัติ · แยกวิธีแจ้งระหว่างการแก้ไขสาระสำคัญกับการแก้ไขเล็กน้อยหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดสำเนาถาวรของนโยบาย แล้วค้นคำว่า `change` · `amend` · `update` · `เปลี่ยนแปลง` · `แก้ไข` · `ปรับปรุง` ทีละคำ
  2. คัดลอกหัวข้อว่าด้วยการเปลี่ยนแปลงนโยบายมาทั้งหัวข้อ
  3. บันทึกวิธีแจ้งทุกวิธีที่ระบุ พร้อมข้อความคำต่อคำ
  4. บันทึกระยะเวลาแจ้งล่วงหน้าเป็นจำนวนวัน ถ้าไม่ระบุให้เขียนว่า "ไม่ระบุระยะเวลา"
  5. ค้นข้อความที่ระบุว่าการใช้บริการต่อถือเป็นการยอมรับ แล้วยกมาคำต่อคำ
  6. ตรวจว่าเอกสารแยกวิธีแจ้งระหว่างการแก้ไขสาระสำคัญกับการแก้ไขเล็กน้อยหรือไม่
  7. จับภาพหัวข้อทั้งหัวข้อ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหัวข้อการเปลี่ยนแปลงนโยบาย (`RST-BRKA-P10-023-01`) · ข้อความวิธีแจ้งคำต่อคำ · ข้อความว่าด้วยการยอมรับโดยอัตโนมัติ
- **ผ่าน:** นโยบายระบุวิธีแจ้งอย่างน้อย 1 วิธีที่ส่งถึงลูกค้าโดยตรง และระบุระยะเวลาแจ้งล่วงหน้าเป็นจำนวนวันสำหรับการแก้ไขสาระสำคัญ
- **ไม่ผ่าน:** ไม่มีหัวข้อนี้เลย หรือมีแต่ระบุเพียงว่าจะประกาศบนเว็บโดยไม่แจ้งลูกค้าโดยตรงและไม่ระบุระยะเวลาล่วงหน้า
- **ยังไม่ได้ตรวจ:** ยังไม่พบเอกสารนโยบายเลยตามข้อ 002
- **ตัวอย่าง:** Broker C เขียนว่าจะปรับปรุงนโยบายเป็นครั้งคราวและให้ลูกค้าตรวจสอบหน้านี้เอง ไม่มีวิธีแจ้งใดและไม่มีระยะเวลาล่วงหน้า → **ไม่ผ่าน**

**P10-024 · ความสอดคล้องระหว่างนโยบายความเป็นส่วนตัวกับเอกสารสัญญาฉบับอื่น** `w3` `DOC`

- **ตรวจอะไร:** ตรวจว่าข้อความว่าด้วยข้อมูลส่วนบุคคลในนโยบายความเป็นส่วนตัว ขัดกับข้อความในเอกสารสัญญาฉบับอื่นของโบรกหรือไม่ **โดยใช้ทะเบียนเอกสารสัญญาจากผลตรวจ `p07-01` เป็นแหล่งเดียวของรายชื่อเอกสาร ห้ามไล่หาเอกสารใหม่ในข้อนี้** จุดที่ต้องเปิดดูคือทุกเอกสารในทะเบียนนั้นที่มีข้อความว่าด้วยข้อมูลส่วนบุคคล ตัวแปรที่ต้องบันทึกคือ จำนวนเอกสารที่มีข้อความเรื่องนี้ · จุดที่ขัดกันทุกจุด · เอกสารระบุลำดับความมีผลเหนือกว่าระหว่างฉบับหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดทะเบียนเอกสารสัญญาจากผลตรวจ `p07-01` แล้วคัดรายชื่อเอกสารทุกฉบับที่บันทึกไว้
  2. เปิดสำเนาถาวรของทุกเอกสารในทะเบียน แล้วค้นคำว่า `personal data` · `privacy` · `ข้อมูลส่วนบุคคล` · `ความเป็นส่วนตัว` ทีละคำในทุกฉบับ
  3. คัดลอกทุกข้อความที่พบลงตารางเดียวกัน โดยระบุชื่อเอกสารและตำแหน่งของแต่ละข้อความ
  4. เทียบข้อความเหล่านั้นกับนโยบายความเป็นส่วนตัวใน 4 ประเด็น ได้แก่ ประเภทข้อมูลที่เก็บ · ระยะเวลาเก็บ · การโอนออกนอกประเทศ · สิทธิของเจ้าของข้อมูล
  5. บันทึกทุกจุดที่ขัดกัน โดยยกข้อความจากทั้งสองฉบับมาไว้คู่กันในตารางเดียว
  6. ค้นคำว่า `prevail` · `precedence` · `มีผลเหนือกว่า` · `ลำดับ` ในทุกเอกสาร บันทึกข้อความที่กำหนดลำดับความมีผลเหนือกว่า
  7. บันทึกตารางเทียบพร้อมภาพหลักฐานทุกจุดที่ขัดกัน แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางเทียบข้อความข้ามเอกสาร (`RST-BRKA-P10-024-01`) · ภาพหลักฐานทุกจุดที่ขัดกัน (`-02` เป็นต้นไป) · ข้อความว่าด้วยลำดับความมีผลเหนือกว่าคำต่อคำ
- **ผ่าน:** ไม่พบจุดขัดกันใน 4 ประเด็นที่เทียบ หรือพบแต่มีข้อความกำหนดลำดับความมีผลเหนือกว่าที่ชี้ชัดว่าให้ยึดฉบับใด
- **ไม่ผ่าน:** พบจุดขัดกันอย่างน้อย 1 จุดใน 4 ประเด็น โดยไม่มีข้อความกำหนดลำดับความมีผลเหนือกว่า
- **ยังไม่ได้ตรวจ:** ยังไม่มีทะเบียนเอกสารสัญญาจากผลตรวจ `p07-01`
- **ตัวอย่าง:** นโยบายของ Broker A ระบุว่าเก็บข้อมูลลูกค้า 5 ปีหลังปิดบัญชี แต่ข้อตกลงลูกค้าในทะเบียน `p07-01` ระบุ 10 ปี และไม่มีข้อความใดกำหนดว่าให้ยึดฉบับใด → **ไม่ผ่าน**

**P10-025 · ข้อสรุปปิดหมวด — ดัชนีความครบถ้วนของนโยบาย** `w2` `DOC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจสรุปผลข้อ 002–024 ออกมาเป็นดัชนีความครบถ้วนของนโยบายที่คำนวณซ้ำได้หรือไม่ จุดที่ต้องเปิดดูคือแบบฟอร์มบันทึกผลของข้อ 002 ถึง 024 ตัวแปรที่ต้องบันทึกคือ จำนวนข้อที่ตัดสินว่าผ่าน · จำนวนข้อที่ไม่ผ่าน · จำนวนข้อที่ยังไม่ได้ตรวจ · ค่าดัชนีที่คำนวณได้ · รายการหัวข้อบังคับที่ขาดหายทั้งหมด ข้อนี้เป็นข้อปิดหมวดที่ทำให้หมวด S01 ส่งผลเป็นตัวเลขเดียวไปยังการให้คะแนนได้ **ห้ามคำนวณจากความรู้สึก ต้องคำนวณจากช่องผลของข้อก่อนหน้าเท่านั้น**
- **ขั้นตอนการตรวจ:**
  1. เปิดแบบฟอร์มบันทึกผลของข้อ 002 ถึง 024 ทั้งหมด แล้วคัดค่าผลลัพธ์ของแต่ละข้อลงตารางเดียว
  2. นับจำนวนข้อที่ผ่าน ไม่ผ่าน และยังไม่ได้ตรวจ แยกกันสามช่อง
  3. คำนวณดัชนีความครบถ้วนเป็นร้อยละ โดยใช้จำนวนข้อที่ผ่าน หารด้วยจำนวนข้อที่ตัดสินได้ทั้งหมด (ไม่นับข้อที่ยังไม่ได้ตรวจ) แล้วปัดเป็นจำนวนเต็ม
  4. ไล่รายการหัวข้อบังคับ 8 หัวข้อ ได้แก่ ผู้ควบคุมข้อมูล · ประเภทข้อมูล · วัตถุประสงค์ · ฐานทางกฎหมาย · ระยะเวลาเก็บ · การโอนออกนอกประเทศ · สิทธิ · การร้องเรียน แล้วทำเครื่องหมายว่าหัวข้อใดขาด
  5. ให้ผู้ตรวจคนที่สองคำนวณดัชนีจากตารางเดียวกันโดยไม่เห็นผลของคนแรก แล้วเทียบค่าที่ได้
  6. ถ้าค่าที่สองคนคำนวณได้ต่างกัน ให้ไล่หาสาเหตุทีละข้อจนตรงกัน แล้วบันทึกสาเหตุที่ต่างไว้
  7. บันทึกตารางสรุปหมวดพร้อมค่าดัชนีและรายการหัวข้อที่ขาด แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางสรุปผลข้อ 002–024 (`RST-BRKA-P10-025-01`) · ผลคำนวณดัชนีของผู้ตรวจสองคน · รายการหัวข้อบังคับที่ขาด
- **ผ่าน:** มีตารางสรุปที่คัดค่ามาจากข้อ 002–024 ครบทุกข้อ และผู้ตรวจสองคนคำนวณดัชนีได้ค่าเดียวกัน
- **ไม่ผ่าน:** ไม่มีตารางสรุป หรือมีข้อที่ไม่ได้คัดค่าเข้าตาราง หรือผู้ตรวจสองคนคำนวณได้ต่างกันหลังไล่หาสาเหตุครบแล้ว
- **ยังไม่ได้ตรวจ:** ยังตรวจข้อ 002–024 ไม่ครบทุกข้อ
- **ตัวอย่าง:** ผู้ตรวจ Broker B คัดค่าครบ 23 ข้อ ได้ผ่าน 14 ไม่ผ่าน 8 ยังไม่ได้ตรวจ 1 คำนวณดัชนีได้ 64% และผู้ตรวจคนที่สองคำนวณได้ 64% เท่ากัน โดยระบุหัวข้อที่ขาดคือฐานทางกฎหมายและการร้องเรียน → **ผ่าน**

## S02 · ข้อมูลที่เก็บจริงเทียบกับที่ประกาศ (026–050)

**P10-026 · การบันทึกทุกช่องข้อมูลที่ถูกขอตลอดเส้นทางลูกค้า** `w3` `ACC+WEB`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจเติมตาราง `PII-SET` ครบทุกจุดที่โบรกขอข้อมูลตลอดเส้นทางลูกค้าหรือไม่ ไม่ใช่เฉพาะหน้าสมัคร จุดที่ต้องเปิดดูคือทุกหน้าจอที่มีช่องกรอกหรือปุ่มอัปโหลด ตั้งแต่หน้าสมัคร หน้ายืนยันตัวตน หน้าฝากเงินครั้งแรก หน้าถอนเงินครั้งแรก และข้อความที่ฝ่ายบริการส่งมาขอเพิ่ม ตัวแปรที่ต้องบันทึกคือ จำนวนช่องทั้งหมดที่พบ · จำนวนขั้นตอนที่ไล่ครบ · จำนวนแถวของ `PII-SET` ที่มีสถานะ "ถูกขอ" · ช่องที่พบแต่ยังไม่มีแถวรองรับใน `PII-SET`
- **ขั้นตอนการตรวจ:**
  1. เปิดตาราง `PII-SET` จากข้อ 001 แล้วเตรียมช่องบันทึกให้พร้อม
  2. เดินเส้นทางสมัครทีละหน้าจอ จับภาพเต็มหน้าทุกหน้าก่อนกรอก แล้วบันทึกทุกช่องที่ปรากฏลงตาราง
  3. เดินขั้นตอนยืนยันตัวตนทีละหน้าจอ ทำซ้ำการจับภาพและการบันทึกช่องเช่นเดียวกับขั้น 2
  4. ทำรายการฝากเงินครั้งแรกและถอนเงินครั้งแรก แล้วบันทึกช่องข้อมูลที่ถูกขอเพิ่มในสองขั้นตอนนี้
  5. รวบรวมข้อความทุกฉบับที่โบรกส่งมาขอข้อมูลเพิ่มในช่วง 60 วันแรกหลังเปิดบัญชี แล้วบันทึกสิ่งที่ถูกขอลงตาราง
  6. ไล่ตรวจว่าช่องที่พบทุกช่องมีแถวรองรับใน `PII-SET` หรือไม่ ถ้าไม่มีให้เพิ่มแถวใหม่พร้อมรหัสต่อจาก `PII-15`
  7. ปิดบังข้อมูลส่วนตัวในภาพทุกภาพเป็นฉบับ `-RED` แล้วเก็บฉบับ `-FULL` ในที่เก็บที่เข้ารหัสตามกฎความปลอดภัยของเสานี้ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพเต็มทุกหน้าจอที่มีช่องกรอก ทั้งฉบับ `-FULL` และ `-RED` (`RST-BRKA-P10-026-01` เป็นต้นไป) · ตาราง `PII-SET` ที่เติมครบ · ข้อความขอข้อมูลเพิ่มจากโบรก
- **ผ่าน:** เติม `PII-SET` ครบทุกช่องที่พบใน 5 ขั้นตอน (สมัคร · ยืนยันตัวตน · ฝากครั้งแรก · ถอนครั้งแรก · ขอเพิ่มหลังเปิดบัญชี) และทุกช่องมีแถวรองรับพร้อม Evidence ID
- **ไม่ผ่าน:** มีขั้นตอนใดใน 5 ขั้นตอนที่ยังไม่ได้ไล่ หรือมีช่องที่พบแต่ยังไม่มีแถวรองรับใน `PII-SET`
- **ยังไม่ได้ตรวจ:** ยังทำรายการฝากหรือถอนครั้งแรกไม่สำเร็จ จึงยังไล่ครบ 5 ขั้นตอนไม่ได้
- **ตัวอย่าง:** ผู้ตรวจ Broker A ไล่ครบ 4 ขั้นตอน แต่ยังไม่ได้ถอนเงินครั้งแรก จึงบันทึกสถานะข้อนี้เป็นยังไม่ได้ตรวจ แทนการสรุปว่าครบ → **ไม่ผ่าน** ถ้ารายงานว่าครบทั้งที่ยังขาดขั้นตอน

**P10-027 · ข้อมูลระบุตัวตนพื้นฐานที่ถูกขอ ประกาศไว้ในนโยบายหรือไม่** `w2` `DOC`

- **ตรวจอะไร:** เทียบรายการ `PII-01` ถึง `PII-06` (ชื่อ · วันเกิด · สัญชาติและประเทศที่พำนัก · ที่อยู่ · โทรศัพท์ · อีเมล) ที่ถูกขอจริง กับรายการประเภทข้อมูลที่นโยบายประกาศไว้ตามข้อ 012 ทีละรายการ จุดที่ต้องเปิดดูคือตาราง `PII-SET` และรายการประเภทข้อมูลที่คัดลอกไว้ในข้อ 012 ตัวแปรที่ต้องบันทึกคือ รายการใดพบในนโยบาย · ข้อความในนโยบายที่ตรงกันคำต่อคำ · รายการใดถูกขอแต่ไม่ประกาศ
- **ขั้นตอนการตรวจ:**
  1. เปิดตาราง `PII-SET` แล้วกรองเฉพาะแถว `PII-01` ถึง `PII-06` ที่มีสถานะ "ถูกขอ"
  2. เปิดรายการประเภทข้อมูลที่คัดลอกจากนโยบายในข้อ 012 วางไว้คู่กัน
  3. ไล่ทีละแถว แล้วค้นในสำเนานโยบายด้วยคำที่ตรงกับชื่อช่องบนหน้าจอ บันทึกข้อความที่พบคำต่อคำ
  4. ถ้าไม่พบคำที่ตรง ให้ค้นด้วยคำใกล้เคียงอีก 2 คำ ก่อนสรุปว่าไม่พบ แล้วบันทึกคำที่ใช้ค้นทั้งหมด
  5. เติมช่อง `ประกาศในนโยบายหรือไม่` ของแต่ละแถวใน `PII-SET` พร้อมข้อความที่ตรงกัน
  6. นับจำนวนแถวที่ถูกขอแต่ไม่ประกาศ แล้วจับภาพช่องกรอกบนหน้าจอของทุกแถวนั้นเป็นหลักฐาน
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตาราง `PII-SET` แถว `PII-01` ถึง `PII-06` ที่เติมครบ (`RST-BRKA-P10-027-01`) · ภาพช่องกรอกของทุกแถวที่ไม่ประกาศ ฉบับ `-RED` (`-02` เป็นต้นไป) · รายการคำที่ใช้ค้น
- **ผ่าน:** ทุกแถวใน `PII-01` ถึง `PII-06` ที่มีสถานะถูกขอ พบข้อความรองรับในนโยบาย
- **ไม่ผ่าน:** มีอย่างน้อย 1 แถวที่ถูกขอจริงแต่ค้นในนโยบายด้วยคำตรงและคำใกล้เคียงแล้วไม่พบข้อความรองรับ
- **ยังไม่ได้ตรวจ:** ยังเติม `PII-SET` ไม่ครบตามข้อ 026 หรือไม่มีรายการประเภทข้อมูลจากข้อ 012
- **ตัวอย่าง:** Broker B ขอสัญชาติและประเทศที่พำนักในหน้าสมัคร แต่นโยบายไล่รายการไว้เพียง ชื่อ ที่อยู่ อีเมล และโทรศัพท์ ไม่มีคำว่าสัญชาติหรือประเทศที่พำนักในทั้งฉบับ → **ไม่ผ่าน**

**P10-028 · ที่อยู่และเอกสารยืนยันที่อยู่ที่ถูกขอ ประกาศไว้หรือไม่** `w2` `DOC+ACC`

- **ตรวจอะไร:** เทียบรายการ `PII-08` เอกสารยืนยันที่อยู่ ที่ถูกขอจริง กับรายการที่นโยบายประกาศ จุดที่ต้องเปิดดูคือหน้าจอที่ขอเอกสารยืนยันที่อยู่ และหัวข้อประเภทข้อมูลในนโยบาย ตัวแปรที่ต้องบันทึกคือ ชนิดเอกสารที่โบรกยอมรับทั้งหมด · อายุเอกสารสูงสุดที่ยอมรับ · จำนวนฉบับที่ขอ · นโยบายกล่าวถึงเอกสารยืนยันที่อยู่หรือไม่ · เอกสารยืนยันที่อยู่มักมีข้อมูลอื่นติดมาด้วย เช่น ยอดเงินในบัญชี นโยบายกล่าวถึงข้อมูลส่วนเกินนี้หรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าจอที่ขอเอกสารยืนยันที่อยู่ จับภาพเต็มหน้าให้เห็นรายการชนิดเอกสารที่ยอมรับทั้งหมด
  2. บันทึกชนิดเอกสารทุกชนิดที่ยอมรับ อายุเอกสารสูงสุด และจำนวนฉบับที่ขอ ลงแถว `PII-08` ของ `PII-SET`
  3. ค้นในสำเนานโยบายด้วยคำว่า `proof of address` · `utility bill` · `bank statement` · `เอกสารยืนยันที่อยู่` · `บิล` · `รายการเดินบัญชี` ทีละคำ
  4. บันทึกข้อความที่พบคำต่อคำ ถ้าไม่พบให้บันทึกคำที่ใช้ค้นทั้งหมดพร้อมผลว่าไม่พบ
  5. ตรวจว่านโยบายกล่าวถึงข้อมูลส่วนเกินที่ติดมากับเอกสารหรือไม่ เช่น ยอดคงเหลือในรายการเดินบัญชี บันทึกผล
  6. ตรวจว่าหน้าจอแนะนำให้ปิดบังข้อมูลส่วนเกินก่อนอัปโหลดหรือไม่ จับภาพคำแนะนำถ้ามี
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอที่ขอเอกสารยืนยันที่อยู่ ฉบับ `-RED` (`RST-BRKA-P10-028-01`) · แถว `PII-08` ที่เติมครบ · ข้อความในนโยบายคำต่อคำ · ภาพคำแนะนำการปิดบังถ้ามี (`-02`)
- **ผ่าน:** นโยบายกล่าวถึงเอกสารยืนยันที่อยู่เป็นประเภทข้อมูลที่เก็บ และกล่าวถึงหรือให้คำแนะนำเรื่องข้อมูลส่วนเกินที่ติดมากับเอกสาร
- **ไม่ผ่าน:** นโยบายไม่กล่าวถึงเอกสารยืนยันที่อยู่เลยทั้งที่โบรกขอจริง หรือกล่าวถึงแต่ไม่มีทั้งคำอธิบายและคำแนะนำเรื่องข้อมูลส่วนเกิน
- **ยังไม่ได้ตรวจ:** โบรกไม่ขอเอกสารยืนยันที่อยู่ในขั้นตอนใดเลย (ต้องบันทึกข้อเท็จจริงนี้ไว้ ห้ามตีความเป็นไม่ผ่าน)
- **ตัวอย่าง:** Broker C ขอรายการเดินบัญชีย้อนหลัง 3 เดือน โดยนโยบายกล่าวถึงเอกสารยืนยันที่อยู่ไว้ และหน้าจออัปโหลดมีข้อความแนะนำให้ปิดทับยอดคงเหลือได้ → **ผ่าน**

**P10-029 · เอกสารแสดงตนที่ถูกขอ ประกาศไว้หรือไม่ และขอกี่ฉบับ** `w3` `DOC+ACC`

- **ตรวจอะไร:** เทียบรายการ `PII-07` เอกสารแสดงตน ที่ถูกขอจริง กับรายการที่นโยบายประกาศ และตรวจจำนวนฉบับที่ถูกขอ จุดที่ต้องเปิดดูคือหน้าจอยืนยันตัวตนทุกหน้า ตัวแปรที่ต้องบันทึกคือ ชนิดเอกสารที่ยอมรับ · จำนวนฉบับที่บังคับต้องส่ง · โบรกขอมากกว่า 1 ชนิดพร้อมกันหรือให้เลือกชนิดใดชนิดหนึ่ง · เลขประจำตัวบนเอกสารถูกให้กรอกเป็นข้อความแยกต่างหากด้วยหรือไม่ · นโยบายกล่าวถึงเอกสารแสดงตนและเลขประจำตัวหรือไม่ **ห้ามนำภาพเอกสารแสดงตนฉบับเต็มเข้าไปในรายงานทุกกรณีตามกฎความปลอดภัยของเสานี้**
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าจอยืนยันตัวตน จับภาพเต็มหน้า **ก่อนอัปโหลดเอกสารใด** เพื่อให้ภาพไม่มีเอกสารจริงปรากฏ
  2. บันทึกชนิดเอกสารที่ยอมรับทุกชนิด และบันทึกว่าเป็นแบบเลือกชนิดใดชนิดหนึ่งหรือบังคับหลายชนิดพร้อมกัน
  3. บันทึกจำนวนฉบับที่บังคับต้องส่งเพื่อผ่านขั้นตอนนี้ ลงแถว `PII-07` ของ `PII-SET`
  4. บันทึกว่ามีช่องให้กรอกเลขประจำตัวบนเอกสารเป็นข้อความแยกต่างหากหรือไม่ จับภาพช่องนั้นขณะยังว่าง
  5. ค้นในสำเนานโยบายด้วยคำว่า `identity document` · `passport` · `identification` · `เอกสารแสดงตน` · `หนังสือเดินทาง` · `บัตรประชาชน` ทีละคำ บันทึกข้อความที่พบคำต่อคำ
  6. ค้นเพิ่มด้วยคำว่า `identification number` · `เลขประจำตัว` เพื่อดูว่านโยบายกล่าวถึงตัวเลขบนเอกสารแยกต่างหากหรือไม่
  7. บรรยายผลเป็นข้อความในแบบฟอร์มโดยไม่แนบภาพเอกสารจริง แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอยืนยันตัวตนขณะยังไม่อัปโหลด (`RST-BRKA-P10-029-01`) · แถว `PII-07` ที่เติมครบ · ข้อความในนโยบายคำต่อคำ · **ห้ามเก็บภาพเอกสารแสดงตนจริงไว้ในชุดหลักฐานของข้อนี้**
- **ผ่าน:** นโยบายกล่าวถึงเอกสารแสดงตนเป็นประเภทข้อมูลที่เก็บ และกล่าวถึงเลขประจำตัวบนเอกสารด้วยถ้าโบรกขอกรอกแยกต่างหาก
- **ไม่ผ่าน:** นโยบายไม่กล่าวถึงเอกสารแสดงตนเลย หรือกล่าวถึงเฉพาะเอกสารแต่ไม่กล่าวถึงเลขประจำตัวทั้งที่มีช่องให้กรอกแยก
- **ยังไม่ได้ตรวจ:** ยังไม่ถึงขั้นตอนยืนยันตัวตนของโบรกรายนี้
- **ตัวอย่าง:** Broker A ขอหนังสือเดินทาง 1 ฉบับพร้อมช่องกรอกเลขหนังสือเดินทางแยกต่างหาก แต่นโยบายกล่าวถึงเพียง "สำเนาเอกสารแสดงตน" โดยไม่มีคำใดกล่าวถึงการเก็บเลขประจำตัวเป็นข้อมูล → **ไม่ผ่าน**

**P10-030 ● · ภาพใบหน้าและวิดีโอยืนยันตัวตน ประกาศไว้หรือไม่** `w3` `DOC+ACC`

- **ตรวจอะไร:** เทียบรายการ `PII-12` ภาพถ่ายใบหน้า ภาพถือเอกสารคู่ใบหน้า และวิดีโอยืนยันตัวตน ที่ถูกขอจริง กับสิ่งที่นโยบายประกาศ จุดที่ต้องเปิดดูคือขั้นตอนยืนยันตัวตนแบบถ่ายภาพหรือวิดีโอ ตัวแปรที่ต้องบันทึกคือ ถูกขอหรือไม่ · รูปแบบที่ขอ (ภาพนิ่ง · ภาพถือเอกสาร · วิดีโอ · การตรวจจับว่ามีชีวิต) · ผู้ให้บริการภายนอกที่ทำหน้าที่นี้ถ้ามีชื่อปรากฏบนหน้าจอ · นโยบายใช้คำว่าข้อมูลชีวมิติหรือข้อมูลอ่อนไหวหรือไม่ · มีการขอความยินยอมแยกต่างหากก่อนถ่ายหรือไม่ ข้อมูลชนิดนี้เปลี่ยนไม่ได้เมื่อรั่วไหล จึงเป็นจุดที่การไม่ประกาศมีผลรุนแรงที่สุดในหมวดนี้
- **ขั้นตอนการตรวจ:**
  1. เปิดขั้นตอนยืนยันตัวตนจนถึงหน้าจอที่ขอถ่ายภาพหรือวิดีโอ จับภาพหน้าจอ **ก่อนเปิดกล้อง**
  2. บันทึกรูปแบบที่ถูกขอทุกรูปแบบ และบันทึกว่ารูปแบบใดบังคับ รูปแบบใดเลือกได้ ลงแถว `PII-12`
  3. บันทึกชื่อผู้ให้บริการภายนอกที่ปรากฏบนหน้าจอหรือในที่อยู่เว็บของหน้านั้น ถ้ามี
  4. บันทึกว่ามีหน้าจอขอความยินยอมแยกต่างหากก่อนเปิดกล้องหรือไม่ ถ้ามีให้จับภาพและคัดลอกข้อความคำต่อคำ
  5. ค้นในสำเนานโยบายด้วยคำว่า `biometric` · `facial` · `selfie` · `liveness` · `ชีวมิติ` · `ใบหน้า` · `ภาพถ่าย` ทีละคำ บันทึกผล
  6. ตรวจว่านโยบายจัดข้อมูลนี้เป็นข้อมูลอ่อนไหวและระบุฐานทางกฎหมายเฉพาะหรือไม่ โดยดูจากผลข้อ 014
  7. เก็บภาพหน้าจอฉบับ `-RED` และเก็บฉบับ `-FULL` ในที่เก็บที่เข้ารหัส **ห้ามนำภาพใบหน้าจริงเข้าชุดหลักฐานของข้อนี้** แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอก่อนเปิดกล้อง (`RST-BRKA-P10-030-01`) · ภาพหน้าจอขอความยินยอมถ้ามี (`-02`) · แถว `PII-12` ที่เติมครบ · ข้อความในนโยบายคำต่อคำ · **ห้ามเก็บภาพใบหน้าหรือวิดีโอยืนยันตัวตนจริงไว้ในชุดหลักฐานของข้อนี้**
- **ผ่าน:** นโยบายกล่าวถึงการเก็บภาพใบหน้าหรือวิดีโอยืนยันตัวตนอย่างชัดเจน จัดเป็นข้อมูลอ่อนไหวหรือชีวมิติ และมีฐานทางกฎหมายเฉพาะกำกับ
- **ไม่ผ่าน:** โบรกขอภาพใบหน้าหรือวิดีโอจริง แต่นโยบายไม่กล่าวถึงเลย หรือกล่าวถึงแต่ไม่จัดเป็นข้อมูลอ่อนไหวและไม่มีฐานทางกฎหมายเฉพาะ
- **ยังไม่ได้ตรวจ:** โบรกไม่ขอภาพใบหน้าหรือวิดีโอยืนยันตัวตนในขั้นตอนใดเลย (ต้องบันทึกข้อเท็จจริงนี้ไว้ ห้ามตีความเป็นไม่ผ่าน)
- **ตัวอย่าง:** Broker B ให้ถ่ายวิดีโอหันหน้าซ้ายขวาเพื่อตรวจจับว่ามีชีวิต และมีหน้าจอขอความยินยอมแยกก่อนเปิดกล้อง แต่ค้นทั้งนโยบายแล้วไม่พบคำว่าใบหน้า ชีวมิติ หรือภาพถ่ายเลย → **ไม่ผ่าน**

**P10-031 · ข้อมูลรายได้ อาชีพ และแหล่งที่มาของเงิน ประกาศไว้หรือไม่** `w2` `DOC+ACC`

- **ตรวจอะไร:** เทียบรายการ `PII-09` และ `PII-10` (อาชีพ นายจ้าง รายได้ต่อปี แหล่งที่มาของเงิน และเอกสารประกอบ) ที่ถูกขอจริง กับสิ่งที่นโยบายประกาศ จุดที่ต้องเปิดดูคือหน้าจอที่ขอข้อมูลทางการเงินส่วนบุคคลในขั้นตอนสมัครและขั้นตอนฝากเงิน ตัวแปรที่ต้องบันทึกคือ ช่องที่ถูกขอทั้งหมด · เป็นการเลือกจากช่วงค่าหรือกรอกตัวเลขจริง · เอกสารประกอบที่ถูกขอ · นโยบายกล่าวถึงข้อมูลกลุ่มนี้หรือไม่ · เหตุผลที่โบรกอ้างคู่กับช่องเหล่านี้
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าจอที่ขอข้อมูลอาชีพและรายได้ จับภาพเต็มหน้าก่อนกรอก
  2. บันทึกทุกช่องที่ถูกขอ พร้อมระบุว่าเป็นช่องเลือกจากช่วงค่าหรือช่องกรอกตัวเลขจริง ลงแถว `PII-09` และ `PII-10`
  3. บันทึกข้อความอธิบายที่โบรกแสดงคู่กับช่องเหล่านี้คำต่อคำ ถ้าไม่มีให้เขียนว่า "ไม่มีคำอธิบาย"
  4. เดินขั้นตอนฝากเงินครั้งแรกจนถึงจุดที่โบรกขอเอกสารแสดงแหล่งที่มาของเงิน ถ้ามี แล้วบันทึกชนิดเอกสารที่ยอมรับ
  5. ค้นในสำเนานโยบายด้วยคำว่า `income` · `employment` · `occupation` · `source of funds` · `source of wealth` · `รายได้` · `อาชีพ` · `แหล่งที่มาของเงิน` ทีละคำ บันทึกผล
  6. เติมช่อง `ประกาศในนโยบายหรือไม่` ของสองแถวนี้ พร้อมข้อความที่ตรงกัน
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอที่ขอข้อมูลรายได้และอาชีพ ฉบับ `-RED` (`RST-BRKA-P10-031-01`) · ภาพหน้าจอที่ขอเอกสารแหล่งที่มาของเงิน (`-02`) · แถว `PII-09` และ `PII-10` ที่เติมครบ
- **ผ่าน:** ทุกช่องที่ถูกขอในกลุ่มนี้พบข้อความรองรับในนโยบาย
- **ไม่ผ่าน:** มีช่องอย่างน้อย 1 ช่องในกลุ่มนี้ที่ถูกขอจริงแต่ไม่พบข้อความรองรับในนโยบาย
- **ยังไม่ได้ตรวจ:** โบรกไม่ขอข้อมูลกลุ่มนี้ในขั้นตอนใดเลย (ต้องบันทึกข้อเท็จจริงนี้ไว้ ห้ามตีความเป็นไม่ผ่าน)
- **ตัวอย่าง:** Broker C ขอทั้งชื่อนายจ้างและรายได้ต่อปีเป็นตัวเลขจริง แต่นโยบายกล่าวถึงเพียง "ข้อมูลทางการเงิน" โดยไม่มีคำใดกล่าวถึงอาชีพหรือนายจ้าง → **ไม่ผ่าน**

**P10-032 ● · ข้อมูลการเงินสำหรับฝากถอนที่ถูกขอ ประกาศไว้หรือไม่** `w3` `DOC+ACC`

- **ตรวจอะไร:** เทียบรายการ `PII-11` (เลขบัญชีธนาคาร เลขบัตร ที่อยู่กระเป๋าสินทรัพย์ดิจิทัล) ที่ถูกขอจริง กับสิ่งที่นโยบายประกาศ จุดที่ต้องเปิดดูคือหน้าจอฝากเงินและหน้าจอถอนเงิน ตัวแปรที่ต้องบันทึกคือ ข้อมูลการเงินชนิดใดถูกขอบ้าง · ถูกขอในรูปแบบใด (กรอกเอง · อัปโหลดภาพ · ผ่านหน้าจอของผู้ให้บริการชำระเงินภายนอก) · โบรกเก็บข้อมูลนั้นไว้เองหรือส่งต่อทันที · นโยบายกล่าวถึงข้อมูลกลุ่มนี้หรือไม่ · หน้าจอแสดงเลขบัญชีย้อนหลังในบัญชีผู้ใช้แบบเต็มหรือแบบปิดบางส่วน
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าจอฝากเงิน จับภาพหน้ารายการช่องทางทั้งหมดก่อนเลือกช่องทางใด
  2. เลือกช่องทางที่จะใช้จริง แล้วจับภาพหน้าจอถัดไปก่อนกรอกข้อมูลใด บันทึกทุกช่องที่ถูกขอ
  3. บันทึกว่าช่องเหล่านั้นอยู่บนโดเมนของโบรกหรืออยู่บนโดเมนของผู้ให้บริการชำระเงินภายนอก โดยอ่านจากแถบที่อยู่เว็บ แล้วจับภาพให้เห็นที่อยู่เว็บ
  4. เปิดหน้าจอถอนเงิน แล้วทำซ้ำขั้น 2–3 บันทึกช่องที่ถูกขอในขั้นตอนถอน
  5. หลังทำรายการเสร็จ เปิดหน้าตั้งค่าบัญชีเพื่อดูว่าข้อมูลการเงินที่กรอกไปถูกเก็บไว้แสดงย้อนหลังหรือไม่ และแสดงแบบเต็มหรือปิดบางส่วน จับภาพ
  6. ค้นในสำเนานโยบายด้วยคำว่า `payment` · `bank account` · `card` · `wallet` · `บัญชีธนาคาร` · `บัตร` · `กระเป๋า` ทีละคำ บันทึกผล
  7. ปิดบังเลขบัญชีและเลขบัตรทุกตัวในภาพด้วยแถบทึบที่ลบข้อมูลออกจริงเป็นฉบับ `-RED` แล้วเก็บฉบับ `-FULL` ในที่เก็บที่เข้ารหัส ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าจอฝากและถอนที่เห็นที่อยู่เว็บ ฉบับ `-RED` (`RST-BRKA-P10-032-01` ถึง `-04`) · ภาพหน้าตั้งค่าบัญชีที่แสดงข้อมูลการเงินย้อนหลัง (`-05`) · แถว `PII-11` ที่เติมครบ
- **ผ่าน:** ทุกชนิดข้อมูลการเงินที่ถูกขอบนโดเมนของโบรกเอง พบข้อความรองรับในนโยบาย และการแสดงย้อนหลังในบัญชีผู้ใช้เป็นแบบปิดบางส่วน
- **ไม่ผ่าน:** มีชนิดข้อมูลการเงินที่ถูกขอบนโดเมนของโบรกแต่ไม่พบข้อความรองรับในนโยบาย หรือบัญชีผู้ใช้แสดงเลขบัญชีหรือเลขบัตรแบบเต็มโดยไม่ปิดบางส่วน
- **ยังไม่ได้ตรวจ:** ยังทำรายการฝากหรือถอนไม่สำเร็จ จึงยังไม่เห็นช่องที่ถูกขอจริง
- **ตัวอย่าง:** Broker A ให้กรอกเลขบัญชีธนาคารบนหน้าจอของโบรกเอง และหน้าตั้งค่าบัญชีแสดงเลขบัญชีเต็ม 10 หลักทุกครั้งที่เปิด → **ไม่ผ่าน**

**P10-033 · แบบประเมินความรู้และประสบการณ์การลงทุน ถือเป็นข้อมูลที่ประกาศหรือไม่** `w1` `DOC+ACC`

- **ตรวจอะไร:** เทียบรายการ `PII-13` แบบประเมินความรู้และประสบการณ์การลงทุน ที่ถูกขอจริง กับสิ่งที่นโยบายประกาศ จุดที่ต้องเปิดดูคือแบบประเมินในขั้นตอนสมัคร ตัวแปรที่ต้องบันทึกคือ จำนวนคำถามทั้งหมด · คำถามใดถามข้อมูลส่วนบุคคลนอกเหนือจากความรู้ทางการเงิน เช่น ระดับการศึกษา สถานะการทำงาน · ผลการประเมินถูกเก็บไว้ในบัญชีหรือไม่ · นโยบายกล่าวถึงข้อมูลกลุ่มนี้หรือไม่ **ข้อนี้ตรวจเฉพาะมิติข้อมูลส่วนบุคคล ไม่ตรวจความเหมาะสมของแบบประเมินเองซึ่งอยู่ในเสาอื่น**
- **ขั้นตอนการตรวจ:**
  1. เปิดแบบประเมินในขั้นตอนสมัคร จับภาพทุกหน้าจอของแบบประเมินก่อนตอบ
  2. บันทึกคำถามทุกข้อลงตาราง พร้อมทำเครื่องหมายว่าข้อใดถามข้อมูลส่วนบุคคลนอกเหนือจากความรู้ทางการเงิน
  3. บันทึกจำนวนคำถามทั้งหมด และจำนวนคำถามที่ถามข้อมูลส่วนบุคคล ลงแถว `PII-13`
  4. ตอบแบบประเมินตามความจริง แล้วบันทึกว่าระบบแสดงผลการประเมินหรือไม่ และเก็บผลไว้ให้เปิดดูย้อนหลังในบัญชีหรือไม่
  5. ค้นในสำเนานโยบายด้วยคำว่า `suitability` · `appropriateness` · `knowledge` · `experience` · `แบบประเมิน` · `ความรู้` · `ประสบการณ์` ทีละคำ บันทึกผล
  6. บันทึกว่านโยบายกล่าวถึงการเก็บผลการประเมินไว้ใช้ต่อหรือไม่ และใช้เพื่อวัตถุประสงค์ใด
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพทุกหน้าจอของแบบประเมินก่อนตอบ ฉบับ `-RED` (`RST-BRKA-P10-033-01` เป็นต้นไป) · ตารางคำถามทั้งหมด · แถว `PII-13` ที่เติมครบ
- **ผ่าน:** นโยบายกล่าวถึงการเก็บข้อมูลจากแบบประเมินและระบุวัตถุประสงค์ของการเก็บ
- **ไม่ผ่าน:** โบรกเก็บผลการประเมินไว้ในบัญชี แต่นโยบายไม่กล่าวถึงข้อมูลกลุ่มนี้เลย
- **ยังไม่ได้ตรวจ:** โบรกไม่มีแบบประเมินในขั้นตอนสมัคร
- **ตัวอย่าง:** Broker B มีแบบประเมิน 12 ข้อ ในนั้นถามระดับการศึกษาและสถานะการทำงานด้วย โดยนโยบายกล่าวถึงการเก็บผลการประเมินเพื่อประเมินความเหมาะสมของผลิตภัณฑ์ → **ผ่าน**

**P10-034 · รายการที่ถูกขอจริงแต่ไม่ปรากฏในนโยบายเลย** `w3` `DOC`

- **ตรวจอะไร:** รวบผลจากข้อ 027–033 ออกมาเป็นรายการเดียวของ "ข้อมูลที่โบรกขอจริงแต่ไม่ได้ประกาศไว้ในนโยบาย" จุดที่ต้องเปิดดูคือช่อง `ประกาศในนโยบายหรือไม่` ของทุกแถวใน `PII-SET` ตัวแปรที่ต้องบันทึกคือ จำนวนแถวที่มีสถานะถูกขอ · จำนวนแถวที่ไม่พบในนโยบาย · รายชื่อแถวที่ไม่พบ · ระดับความอ่อนไหวของแต่ละแถวที่ไม่พบ ข้อนี้เป็นส่วนต่างฝั่งที่โบรกเก็บเกินกว่าที่ประกาศ ซึ่งเป็นทิศทางที่กระทบลูกค้ามากกว่าอีกทิศทางหนึ่ง
- **ขั้นตอนการตรวจ:**
  1. เปิดตาราง `PII-SET` ที่เติมครบแล้ว จากข้อ 026–033
  2. กรองเฉพาะแถวที่ช่อง `ขั้นตอนที่ถูกขอ` ไม่ว่างเปล่า แล้วนับจำนวน
  3. กรองต่อเฉพาะแถวที่ช่อง `ประกาศในนโยบายหรือไม่` มีค่าว่า "ไม่พบ" แล้วนับจำนวนและคัดรายชื่อออกมา
  4. สำหรับแต่ละแถวที่ไม่พบ ให้ตรวจซ้ำด้วยการค้นในสำเนานโยบายอีกครั้งด้วยคำที่ต่างจากเดิมอย่างน้อย 2 คำ เพื่อกันการพลาด แล้วบันทึกคำที่ใช้ค้น
  5. จัดระดับความอ่อนไหวของแต่ละแถวที่ยังไม่พบเป็นสามระดับ คือ ข้อมูลชีวมิติและเอกสารแสดงตน · ข้อมูลการเงิน · ข้อมูลติดต่อทั่วไป
  6. จับภาพช่องกรอกหรือหน้าจอที่ขอข้อมูลของทุกแถวที่ยังไม่พบ เป็นหลักฐานยืนยันว่าถูกขอจริง
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกตารางส่วนต่าง ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางรายการที่ถูกขอแต่ไม่ประกาศ (`RST-BRKA-P10-034-01`) · ภาพช่องกรอกของทุกรายการในตาราง ฉบับ `-RED` (`-02` เป็นต้นไป) · รายการคำที่ใช้ค้นซ้ำ
- **ผ่าน:** ไม่มีแถวใดที่ถูกขอจริงแล้วค้นในนโยบายด้วยคำตรงและคำต่างอีก 2 คำแล้วยังไม่พบ
- **ไม่ผ่าน:** มีอย่างน้อย 1 แถวที่ถูกขอจริงแต่ค้นซ้ำแล้วยังไม่พบในนโยบาย
- **ยังไม่ได้ตรวจ:** ยังเติม `PII-SET` ไม่ครบตามข้อ 026
- **ตัวอย่าง:** ผู้ตรวจ Broker A พบ 3 แถวที่ถูกขอแต่ไม่ประกาศ ได้แก่ วิดีโอยืนยันตัวตน ชื่อนายจ้าง และข้อมูลอุปกรณ์ โดยค้นซ้ำด้วยคำต่างอีก 2 คำต่อแถวแล้วยังไม่พบ → **ไม่ผ่าน**

**P10-035 · ประเภทข้อมูลที่ประกาศไว้แต่ไม่เคยถูกขอจริง** `w1` `DOC`

- **ตรวจอะไร:** ตรวจส่วนต่างอีกทิศทางหนึ่ง คือประเภทข้อมูลที่นโยบายประกาศว่าเก็บ แต่ตลอดเส้นทางลูกค้าไม่เคยถูกขอเลย จุดที่ต้องเปิดดูคือรายการประเภทข้อมูลจากข้อ 012 เทียบกับ `PII-SET` ตัวแปรที่ต้องบันทึกคือ จำนวนประเภทที่ประกาศ · จำนวนที่ไม่เคยถูกขอ · รายชื่อประเภทที่ไม่เคยถูกขอ · นโยบายระบุหรือไม่ว่าประเภทเหล่านั้นเก็บในกรณีใด ส่วนต่างทิศทางนี้ไม่ได้แปลว่าโบรกทำผิด แต่ถ้ามีมากเกินไปแสดงว่านโยบายเขียนกว้างเผื่อไว้จนไม่สะท้อนการเก็บจริง
- **ขั้นตอนการตรวจ:**
  1. เปิดรายการประเภทข้อมูลที่คัดลอกจากนโยบายในข้อ 012 แล้วนับจำนวนทั้งหมด
  2. ไล่ทีละประเภท แล้วค้นใน `PII-SET` ว่ามีแถวใดที่มีสถานะถูกขอและตรงกับประเภทนั้นหรือไม่
  3. คัดรายชื่อประเภทที่ไม่มีแถวใดตรงเลย ออกมาเป็นรายการแยก
  4. สำหรับแต่ละประเภทในรายการนั้น ให้อ่านข้อความในนโยบายว่าระบุเงื่อนไขการเก็บหรือไม่ เช่น เก็บเฉพาะเมื่อใช้บริการบางอย่าง แล้วบันทึกคำต่อคำ
  5. คำนวณอัตราส่วนของประเภทที่ไม่เคยถูกขอ ต่อจำนวนประเภทที่ประกาศทั้งหมด เป็นร้อยละ
  6. บันทึกว่าผู้ตรวจได้ใช้บริการครบทุกส่วนที่นโยบายอ้างถึงหรือไม่ เพราะบางประเภทอาจถูกขอเฉพาะบริการที่ยังไม่ได้ใช้
  7. บันทึกตารางส่วนต่างทิศทางนี้ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางประเภทที่ประกาศแต่ไม่เคยถูกขอ (`RST-BRKA-P10-035-01`) · ข้อความเงื่อนไขการเก็บคำต่อคำ · บันทึกบริการที่ผู้ตรวจใช้และยังไม่ได้ใช้
- **ผ่าน:** ทุกประเภทที่ประกาศแต่ไม่เคยถูกขอ มีข้อความในนโยบายระบุเงื่อนไขว่าเก็บในกรณีใด
- **ไม่ผ่าน:** มีประเภทที่ประกาศแต่ไม่เคยถูกขออย่างน้อย 1 ประเภท ที่นโยบายไม่ระบุเงื่อนไขใดเลยว่าจะเก็บเมื่อใด
- **ยังไม่ได้ตรวจ:** นโยบายไม่ระบุประเภทข้อมูลตามข้อ 012 จึงไม่มีสิ่งให้เทียบ
- **ตัวอย่าง:** Broker C ประกาศว่าเก็บข้อมูลการบันทึกเสียงสนทนา ซึ่งผู้ตรวจไม่เคยถูกขอ แต่นโยบายระบุชัดว่าเก็บเฉพาะเมื่อลูกค้าติดต่อทางโทรศัพท์ → **ผ่าน**

**P10-036 ● · ข้อมูลที่ถูกขอเกินความจำเป็นต่อการเปิดบัญชีหรือไม่** `w3` `ACC+DOC`

- **ตรวจอะไร:** ตรวจว่ามีข้อมูลใดที่โบรกบังคับให้ให้ ทั้งที่ไม่จำเป็นต่อการเปิดบัญชีและการปฏิบัติตามกฎหมายหรือไม่ จุดที่ต้องเปิดดูคือแถวใน `PII-SET` ที่มีสถานะบังคับ ตัวแปรที่ต้องบันทึกคือ จำนวนแถวที่บังคับ · แถวใดที่เหตุผลที่โบรกอ้างไม่โยงกับการเปิดบัญชีหรือกฎหมาย · แถวใดที่โบรกไม่ให้เหตุผลใดเลย · เทียบจำนวนช่องบังคับกับโบรกอื่นในชุดตรวจเดียวกัน การตัดสินต้องอิงเหตุผลที่โบรกให้ไว้เอง **ห้ามตัดสินจากความเห็นส่วนตัวของผู้ตรวจ**
- **ขั้นตอนการตรวจ:**
  1. เปิดตาราง `PII-SET` แล้วกรองเฉพาะแถวที่ช่อง `บังคับหรือไม่` มีค่าว่า "บังคับ" นับจำนวน
  2. ไล่ทีละแถว แล้วอ่านช่อง `เหตุผลที่โบรกอ้าง` บันทึกว่าเหตุผลนั้นโยงกับการเปิดบัญชี การปฏิบัติตามกฎหมาย หรือไม่โยงกับสิ่งใดเลย
  3. สำหรับแถวที่ไม่มีคำอธิบาย ให้ค้นในนโยบายและในหน้าคำถามที่พบบ่อยว่ามีคำอธิบายที่อื่นหรือไม่ บันทึกผล
  4. ติดต่อฝ่ายบริการลูกค้าในฐานะลูกค้าที่สงสัย ถามเหตุผลของช่องบังคับที่ไม่มีคำอธิบาย **ห้ามบอกว่าเป็นผู้ตรวจ** ถามครั้งละ 1 ช่อง ห่างกันครั้งละอย่างน้อย 24 ชั่วโมง รวมไม่เกิน 3 ช่องต่อโบรก
  5. บันทึกคำตอบที่ได้คำต่อคำ พร้อมวันเวลา UTC ที่ถามและที่ได้รับคำตอบ
  6. เทียบจำนวนช่องบังคับของโบรกรายนี้กับโบรกอื่นในชุดตรวจเดียวกัน แล้วบันทึกลำดับ
  7. ปิดบังข้อมูลส่วนตัวในภาพบทสนทนาเป็นฉบับ `-RED` แล้วบันทึกตารางผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางแถวบังคับพร้อมเหตุผลที่โบรกอ้าง (`RST-BRKA-P10-036-01`) · ภาพบทสนทนากับฝ่ายบริการ ฉบับ `-RED` (`-02` ถึง `-04`) · ตารางเทียบจำนวนช่องบังคับข้ามโบรก
- **ผ่าน:** ทุกแถวที่บังคับ มีเหตุผลที่โยงกับการเปิดบัญชีหรือการปฏิบัติตามกฎหมาย ไม่ว่าจะได้จากหน้าจอ จากนโยบาย หรือจากคำตอบของฝ่ายบริการ
- **ไม่ผ่าน:** มีอย่างน้อย 1 แถวที่บังคับ โดยไม่มีเหตุผลใดที่โยงกับการเปิดบัญชีหรือกฎหมาย ทั้งจากหน้าจอ จากนโยบาย และจากคำตอบของฝ่ายบริการ
- **ยังไม่ได้ตรวจ:** ยังเติมช่อง `บังคับหรือไม่` ใน `PII-SET` ไม่ครบตามข้อ 037
- **ตัวอย่าง:** Broker B บังคับกรอกชื่อนายจ้างและตำแหน่งงานเพื่อเปิดบัญชี ไม่มีคำอธิบายบนหน้าจอ ไม่มีในนโยบาย และฝ่ายบริการตอบเพียงว่าเป็นข้อกำหนดของระบบ → **ไม่ผ่าน**

**P10-037 ● · ช่องที่บังคับกรอกจริงเทียบกับที่นโยบายบอกว่าไม่บังคับ** `w3` `ACC+WEB`

- **ตรวจอะไร:** ตรวจว่าช่องใดบังคับกรอกจริงบนหน้าจอ และตรงกับที่นโยบายหรือข้อความบนหน้าจอบอกไว้หรือไม่ จุดที่ต้องเปิดดูคือแบบฟอร์มทุกหน้าที่มีช่องกรอก ตัวแปรที่ต้องบันทึกคือ ช่องที่มีเครื่องหมายบังคับ · ช่องที่ไม่มีเครื่องหมายแต่ระบบไม่ให้ผ่านเมื่อเว้นว่าง · ข้อความแจ้งเตือนที่ระบบแสดงเมื่อเว้นว่าง · นโยบายหรือหน้าจอระบุว่าช่องใดไม่บังคับ การทดสอบต้องทำด้วยการเว้นช่องแล้วกดถัดไปตามปกติเท่านั้น **ห้ามแก้ค่าที่ส่งออกจากเบราว์เซอร์ ห้ามใช้เครื่องมือใดนอกจากการกรอกตามหน้าจอ**
- **ขั้นตอนการตรวจ:**
  1. เปิดแบบฟอร์มสมัครหน้าแรก จับภาพเต็มหน้าก่อนกรอก แล้วบันทึกทุกช่องที่มีเครื่องหมายบังคับกำกับ
  2. กรอกเฉพาะช่องที่มีเครื่องหมายบังคับ เว้นช่องที่ไม่มีเครื่องหมายไว้ทั้งหมด แล้วกดถัดไปหนึ่งครั้ง
  3. บันทึกว่าระบบยอมให้ผ่านหรือไม่ ถ้าไม่ยอม ให้บันทึกชื่อช่องที่ระบบเรียกร้องและข้อความแจ้งเตือนคำต่อคำ พร้อมจับภาพ
  4. กรอกเพิ่มเฉพาะช่องที่ระบบเรียกร้อง แล้วกดถัดไปอีกครั้ง ทำซ้ำขั้นนี้ได้ไม่เกิน 3 รอบต่อหนึ่งหน้าจอ เพื่อไม่ให้เป็นการยิงคำขอถี่ผิดปกติ
  5. ทำซ้ำขั้น 1–4 กับทุกหน้าจอของแบบฟอร์มจนจบขั้นตอนสมัคร โดยเว้นระยะระหว่างหน้าจออย่างน้อย 60 วินาที
  6. เติมช่อง `บังคับหรือไม่` ของทุกแถวใน `PII-SET` ตามผลการทดสอบจริง ไม่ใช่ตามเครื่องหมายบนหน้าจอ
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกตารางเทียบเครื่องหมายกับผลจริง ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพทุกหน้าจอก่อนกรอกและภาพข้อความแจ้งเตือนทุกครั้ง ฉบับ `-RED` (`RST-BRKA-P10-037-01` เป็นต้นไป) · ตารางเทียบเครื่องหมายบังคับกับผลการทดสอบจริง · `PII-SET` ที่เติมช่องบังคับครบ
- **ผ่าน:** ช่องที่ระบบบังคับจริงตรงกับช่องที่มีเครื่องหมายบังคับกำกับทุกช่อง
- **ไม่ผ่าน:** มีอย่างน้อย 1 ช่องที่ไม่มีเครื่องหมายบังคับ หรือที่หน้าจอหรือนโยบายบอกว่าไม่บังคับ แต่ระบบไม่ให้ผ่านเมื่อเว้นว่าง
- **ยังไม่ได้ตรวจ:** ยังไม่ได้เริ่มขั้นตอนสมัครกับโบรกรายนี้
- **ตัวอย่าง:** Broker A มีช่องหมายเลขโทรศัพท์ที่ไม่มีเครื่องหมายบังคับและเขียนกำกับว่าไม่จำเป็น แต่เว้นว่างแล้วระบบขึ้นข้อความว่าต้องกรอกจึงจะดำเนินการต่อได้ → **ไม่ผ่าน**

**P10-038 · การกรอกน้อยที่สุดเท่าที่ระบบยอมรับ ทำได้จริงหรือไม่** `w2` `ACC`

- **ตรวจอะไร:** ตรวจว่าลูกค้าที่ต้องการให้ข้อมูลน้อยที่สุด เปิดบัญชีและใช้งานพื้นฐานได้จริงหรือไม่ จุดที่ต้องเปิดดูคือผลลัพธ์ของบัญชีที่กรอกเฉพาะช่องบังคับตามข้อ 037 ตัวแปรที่ต้องบันทึกคือ บัญชีเปิดสำเร็จหรือไม่ · ฟังก์ชันใดถูกจำกัดเมื่อไม่ให้ข้อมูลที่ไม่บังคับ · ระบบทวงถามข้อมูลที่ไม่บังคับซ้ำกี่ครั้งและด้วยวิธีใด · การทวงถามนั้นปิดได้หรือไม่ ข้อนี้ต่างจากข้อ 037 ที่ตรวจการบังคับ ณ จุดกรอก ข้อนี้ตรวจผลที่ตามมาหลังเลือกไม่ให้ข้อมูลที่ไม่บังคับ
- **ขั้นตอนการตรวจ:**
  1. เปิดบัญชีโดยกรอกเฉพาะช่องที่ผลข้อ 037 ระบุว่าบังคับจริง แล้วบันทึกว่าเปิดสำเร็จหรือไม่
  2. บันทึกรายการฟังก์ชันพื้นฐานที่ทดสอบได้ ได้แก่ เข้าสู่ระบบ · ดูราคา · ฝากเงิน · ส่งคำสั่ง · ถอนเงิน แล้วทดสอบทีละอย่าง
  3. บันทึกว่าฟังก์ชันใดถูกจำกัด พร้อมข้อความที่ระบบแสดงคำต่อคำ และจับภาพ
  4. นับจำนวนครั้งที่ระบบทวงถามข้อมูลที่ไม่บังคับ ตลอด 30 วันแรกหลังเปิดบัญชี โดยตรวจกล่องข้อความ อีเมล และแจ้งเตือนในบัญชี สัปดาห์ละ 1 ครั้ง รวม 4 ครั้ง
  5. บันทึกช่องทางที่ใช้ทวงถามแต่ละครั้ง และบันทึกว่ามีปุ่มปิดหรือข้ามได้หรือไม่
  6. ทดสอบกดปิดหรือข้ามการทวงถาม 1 ครั้ง แล้วบันทึกว่าการทวงถามหยุดหรือกลับมาอีก
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกตารางผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพผลการเปิดบัญชี ฉบับ `-RED` (`RST-BRKA-P10-038-01`) · ภาพข้อความจำกัดฟังก์ชันทุกจุด (`-02` เป็นต้นไป) · ตารางนับจำนวนครั้งการทวงถาม 4 รอบ
- **ผ่าน:** เปิดบัญชีและใช้ฟังก์ชันพื้นฐานได้ทั้ง 5 อย่างโดยไม่ต้องให้ข้อมูลที่ไม่บังคับ และการทวงถามมีปุ่มปิดหรือข้ามได้
- **ไม่ผ่าน:** มีฟังก์ชันพื้นฐานอย่างน้อย 1 อย่างที่ใช้ไม่ได้จนกว่าจะให้ข้อมูลที่ระบบเองระบุว่าไม่บังคับ หรือการทวงถามไม่มีทางปิดและกลับมาซ้ำทุกครั้งที่เข้าสู่ระบบ
- **ยังไม่ได้ตรวจ:** ยังเปิดบัญชีไม่สำเร็จด้วยสาเหตุอื่นที่ไม่เกี่ยวกับข้อมูลที่ไม่บังคับ
- **ตัวอย่าง:** Broker C ให้เปิดบัญชีได้โดยไม่กรอกรายได้ แต่ปุ่มฝากเงินถูกปิดพร้อมข้อความว่าต้องกรอกข้อมูลรายได้ก่อน ทั้งที่ช่องนั้นระบุว่าไม่บังคับ → **ไม่ผ่าน**

**P10-039 · การขอเอกสารเพิ่มหลังเปิดบัญชีแล้ว และเหตุผลที่ให้** `w2` `ACC+SUP`

- **ตรวจอะไร:** ตรวจว่าโบรกขอข้อมูลหรือเอกสารเพิ่มหลังเปิดบัญชีสำเร็จแล้วหรือไม่ และให้เหตุผลอย่างไร จุดที่ต้องเปิดดูคือกล่องข้อความในบัญชี อีเมล และหน้าจอที่ถูกกั้นระหว่างใช้งาน ตัวแปรที่ต้องบันทึกคือ จำนวนครั้งที่ถูกขอเพิ่มใน 90 วันแรก · สิ่งที่ถูกขอแต่ละครั้ง · เหตุผลที่โบรกให้คำต่อคำ · การขอนั้นเกิดพร้อมกับการกั้นฟังก์ชันใดหรือไม่ · กำหนดเวลาที่โบรกให้ส่ง · ผลถ้าไม่ส่ง **ข้อนี้ไม่ตรวจซ้ำเรื่องการกั้นการถอนเงินซึ่งอยู่ในเสาอื่น** ข้อนี้ตรวจเฉพาะมิติของการเก็บข้อมูลเพิ่มและการประกาศ
- **ขั้นตอนการตรวจ:**
  1. ตรวจกล่องข้อความในบัญชี อีเมล และแจ้งเตือน สัปดาห์ละ 1 ครั้ง รวม 13 สัปดาห์ นับจากวันเปิดบัญชี
  2. บันทึกทุกครั้งที่โบรกขอข้อมูลหรือเอกสารเพิ่ม พร้อมวันเวลา UTC และช่องทางที่ใช้ขอ
  3. คัดลอกข้อความที่โบรกใช้ขอทุกฉบับคำต่อคำ พร้อมเหตุผลที่ให้ ถ้าไม่ให้เหตุผลให้เขียนว่า "ไม่ให้เหตุผล"
  4. บันทึกว่าการขอครั้งนั้นมาพร้อมกับการกั้นฟังก์ชันใดหรือไม่ และกั้นตั้งแต่เมื่อใด
  5. บันทึกกำหนดเวลาที่โบรกให้ส่ง และข้อความที่ระบุผลถ้าไม่ส่งภายในกำหนด
  6. ค้นในสำเนานโยบายและในทะเบียนเอกสารจาก `p07-01` ว่ามีข้อความรองรับการขอเอกสารเพิ่มภายหลังหรือไม่ บันทึกผล
  7. เพิ่มแถวใหม่ใน `PII-SET` สำหรับทุกสิ่งที่ถูกขอเพิ่ม แล้วปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพข้อความขอเอกสารเพิ่มทุกฉบับ ฉบับ `-RED` (`RST-BRKA-P10-039-01` เป็นต้นไป) · ตารางบันทึก 13 สัปดาห์ · แถวใหม่ใน `PII-SET` · ข้อความรองรับในนโยบายถ้ามี
- **ผ่าน:** ทุกครั้งที่ขอเพิ่ม โบรกให้เหตุผลที่ระบุได้ และมีข้อความรองรับการขอเพิ่มภายหลังในนโยบายหรือในเอกสารสัญญา
- **ไม่ผ่าน:** มีการขอเพิ่มอย่างน้อย 1 ครั้งที่ไม่ให้เหตุผลใด หรือไม่มีข้อความรองรับการขอเพิ่มภายหลังทั้งในนโยบายและในเอกสารสัญญา
- **ยังไม่ได้ตรวจ:** ยังเปิดบัญชีไม่ครบ 90 วัน จึงยังนับไม่ครบ 13 สัปดาห์
- **ตัวอย่าง:** Broker A ส่งข้อความในวันที่ 46 ขอรายการเดินบัญชีย้อนหลัง 6 เดือน โดยระบุเหตุผลว่าเป็นการทบทวนข้อมูลลูกค้าตามกฎหมายป้องกันการฟอกเงิน และนโยบายมีข้อความรองรับการขอเอกสารเพิ่มเป็นระยะ → **ผ่าน**

**P10-040 ● · ช่องทางที่ใช้ส่งเอกสาร ปลอดภัยหรือให้ส่งทางอีเมลธรรมดา** `w3` `ACC+SUP`

- **ตรวจอะไร:** ตรวจว่าโบรกให้ส่งเอกสารที่มีข้อมูลส่วนบุคคลผ่านช่องทางใด และช่องทางนั้นเหมาะสมหรือไม่ จุดที่ต้องเปิดดูคือหน้าจออัปโหลดในบัญชี และข้อความที่ฝ่ายบริการใช้ขอเอกสาร ตัวแปรที่ต้องบันทึกคือ ช่องทางที่โบรกกำหนด · ที่อยู่เว็บของหน้าอัปโหลดขึ้นต้นด้วยการเชื่อมต่อที่เข้ารหัสหรือไม่ · โบรกแนะนำให้ส่งทางอีเมลธรรมดาหรือไม่ · โบรกขอให้ส่งผ่านแอปข้อความของบุคคลที่สามหรือไม่ · มีคำแนะนำเรื่องการปิดบังข้อมูลส่วนเกินหรือไม่ **ให้ใช้เพียงเครื่องมือมาตรฐานของเบราว์เซอร์ในการอ่านสถานะการเชื่อมต่อ ห้ามทดสอบช่องโหว่ใด**
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้าอัปโหลดเอกสารในบัญชี จับภาพให้เห็นแถบที่อยู่เว็บและสัญลักษณ์สถานะการเชื่อมต่อ
  2. กดที่สัญลักษณ์สถานะการเชื่อมต่อของเบราว์เซอร์ แล้วจับภาพหน้าต่างที่แสดงว่าการเชื่อมต่อเข้ารหัสหรือไม่
  3. อ่านข้อความทุกฉบับที่โบรกใช้ขอเอกสาร แล้วบันทึกช่องทางที่โบรกระบุให้ใช้ คำต่อคำ
  4. บันทึกว่ามีข้อความใดแนะนำหรือยอมรับการส่งทางอีเมลธรรมดาหรือทางแอปข้อความของบุคคลที่สามหรือไม่ พร้อมยกข้อความมา
  5. ถามฝ่ายบริการในฐานะลูกค้าว่ามีช่องทางส่งเอกสารที่ปลอดภัยกว่าอีเมลหรือไม่ ถาม 1 ครั้ง แล้วบันทึกคำตอบคำต่อคำพร้อมวันเวลา UTC
  6. บันทึกว่าหน้าอัปโหลดหรือข้อความมีคำแนะนำให้ปิดบังข้อมูลส่วนเกินก่อนส่งหรือไม่
  7. ปิดบังข้อมูลส่วนตัวในภาพเป็นฉบับ `-RED` แล้วบันทึกตารางช่องทาง ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าอัปโหลดที่เห็นแถบที่อยู่เว็บและสถานะการเชื่อมต่อ (`RST-BRKA-P10-040-01`, `-02`) · ข้อความขอเอกสารคำต่อคำ · ภาพบทสนทนากับฝ่ายบริการ ฉบับ `-RED` (`-03`)
- **ผ่าน:** โบรกมีหน้าอัปโหลดในบัญชีที่ใช้การเชื่อมต่อแบบเข้ารหัส และไม่มีข้อความใดแนะนำหรือยอมรับการส่งเอกสารทางอีเมลธรรมดาหรือแอปข้อความของบุคคลที่สาม
- **ไม่ผ่าน:** ไม่มีหน้าอัปโหลดในบัญชี หรือมีแต่โบรกแนะนำหรือยอมรับให้ส่งเอกสารทางอีเมลธรรมดาหรือแอปข้อความของบุคคลที่สาม
- **ยังไม่ได้ตรวจ:** โบรกยังไม่เคยขอเอกสารใดจากผู้ตรวจ จึงยังไม่มีช่องทางให้ตรวจ
- **ตัวอย่าง:** Broker B มีหน้าอัปโหลดในบัญชีที่เชื่อมต่อแบบเข้ารหัส แต่ฝ่ายบริการส่งข้อความว่าให้ถ่ายรูปหนังสือเดินทางส่งกลับมาทางอีเมลได้เลยเพื่อความรวดเร็ว → **ไม่ผ่าน**

**P10-041 · เอกสารที่อัปโหลดแล้ว ยังแสดงย้อนหลังในบัญชีหรือไม่** `w2` `ACC`

- **ตรวจอะไร:** ตรวจว่าหลังอัปโหลดเอกสารแสดงตนและเอกสารยืนยันที่อยู่แล้ว ระบบยังเปิดให้ดูภาพเอกสารเหล่านั้นย้อนหลังในบัญชีหรือไม่ และแสดงแบบใด จุดที่ต้องเปิดดูคือหน้าประวัติเอกสารหรือหน้าโปรไฟล์ในบัญชี ตัวแปรที่ต้องบันทึกคือ เปิดดูย้อนหลังได้หรือไม่ · แสดงเป็นภาพเต็มหรือแสดงเพียงชื่อไฟล์และสถานะ · ดาวน์โหลดกลับได้หรือไม่ · ต้องยืนยันตัวตนซ้ำก่อนดูหรือไม่ การแสดงภาพเอกสารเต็มโดยไม่ยืนยันตัวตนซ้ำ ทำให้ผู้ที่เข้าถึงหน้าจอของลูกค้าได้ชั่วคราวเห็นเอกสารทั้งฉบับ
- **ขั้นตอนการตรวจ:**
  1. เข้าสู่ระบบบัญชีตามปกติ แล้วเปิดหน้าโปรไฟล์และหน้าประวัติเอกสาร
  2. บันทึกว่ามีรายการเอกสารที่เคยอัปโหลดปรากฏหรือไม่ และแสดงข้อมูลใดบ้าง
  3. กดที่รายการเอกสารหนึ่งรายการ แล้วบันทึกว่าระบบแสดงภาพเอกสารเต็ม แสดงภาพย่อ หรือแสดงเพียงสถานะ จับภาพหน้าจอโดย **ปิดบังเอกสารก่อนบันทึกเป็นหลักฐาน**
  4. บันทึกว่าระบบขอให้ยืนยันตัวตนซ้ำก่อนแสดงภาพหรือไม่ ถ้าขอ ให้บันทึกวิธีที่ใช้
  5. ตรวจว่ามีปุ่มดาวน์โหลดเอกสารกลับหรือไม่ ถ้ามีให้บันทึกไว้ **โดยไม่ต้องกดดาวน์โหลด**
  6. ออกจากระบบแล้วเข้าใหม่จากอุปกรณ์อื่นที่เป็นของผู้ตรวจเอง แล้วทำซ้ำขั้น 1–4 บันทึกว่าผลต่างกันหรือไม่
  7. เก็บภาพฉบับ `-RED` เท่านั้นในชุดหลักฐาน **ห้ามเก็บภาพเอกสารจริงในข้อนี้** แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพหน้าประวัติเอกสาร ฉบับ `-RED` (`RST-BRKA-P10-041-01`) · ภาพหน้าจอเมื่อกดดูรายการ ฉบับ `-RED` (`-02`) · บันทึกผลจากอุปกรณ์ที่สอง
- **ผ่าน:** ระบบไม่แสดงภาพเอกสารเต็มย้อนหลัง หรือแสดงแต่ขอให้ยืนยันตัวตนซ้ำก่อนทุกครั้ง
- **ไม่ผ่าน:** ระบบแสดงภาพเอกสารแสดงตนเต็มย้อนหลังได้ทันทีหลังเข้าสู่ระบบ โดยไม่ขอยืนยันตัวตนซ้ำ
- **ยังไม่ได้ตรวจ:** ยังไม่เคยอัปโหลดเอกสารใดเข้าบัญชี
- **ตัวอย่าง:** Broker C แสดงเพียงชื่อไฟล์กับสถานะว่าอนุมัติแล้ว กดแล้วไม่เปิดภาพใด และไม่มีปุ่มดาวน์โหลด → **ผ่าน**

**P10-042 · การเก็บข้อมูลอุปกรณ์และการแจ้งล่วงหน้า** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่าเว็บและแอปของโบรกเก็บข้อมูลอุปกรณ์หรือไม่ และแจ้งไว้ในนโยบายหรือไม่ จุดที่ต้องเปิดดูคือเครื่องมือมาตรฐานของเบราว์เซอร์ที่แสดงสิ่งที่หน้าเว็บส่งกลับไป และหัวข้อข้อมูลอุปกรณ์ในนโยบาย ตัวแปรที่ต้องบันทึกคือ พบการเก็บข้อมูลอุปกรณ์หรือไม่ · ชนิดข้อมูลที่เห็นได้ (ชนิดเบราว์เซอร์ · ระบบปฏิบัติการ · ขนาดหน้าจอ · เขตเวลา) · นโยบายกล่าวถึงข้อมูลอุปกรณ์หรือไม่ **ให้อ่านเฉพาะสิ่งที่เครื่องมือมาตรฐานของเบราว์เซอร์แสดงบนเครื่องของผู้ตรวจเอง ห้ามแก้ค่าใด ห้ามส่งคำขอเอง ห้ามใช้เครื่องมือสแกน**
- **ขั้นตอนการตรวจ:**
  1. เปิดเบราว์เซอร์โหมดไม่บันทึกประวัติ ล้างข้อมูลเว็บก่อนเริ่ม แล้วเปิดเครื่องมือมาตรฐานของเบราว์เซอร์ที่หน้าแท็บบันทึกการเชื่อมต่อ
  2. เข้าหน้าแรกของโบรกโดยพิมพ์โดเมนเอง แล้วปล่อยให้หน้าโหลดจนจบโดยไม่กดสิ่งใด
  3. บันทึกรายการปลายทางที่หน้าเว็บติดต่อไปทั้งหมด โดยอ่านจากแท็บบันทึกการเชื่อมต่อ จับภาพทั้งรายการ
  4. เปิดแท็บที่เก็บข้อมูลในเครื่อง แล้วบันทึกรายการค่าที่ถูกเก็บลงเครื่องของผู้ตรวจ พร้อมชื่อค่าและอายุ
  5. บันทึกชนิดข้อมูลอุปกรณ์ที่ระบุได้จากรายการที่เห็น เช่น ขนาดหน้าจอ เขตเวลา ชนิดเบราว์เซอร์ **โดยไม่พยายามอ่านค่าที่ไม่ได้แสดงอยู่แล้ว**
  6. ค้นในสำเนานโยบายด้วยคำว่า `device` · `browser` · `IP address` · `อุปกรณ์` · `เบราว์เซอร์` · `หมายเลขไอพี` ทีละคำ บันทึกผล
  7. เติมแถว `PII-14` ของ `PII-SET` แล้วบันทึกตารางเทียบสิ่งที่พบกับสิ่งที่ประกาศ ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพรายการปลายทางที่หน้าเว็บติดต่อ (`RST-BRKA-P10-042-01`) · ภาพรายการค่าที่ถูกเก็บลงเครื่อง (`-02`) · แถว `PII-14` ที่เติมครบ · ข้อความในนโยบายคำต่อคำ
- **ผ่าน:** นโยบายกล่าวถึงการเก็บข้อมูลอุปกรณ์และระบุชนิดข้อมูลที่เก็บ ครอบคลุมชนิดที่ผู้ตรวจพบจากเครื่องมือมาตรฐานของเบราว์เซอร์
- **ไม่ผ่าน:** พบการเก็บข้อมูลอุปกรณ์ แต่นโยบายไม่กล่าวถึงเลย หรือกล่าวถึงกว้าง ๆ โดยไม่ระบุชนิดข้อมูลใด
- **ยังไม่ได้ตรวจ:** เว็บของโบรกเข้าไม่ได้ตลอดช่วงที่พยายามเข้า 3 รอบ ห่างกันรอบละ 24 ชั่วโมง
- **ตัวอย่าง:** Broker A เก็บค่าที่ระบุชนิดเบราว์เซอร์และเขตเวลาไว้ในเครื่องผู้ตรวจ แต่นโยบายไม่มีคำว่าอุปกรณ์หรือเบราว์เซอร์เลยทั้งฉบับ → **ไม่ผ่าน**

**P10-043 · การเก็บข้อมูลตำแหน่งที่ตั้งและการขอสิทธิ์บนแอปมือถือ** `w2` `WEB+PLT`

- **ตรวจอะไร:** ตรวจว่าโบรกเก็บข้อมูลตำแหน่งที่ตั้งของลูกค้าหรือไม่ ทั้งจากหมายเลขไอพีบนเว็บ และจากการขอสิทธิ์ตำแหน่งบนแอปมือถือ และแจ้งไว้หรือไม่ จุดที่ต้องเปิดดูคือหน้าจอขอสิทธิ์ของแอปมือถือ และรายการสิทธิ์ที่แอปประกาศในร้านค้าแอป ตัวแปรที่ต้องบันทึกคือ แอปขอสิทธิ์ตำแหน่งหรือไม่ · ขอที่ขั้นตอนใด · เป็นสิทธิ์แบบขณะใช้งานหรือแบบตลอดเวลา · ปฏิเสธแล้วแอปยังใช้งานได้หรือไม่ · นโยบายกล่าวถึงข้อมูลตำแหน่งหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้ารายการแอปของโบรกในร้านค้าแอป แล้วจับภาพรายการสิทธิ์ที่แอปประกาศทั้งหมด
  2. ติดตั้งแอปบนอุปกรณ์ของผู้ตรวจเอง แล้วเปิดครั้งแรกโดยยังไม่เข้าสู่ระบบ จับภาพทุกหน้าจอขอสิทธิ์ที่ปรากฏ
  3. บันทึกว่าแอปขอสิทธิ์ตำแหน่งหรือไม่ ขอที่ขั้นตอนใด และเป็นสิทธิ์แบบใด

**P10-044 ● · คุกกี้และตัวติดตามบนเว็บเทียบกับที่ประกาศ** `w3` `WEB`

  2. เปิดเครื่องมือมาตรฐานของเบราว์เซอร์ที่แท็บข้อมูลที่เก็บในเครื่อง แล้วยืนยันว่ารายการว่างเปล่าก่อนเข้าเว็บ จับภาพ
  3. เข้าหน้าแรกของโบรกโดยพิมพ์โดเมนเอง **โดยยังไม่กดแบนเนอร์ใด** รอจนหน้าโหลดจบ แล้วจับภาพรายการคุกกี้ทั้งหมดที่ถูกวาง

  5. เปิดหน้ารายการคุกกี้ที่โบรกประกาศ (นโยบายคุกกี้หรือตารางในแบนเนอร์) แล้วคัดรายการที่ประกาศทั้งหมดมาไว้คู่กัน

- **หลักฐานที่ต้องเก็บ:** ภาพรายการว่างเปล่าก่อนเข้าเว็บ (`RST-BRKA-P10-044-01`) · ภาพรายการคุกกี้หลังโหลดหน้าแรก ทั้งสองรอบ (`-02`, `-03`) · ตารางเทียบคุกกี้ที่พบกับที่ประกาศ · รายการคุกกี้ที่โบรกประกาศ
- **ผ่าน:** คุกกี้ทุกรายการที่พบในทั้งสองรอบ มีรายการรองรับในสิ่งที่โบรกประกาศไว้
- **ไม่ผ่าน:** มีคุกกี้อย่างน้อย 1 รายการที่พบในทั้งสองรอบแต่ไม่ปรากฏในรายการที่ประกาศ หรือโบรกไม่ประกาศรายการคุกกี้ใดเลยทั้งที่วางคุกกี้จริง

**P10-045 · คุกกี้ของบุคคลที่สามที่ถูกวางก่อนกดยอมรับ** `w3` `WEB`

  4. บันทึกทีละรายการว่าเป็นของโดเมนโบรกเองหรือของโดเมนอื่น แล้วนับจำนวนแยกกัน
  5. เปิดรายการคุกกี้ที่โบรกประกาศ แล้วตรวจว่าโบรกจัดรายการที่พบในขั้น 4 เป็นคุกกี้จำเป็นหรือไม่ บันทึกผลทีละรายการ

  7. ทำซ้ำขั้น 1–6 อีก 1 รอบ ห่างจากรอบแรกอย่างน้อย 7 วัน แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพรายการคุกกี้ที่เห็นแบนเนอร์ยังไม่ถูกกดในเฟรมเดียวกัน ทั้งสองรอบ (`RST-BRKA-P10-045-01`, `-02`) · ตารางจำแนกคุกกี้จำเป็นกับไม่จำเป็น · ข้อความบนแบนเนอร์คำต่อคำ
- **ผ่าน:** คุกกี้ทุกรายการที่ถูกวางก่อนกดแบนเนอร์ เป็นรายการที่โบรกจัดเป็นคุกกี้จำเป็น และไม่มีคุกกี้ของโดเมนโฆษณาหรือโดเมนวิเคราะห์ภายนอกในจุดนี้

- **ตัวอย่าง:** Broker B มีปุ่มยอมรับทั้งหมดกดครั้งเดียวจบ แต่การปฏิเสธต้องกดเข้าหน้าตั้งค่า ปิดสวิตช์ทีละหมวด 4 หมวด แล้วกดบันทึก รวม 6 คลิก → **ไม่ผ่าน**

**P10-047 · การถอนความยินยอมคุกกี้ทำได้และมีผลจริงหรือไม่** `w2` `WEB`

- **ตรวจอะไร:** ตรวจว่าหลังยอมรับคุกกี้ไปแล้ว ลูกค้ากลับมาถอนความยินยอมได้หรือไม่ และการถอนนั้นมีผลจริงหรือไม่ จุดที่ต้องเปิดดูคือช่องทางกลับมาแก้ไขการตั้งค่าคุกกี้ และรายการคุกกี้หลังถอน ตัวแปรที่ต้องบันทึกคือ มีช่องทางกลับมาแก้ไขหรือไม่ · อยู่ที่ใดและกี่คลิกจากหน้าแรก · จำนวนคุกกี้ก่อนถอนและหลังถอน · คุกกี้ที่ยังค้างอยู่หลังถอน · หลังถอนแล้วแบนเนอร์กลับมาถามใหม่ทันทีหรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดเบราว์เซอร์โหมดไม่บันทึกประวัติหน้าต่างใหม่ ล้างข้อมูลเว็บ แล้วเข้าหน้าแรกและกดยอมรับคุกกี้ทั้งหมด
  2. จับภาพรายการคุกกี้ทั้งหมดหลังกดยอมรับ แล้วนับจำนวน
  3. ไล่หาช่องทางกลับมาแก้ไขการตั้งค่าคุกกี้ นับจำนวนคลิกจากหน้าแรก และบันทึกตำแหน่งที่พบ
  4. ถอนความยินยอมทุกหมวดที่ถอนได้ แล้วกดบันทึกการตั้งค่า จับภาพหน้าจอยืนยันการบันทึก
  5. โหลดหน้าแรกใหม่ 1 ครั้ง แล้วจับภาพรายการคุกกี้ทั้งหมดอีกครั้ง นับจำนวนและเทียบกับขั้น 2
  6. คัดรายการคุกกี้ที่ยังค้างอยู่หลังถอน แล้วตรวจว่าโบรกจัดเป็นคุกกี้จำเป็นหรือไม่
  7. รอ 24 ชั่วโมงแล้วเข้าเว็บอีกครั้ง บันทึกว่าการตั้งค่าที่ถอนไว้ยังคงอยู่หรือถูกล้างกลับ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพรายการคุกกี้ก่อนถอนและหลังถอน (`RST-BRKA-P10-047-01`, `-02`) · ภาพหน้าตั้งค่าคุกกี้และหน้าจอยืนยันการบันทึก (`-03`) · ภาพรายการคุกกี้หลังผ่านไป 24 ชั่วโมง (`-04`)
- **ผ่าน:** มีช่องทางกลับมาถอนความยินยอมที่เข้าถึงได้ภายใน 3 คลิกจากหน้าแรก และหลังถอนแล้วคุกกี้ที่ไม่จำเป็นถูกลบออกจริง และการตั้งค่ายังคงอยู่หลังผ่านไป 24 ชั่วโมง `[เกณฑ์เสนอ: 3 คลิก]`
- **ไม่ผ่าน:** ไม่มีช่องทางกลับมาถอน หรือถอนแล้วยังมีคุกกี้ที่ไม่จำเป็นค้างอยู่ หรือการตั้งค่าถูกล้างกลับภายใน 24 ชั่วโมง
- **ยังไม่ได้ตรวจ:** เว็บไม่แสดงแบนเนอร์ขอความยินยอมใดเลย จึงไม่มีความยินยอมให้ถอน
- **ตัวอย่าง:** Broker C มีลิงก์ตั้งค่าคุกกี้ที่ส่วนท้ายทุกหน้า ถอนแล้วคุกกี้ของโดเมนโฆษณาหายไปทั้งหมด และการตั้งค่ายังคงอยู่เมื่อกลับมาในวันถัดไป → **ผ่าน**

**P10-048 · นโยบายคุกกี้แยกฉบับและสอดคล้องกับนโยบายความเป็นส่วนตัวหรือไม่** `w1` `WEB+DOC`

- **ตรวจอะไร:** ตรวจว่าโบรกมีนโยบายคุกกี้แยกฉบับหรือไม่ และถ้ามี เนื้อหาขัดกับนโยบายความเป็นส่วนตัวหรือไม่ จุดที่ต้องเปิดดูคือหน้ารวมเอกสารกฎหมายและแบนเนอร์คุกกี้ ตัวแปรที่ต้องบันทึกคือ มีนโยบายคุกกี้แยกหรือไม่ · วันที่มีผลของสองฉบับตรงกันหรือไม่ · จำนวนหมวดคุกกี้ที่แต่ละฉบับระบุ · จุดที่ขัดกัน · นโยบายความเป็นส่วนตัวชี้ไปยังนโยบายคุกกี้หรือไม่
- **ขั้นตอนการตรวจ:**
  1. เปิดหน้ารวมเอกสารกฎหมาย แล้วค้นคำว่า `cookie` · `คุกกี้` บันทึกทุกเอกสารที่พบ
  2. เปิดนโยบายคุกกี้ที่พบ แล้วเก็บสำเนาถาวรพร้อมวันเวลา UTC ที่บันทึก
  3. บันทึกวันที่มีผลของนโยบายคุกกี้ แล้วเทียบกับวันที่มีผลของนโยบายความเป็นส่วนตัวจากข้อ 005 บันทึกส่วนต่างเป็นจำนวนวัน
  4. คัดหมวดคุกกี้ที่แต่ละฉบับระบุออกมาเป็นสองรายการวางคู่กัน แล้วนับจำนวนหมวดของแต่ละฉบับ
  5. เทียบเนื้อหาใน 3 ประเด็น ได้แก่ ชนิดคุกกี้ที่ใช้ · ระยะเวลาเก็บคุกกี้ · การส่งข้อมูลให้โดเมนอื่น บันทึกทุกจุดที่ขัดกัน
  6. ตรวจว่านโยบายความเป็นส่วนตัวมีลิงก์หรือข้อความชี้ไปยังนโยบายคุกกี้หรือไม่ และในทางกลับกันด้วย
  7. บันทึกตารางเทียบสองฉบับ แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** สำเนาถาวรของนโยบายคุกกี้ (`RST-BRKA-P10-048-01`) · ตารางเทียบหมวดคุกกี้สองฉบับ · ภาพจุดที่ขัดกันทุกจุด (`-02` เป็นต้นไป)
- **ผ่าน:** มีนโยบายคุกกี้ที่เนื้อหาไม่ขัดกับนโยบายความเป็นส่วนตัวใน 3 ประเด็นที่เทียบ และสองฉบับชี้ถึงกันอย่างน้อยทางเดียว
- **ไม่ผ่าน:** พบจุดขัดกันอย่างน้อย 1 จุดใน 3 ประเด็น หรือมีนโยบายคุกกี้แยกฉบับแต่ไม่มีฉบับใดชี้ถึงอีกฉบับเลย
- **ยังไม่ได้ตรวจ:** โบรกไม่มีนโยบายคุกกี้แยกฉบับ และเนื้อหาเรื่องคุกกี้อยู่รวมในนโยบายความเป็นส่วนตัว (ต้องบันทึกข้อเท็จจริงนี้ไว้ ห้ามตีความเป็นไม่ผ่าน)
- **ตัวอย่าง:** นโยบายคุกกี้ของ Broker A ระบุคุกกี้โฆษณาอายุ 24 เดือน แต่นโยบายความเป็นส่วนตัวระบุว่าไม่ใช้คุกกี้โฆษณาใดเลย → **ไม่ผ่าน**

**P10-049 · การขอข้อมูลผ่านแชทหรือโทรศัพท์ที่ไม่ผ่านแบบฟอร์ม** `w2` `SUP`

- **ตรวจอะไร:** ตรวจว่าเจ้าหน้าที่ของโบรกขอข้อมูลส่วนบุคคลผ่านช่องทางสนทนาโดยไม่ผ่านแบบฟอร์มของระบบหรือไม่ จุดที่ต้องเปิดดูคือบทสนทนาทุกครั้งกับฝ่ายบริการ ตัวแปรที่ต้องบันทึกคือ จำนวนครั้งที่ติดต่อ · จำนวนครั้งที่ถูกขอข้อมูลส่วนบุคคลในบทสนทนา · ชนิดข้อมูลที่ถูกขอ · ถูกขอเพื่อยืนยันตัวตนหรือเพื่อเก็บเพิ่ม · เจ้าหน้าที่ขอข้อมูลอ่อนไหวเช่นเลขเอกสารเต็มหรือรหัสผ่านหรือไม่ **เจ้าหน้าที่ที่ขอรหัสผ่านถือเป็นข้อบกพร่องร้ายแรงเสมอ ห้ามให้รหัสผ่านแก่ผู้ใดในทุกกรณี**
- **ขั้นตอนการตรวจ:**
  1. ติดต่อฝ่ายบริการผ่านช่องทางสนทนาในฐานะลูกค้าที่มีคำถามทั่วไป รวม 3 ครั้ง ห่างกันครั้งละอย่างน้อย 7 วัน
  2. บันทึกบทสนทนาทุกครั้งเป็นข้อความหรือภาพ พร้อมวันเวลา UTC ที่เริ่มและจบ
  3. บันทึกทุกครั้งที่เจ้าหน้าที่ขอข้อมูลส่วนบุคคล พร้อมชนิดข้อมูลและข้อความที่ใช้ขอ คำต่อคำ
  4. จำแนกว่าการขอแต่ละครั้งเป็นการยืนยันตัวตนเพื่อเข้าถึงบัญชี หรือเป็นการเก็บข้อมูลเพิ่มเติม
  5. บันทึกว่าเจ้าหน้าที่ขอข้อมูลอ่อนไหวใดหรือไม่ เช่น เลขเอกสารแสดงตนเต็ม เลขบัตร รหัสผ่าน รหัสยืนยันครั้งเดียว **ถ้าถูกขอรหัสผ่านหรือรหัสยืนยันครั้งเดียว ให้ปฏิเสธและบันทึกไว้ ห้ามให้เด็ดขาด**
  6. ตรวจว่าข้อมูลที่ถูกขอในบทสนทนา มีแถวรองรับใน `PII-SET` หรือไม่ ถ้าไม่มีให้เพิ่มแถวใหม่
  7. ปิดบังข้อมูลส่วนตัวในภาพบทสนทนาเป็นฉบับ `-RED` แล้วบันทึกตารางผล ตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ภาพบทสนทนาทั้ง 3 ครั้ง ฉบับ `-RED` (`RST-BRKA-P10-049-01` ถึง `-03`) · ตารางจำแนกการขอข้อมูลรายครั้ง · แถวใหม่ใน `PII-SET` ถ้ามี
- **ผ่าน:** ทุกครั้งที่เจ้าหน้าที่ขอข้อมูลในบทสนทนา เป็นการยืนยันตัวตนที่จำกัดเฉพาะข้อมูลเท่าที่จำเป็น และไม่มีครั้งใดที่ขอรหัสผ่านหรือรหัสยืนยันครั้งเดียว
- **ไม่ผ่าน:** มีอย่างน้อย 1 ครั้งที่เจ้าหน้าที่ขอรหัสผ่านหรือรหัสยืนยันครั้งเดียว หรือขอข้อมูลอ่อนไหวเพิ่มเติมในบทสนทนาโดยไม่เกี่ยวกับการยืนยันตัวตนและไม่มีแถวรองรับในสิ่งที่นโยบายประกาศ
- **ยังไม่ได้ตรวจ:** โบรกไม่มีช่องทางสนทนาใด ๆ ให้ติดต่อ
- **ตัวอย่าง:** เจ้าหน้าที่ของ Broker B ขอให้ผู้ตรวจอ่านรหัสยืนยันครั้งเดียวที่ส่งเข้าโทรศัพท์ให้ฟังเพื่อยืนยันตัวตน ผู้ตรวจปฏิเสธและบันทึกบทสนทนาไว้ → **ไม่ผ่าน**

**P10-050 ● · ข้อสรุปปิดหมวด — ตารางส่วนต่างระหว่างที่ประกาศกับที่เก็บจริง** `w3` `DOC`

- **ตรวจอะไร:** ตรวจว่าผู้ตรวจรวบผลข้อ 026–049 ออกมาเป็นตารางส่วนต่างชุดเดียวที่คำนวณซ้ำได้หรือไม่ ตารางนี้เป็นผลผลิตหลักของหมวด S02 และเป็นสิ่งที่ไฟล์อื่นในเสา P10 จะอ้างถึง จุดที่ต้องเปิดดูคือ `PII-SET` ฉบับสมบูรณ์และแบบฟอร์มบันทึกผลข้อ 026–049 ตัวแปรที่ต้องบันทึกคือ จำนวนแถวที่ถูกขอจริงทั้งหมด · จำนวนที่ประกาศ · จำนวนที่ถูกขอแต่ไม่ประกาศ · จำนวนที่ประกาศแต่ไม่เคยถูกขอ · ค่าส่วนต่างสุทธิเป็นร้อยละ · รายการที่อ่อนไหวที่สุดที่อยู่ในส่วนต่าง **ห้ามสรุปจากความรู้สึก ต้องคำนวณจากช่องผลของข้อก่อนหน้าเท่านั้น**
- **ขั้นตอนการตรวจ:**
  1. เปิด `PII-SET` ฉบับสมบูรณ์ แล้วยืนยันว่าทุกแถวมีค่าครบทั้ง 7 ช่อง ถ้ามีช่องว่างให้กลับไปเติมก่อน
  2. นับจำนวนแถวที่มีสถานะถูกขอจริง และจำนวนแถวที่ช่อง `ประกาศในนโยบายหรือไม่` มีค่าว่า "พบ"
  3. คัดผลข้อ 034 เป็นรายการที่ถูกขอแต่ไม่ประกาศ และคัดผลข้อ 035 เป็นรายการที่ประกาศแต่ไม่เคยถูกขอ วางในตารางเดียวกันสองส่วน
  4. คำนวณค่าส่วนต่างสุทธิเป็นร้อยละ โดยใช้จำนวนแถวที่ถูกขอแต่ไม่ประกาศ หารด้วยจำนวนแถวที่ถูกขอจริงทั้งหมด แล้วปัดเป็นจำนวนเต็ม
  5. ทำเครื่องหมายรายการที่อยู่ในสามระดับความอ่อนไหวจากข้อ 034 โดยเรียงระดับข้อมูลชีวมิติและเอกสารแสดงตนไว้บนสุด
  6. ให้ผู้ตรวจคนที่สองคำนวณค่าส่วนต่างสุทธิจาก `PII-SET` ชุดเดียวกันโดยไม่เห็นผลของคนแรก แล้วเทียบค่าที่ได้ ถ้าต่างกันให้ไล่หาสาเหตุทีละแถวจนตรงกัน
  7. บันทึกตารางส่วนต่างฉบับสมบูรณ์เป็นไฟล์ `-RED` สำหรับใช้ในรายงาน และเก็บ `PII-SET` ฉบับ `-FULL` ในที่เก็บที่เข้ารหัส แล้วตั้งชื่อไฟล์ตาม Evidence ID
- **หลักฐานที่ต้องเก็บ:** ตารางส่วนต่างฉบับสมบูรณ์ ฉบับ `-RED` (`RST-BRKA-P10-050-01-RED`) · `PII-SET` ฉบับสมบูรณ์ `-FULL` ในที่เก็บที่เข้ารหัส · ผลคำนวณของผู้ตรวจสองคน · รายการที่อ่อนไหวที่สุดในส่วนต่าง
- **ผ่าน:** มีตารางส่วนต่างที่คัดค่ามาจาก `PII-SET` ครบทุกแถว ผู้ตรวจสองคนคำนวณค่าส่วนต่างสุทธิได้ค่าเดียวกัน และหลักฐานถูกเก็บครบทั้งฉบับ `-FULL` และ `-RED` ตามกฎความปลอดภัยของเสานี้
- **ไม่ผ่าน:** ไม่มีตารางส่วนต่าง หรือมีแถวใน `PII-SET` ที่ยังมีช่องว่าง หรือผู้ตรวจสองคนคำนวณได้ต่างกันหลังไล่หาสาเหตุครบแล้ว หรือมีหลักฐานที่เก็บเพียงฉบับเดียวโดยไม่ครบสองชุด
- **ยังไม่ได้ตรวจ:** ยังตรวจข้อ 026–049 ไม่ครบทุกข้อ
- **ตัวอย่าง:** ผู้ตรวจ Broker A ได้แถวที่ถูกขอจริง 14 แถว ประกาศ 11 แถว ถูกขอแต่ไม่ประกาศ 3 แถว คำนวณส่วนต่างสุทธิได้ 21% ผู้ตรวจคนที่สองคำนวณได้ 21% เท่ากัน และเก็บหลักฐานครบทั้ง `-FULL` และ `-RED` → **ผ่าน**
